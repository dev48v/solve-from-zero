🌐 IDNA + punycode + homograph analyzer — a real UTS #46 / RFC 5891 / RFC 3492 engine. Type a domain in any script and it computes the exact xn-- form your resolver will see, and for anything it refuses it names the condition that decided. The trap at the centre is not a character that means two things — it is a pipeline order: case folding runs before the deviation rule, so faß.de resolves to xn--fa-hia.de and FAẞ.DE — the same German word, shouted — resolves to fass.de. Two different servers, one word, decided by the shift key. 69 reference cases and 232 verifier assertions, checked against an independent shipping UTS #46 implementation with zero disagreements over 3,325 code points and 2,084 generated domains; a live sweep showing that NFKC + toLowerCase reproduces the real 1.1 MB mapping table on 94.6% of code points, where the missing 182 are not scattered exceptions but four named families — and the smallest family is the one holding that capital sharp s; and the Bidi Rule’s six numbered conditions measured over 21,706 labels, where the specification refuses 21.3% of what the browser resolves, always in the same direction, through exactly two of its six conditions. The neighbour. 1abc.example.com is a legal domain. 1abc.مثال.com is not — RFC 5893 condition 1 says a label of a Bidi domain must begin with a strong character, and 1 is a European Number. REFERENCE CASES

running…

Two servers, one word, and the shift key decides which one you reach.

A domain name is not text. It is ASCII, and it has been ASCII since 1987. Every non-ASCII domain you have ever seen — every Cyrillic shop, every Japanese blog, every emoji vanity URL — is a lie your browser tells you on the way to a label that begins xn--. The machinery that performs the lie is IDNA, and it is four specifications deep: RFC 3492 for the encoding, RFC 5891 for validity, RFC 5892 for which characters exist, RFC 5893 for right-to-left, and UTS #46 sitting on top translating between the 2003 version and the 2008 one. Almost every hand-rolled implementation is wrong in the same three places.

1. The bug is the order of the stages, not any one stage

faß.de     →  xn--fa-hia.de     the sharp s survives
FAẞ.DE     →  fass.de           the sharp s became "ss"
Faß.de     →  xn--fa-hia.de     lowercase again, back to the first answer

Same word. Two domains. Nothing in the IDNA switches changed between those three lines — all three are nontransitional processing, the modern default, the one that exists specifically so that ß is preserved rather than expanded. And it is preserved, faithfully, on the first and third lines.

The reason the middle line escapes is that the pipeline has an order:

1  split on label separators
2  MAP each code point        ← case folding lives here
3  apply the DEVIATION rule   ← ß ς ZWJ ZWNJ get decided here
4  normalise to NFC
5  validate the label
6  punycode-encode

U+1E9E LATIN CAPITAL LETTER SHARP S is mapped, and its mapping target is ss — two ASCII letters — not U+00DF. So by the time stage 3 goes looking for a deviation character, the uppercase spelling no longer contains one. The escape hatch IDNA2008 built for the sharp s is only reachable from the lowercase form. There is no flag for this, no error, and no warning: you type a word in capitals and arrive somewhere else.

The same shape, one letter over: Σ case-folds to σ, never to ς. So ς.gr is xn--3xa.gr, and Σ.gr is xn--4xa.gr — final sigma and capital sigma are the same letter in Greek and different domains in DNS. Under the 2003 rules all three collapsed onto xn--4xa; the modern rules split them, which is why a registry that upgraded had to decide what to do with names it had already sold.

2. In a punycode label every hyphen is data, except the last one

xn--bcher-kva        bücher          one hyphen: it is the delimiter
xn--mller-in-65a     müller-in       three hyphens: two are letters
xn--co-oprative-fbb  co-opérative    the one at the end is structure
xn--n3h              ☃               no ASCII survivors, so NO delimiter at all

The literal ASCII characters of the original label are copied out first, then a single -, then the deltas. If the original label already contained hyphens they are copied out too, as data — so a label can hold three hyphens of which exactly one is punctuation, identified only by being last. Write body.indexOf('-') instead of body.lastIndexOf('-') and you have a decoder that is correct on xn--bcher-kva, correct on xn--mnchen-3ya, correct on every single-word label anyone will ever paste into your test file, and wrong on every hyphenated one. The score is on the ANALYSE tab: 0% wrong on labels without an internal hyphen, 100% wrong on labels with one.

And the fourth line is the case that catches the off-by-one instead: when the original label is entirely non-ASCII there are no survivors to copy, so the encoder emits no delimiter. lastIndexOf returns −1 and a decoder that trusts it slices the first delta digit off as though it were literal text.

3. xn-- is not a marker. It is a position.

The four characters xn-- mean “decode me” at offset 0 and mean nothing anywhere else — myxn--foo is an ordinary label. And the test runs after case folding, so XN--MNCHEN-3YA is an encoded label too. That reserved slot is also why the strangest rule in RFC 5891 exists:

ab--cd    INVALID    "--" sits in the 3rd and 4th character positions
a--bcd    valid      same two hyphens, one position to the left
abc--de   valid      same two hyphens, one position to the right

Two hyphens, three labels, identical characters, and only the offset decides. The positions are reserved so that a future encoding could claim ??-- the way punycode claimed xn--. It is the purest positional rule in any of the specs on this page — and your browser does not implement it. WHATWG URL calls ToASCII with CheckHyphens = false, which switches off that rule and the leading-hyphen rule and the trailing-hyphen rule together, so -ab.com and ab-.com both parse fine and then fail in DNS instead, one layer down, with a different error message.

4. Two invisible characters, adjacent code points, opposite verdicts

ب‌ب   VALID     U+200C ZWNJ  between two dual-joining letters
ب‍ب   INVALID   U+200D ZWJ   in the identical slot

Both are deviation characters. Both are zero width. Both are governed by the same CONTEXTJ machinery in RFC 5892 Appendix A. The difference is that ZWNJ has two rules and ZWJ has one: both may follow a Virama, and only ZWNJ may additionally sit between a left- or dual-joining letter and a right- or dual-joining one, skipping any transparent combining marks in between. So in Arabic and Persian, where ZWNJ does real orthographic work, it is allowed; ZWJ, which does not, is not. You cannot see either character, you cannot tell them apart in a diff, and one of them costs you the registration.

The neighbours matter as much as the character: ا‌ب is invalid because ALEF is right-joining, so there is nothing on the left of the ZWNJ for it to be joining from. Reverse the letters and ب‌ا is fine.

5. Four characters are silently deleted, and that is a security feature in reverse

SOFT HYPHEN, COMBINING GRAPHEME JOINER, ZERO WIDTH SPACE and the sixteen variation selectors have status ignored: not rejected, not mapped — removed. Which means:

exa<U+200B>mple.com   IS   example.com

Not “looks like”. Is. Same ACE, same DNS query, same certificate. This is usually taught as reassuring, and it is exactly backwards: a blocklist that compares the typed host string against example.com does not match, so the request is allowed through and then resolves to the thing you were blocking. The lesson is that no security decision may be taken on a host string before ToASCII has run on it.

6. A label can be made illegal by a label three dots away

RFC 5893's Bidi Rule applies to every label of a domain as soon as any label contains a right-to-left character. Condition 1 requires each label to start with a strong character — L, R or AL — and a digit is none of those. So:

1abc.example.com               valid
1abc.مثال.com   condition 1 — and 1abc did not change

This is the same shape as the hyphen rule but at the wrong scale: the thing being validated is a label, and the thing that decides is not in it. Measured over an exhaustive 21,706-label sweep, this one condition accounts for 3,676 of the 4,626 places where the RFC refuses a label a browser resolves — and the divergence is entirely one-directional. The spec is strictly stricter; there is not a single label in the sweep that the RFC accepts and the browser rejects. Which tells you what CheckBidi is really for: it is a registry rule, and the resolution path cannot afford it.

7. The famous attack is not a mixed-script attack

In 2017 аррӏе.com was registered and demonstrated against Chrome and Firefox. Every character is Cyrillic: A, ER, ER, PALOCHKA, IE. So under UTS #39 it is Single Script — the second-best restriction level there is, better than Teχ, better than any genuine Latin-plus-Greek mathematical notation. A mixed-script detector reports it as clean, and it is right to: there is no mixture.

The rule that catches it is whole-script confusability, which is a different mechanism entirely: normalise each character through a confusables table to its prototype, then compare the resulting skeletons. And that mechanism has its own blind spot, also structural: the skeleton is computed per character, so a spoof that spends two characters to buy one — rn for m, vv for w, cl for d — cannot be seen by it at all. rnicrosoft.com is pure ASCII, one script, and its skeleton is not microsoft.com. Three detectors, three mechanisms, three disjoint blind spots, and the scoreboard is on the ANALYSE tab.

The exclusion list is the rule. UTS #39's Moderately Restrictive level allows Latin plus any one other script — except Cyrillic, Greek and Cherokee. That is the entire content of the level: three scripts, chosen because their lowercase letters are the ones that look like Latin ones. A level defined by a three-item denylist is a level that a new script can walk straight through.

8. What was actually hard

  • The mapping table is 1.1 MB of data and this page is one file. Deriving it from NFKC and toLowerCase gets 94.6% of the swept code points right, and the missing 182 sort into four families rather than a list: unassigned code points, the format and separator categories, the twenty-two characters that are silently deleted, and a residue of twenty-six that no rule predicts. One regular expression closes each of the first two families, so a hand-rolled mapper climbs to the high nineties and stops — and the residue is where ẞ→ss lives, the headline of this page, next to U+04C0 Ӏ, which is disallowed while its own lowercase U+04CF ӏ is valid and is the character in the apple spoof. Nothing about the shape of either one says it is special.
  • Every character that maps to something containing a dot has to be disallowed, not mapped — otherwise one code point could split a label in two. U+2488 “⒈” NFKC-decomposes to 1., and if you map it you have invented a new label separator.
  • UseSTD3ASCIIRules = false does not mean any ASCII punctuation is allowed. The URL parser has its own forbidden-host set layered on top, which is why _ survives into a hostname and fullwidth ＠ does not, even though UTS #46 gives them the same status.

🔨 How it is built

1. The pipeline is data, so the order is inspectable

The stages are an array, each one a pure string→string function with a name. The panel on the ANALYSE tab is not a diagram of the pipeline, it is the pipeline, printed with the input and output of each stage. That is the only reason the FAẞ.DE finding is visible rather than merely true: you can watch stage 2 turn the sharp s into ss and stage 3 find nothing to do.

const STAGES = [
  ["split",     s => s.split(SEPARATOR_RE)],
  ["map",       (s,o) => mapString(s, o)],       // case folding lives here
  ["deviation", (s,o) => o.transitional ? expandDeviations(s) : s],
  ["nfc",       s => s.normalize("NFC")],
  ["validate",  (s,o) => checkLabel(s, o)],
  ["encode",    s => aceOf(s)]
];

2. Punycode over code points, never UTF-16 units

const cps = Array.from(label).map(c => c.codePointAt(0));   // not label.charCodeAt

RFC 3492 encodes Unicode scalar values. Iterate a JS string with charCodeAt and .length and you feed the algorithm surrogate halves: U+D83D and U+DCA9 instead of U+1F4A9. Both are in range, both encode without an error, and the output is a valid punycode label for a domain that does not exist. The scoreboard measures it: 0 wrong on the Basic Multilingual Plane, every single one wrong above it, which is to say the bug is invisible until the first person registers an emoji domain.

3. The decoder is where the overflow checks earn their place

if (d > Math.floor((MAXINT - i) / w))        throw err("overflow");
i += d * w;
const t = k <= bias ? TMIN : (k >= bias + TMAX ? TMAX : k - bias);
if (d < t) break;
if (w > Math.floor(MAXINT / (BASE - t)))     throw err("overflow");

Both guards are in the RFC and both are routinely dropped, because in JavaScript nothing visibly breaks: you get a float, then a code point past U+10FFFF, then String.fromCodePoint throws somewhere unrelated. Keeping them turns a crash into a named refusal, which is the whole product here.

The other half of decoding is a check that has nothing to do with arithmetic: re-encode the result and require the original back. RFC 3492's encoder is deterministic, so a label that decodes to something which does not re-encode to itself was never produced by a conforming encoder. Skip that check and xn---kva — a delimiter in position 0, which the encoder never emits — decodes happily, and you have handed one domain two spellings and every cache and allowlist downstream a way to disagree.

4. The mapper is derived, and the exceptions are a table with reasons in it

let m = ch.normalize("NFKC").toLowerCase().normalize("NFC");
for (const c of m) if (SEPARATOR.has(c) || c <= " ") return DISALLOWED;
return m === ch ? VALID : { MAPPED, to: m };

Three lines, plus one property escape for the unassigned code points and one for the format and separator categories, and the live sweep on the ANALYSE tab says how far that gets: 94.6%. The exception list that closes the rest is twenty-six entries, each carrying the reason it is not derivable — a deprecated case pair, a symbol whose compatibility decomposition would introduce a dot, a capital whose fold target is two ASCII letters. The page runs the sweep on every load and prints the exceptions beside it rather than claiming completeness: everything outside those 23 blocks is still handled by the derived rule, and the page says so instead of pretending it shipped a megabyte.

5. Bidi and CONTEXTJ are class lookups, not regexes over characters

function bidiLabel(cs, cond){        // cs = array of Bidi classes
  if (cs[0] !== "L" && cs[0] !== "R" && cs[0] !== "AL") return 1;
  const rtl = cs[0] !== "L";
  if (rtl  && !cs.every(c => RTL_OK.has(c)))            return 2;
  ...
  if (!rtl && !cs.every(c => LTR_OK.has(c)))            return 5;
}

It returns the condition number, not a boolean, for the same reason Day 68's filter returned an index: the label table and the “why was this refused” line are the same call, so they cannot drift apart and give two different answers about one label. Combining marks are found with /\p{M}/u rather than a hand-typed range list — Unicode property escapes are a language feature, so NSM and the leading-combining-mark rule cost one regex each and stay correct as Unicode grows.

6. The three homograph detectors deliberately share no code

Mixed-script works on resolved script sets. Whole-script works on confusable skeletons. Sequence works on a small table of many-to-one visual substitutions. If they shared a normalisation step they would share a blind spot, and the whole point of the scoreboard is that their blind spots are disjoint — which is also the argument for running all three rather than picking the best one.

7. Verified against something that is not this page

Every reference case whose expected value is an ASCII domain was checked against an independent shipping UTS #46 implementation — a different codebase, a different language, a different mapping table — rather than against what this engine happens to produce. The same harness sweeps a generated corpus of non-Bidi domains for exact agreement, and handles the Bidi corpus separately with a one-directional claim: the RFC model must never accept a label the browser rejects. Zero counterexamples, which is a much stronger statement than a pass count.

One thing this page does not do. It does not ship the full IdnaMappingTable, the full confusables table, or complete Bidi_Class and Joining_Type data. Those are megabytes. It ships a derived mapper with a measured error rate, a curated confusables subset, and class tables covering the scripts it demonstrates — and it prints all three scopes on screen. A tool that quietly pretended otherwise would be worse than one that tells you where it stops.
