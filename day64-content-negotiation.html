SOLVEFROMZERO · DAY 64

🤝 Content negotiation — paste a real Accept header and watch a hand-written RFC 9110 matcher pick the representation, showing its working. Almost nobody reads these headers correctly, because the rules are not "highest q wins". Specificity is sorted before q: text/html beats text/* beats */*, and a parameter count breaks ties above that — so text/html;level=1 outranks plain text/html regardless of the q values. A q of 0 is not a preference, it is a prohibition: it means "never send me this", and a server that treats it as "low priority" will cheerfully return a representation the client explicitly refused. Browsers ship headers like text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8, and this page shows exactly why that produces HTML rather than XML. The same algorithm then runs for Accept-Language (with the basic-filtering prefix rules from RFC 4647, where en matches en-GB but never the reverse), Accept-Encoding (with its special identity rule), and Accept-Charset. Vanilla JS, no network.

It is not "highest q wins"


      
Almost every hand-rolled Accept parser sorts by q and takes the top. That is
      wrong, and the header every browser sends proves it:


      
Accept: text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8


      
Sort by q and text/html (q=1, implied) ties with
      application/xhtml+xml, and */* at q=0.8 loses to both — fine so far.
      But now consider a server offering only application/json. It matches
      */* at q=0.8. Should it be served? Yes. And a server offering both
      application/xml and text/html? HTML, because
      specificity outranks q.


      

        
The actual comparison order

        
    
          
  1. Specificity — exact type/subtype beats type/* beats */*
    2. 
          
  2. Parameter count — text/html;level=1 beats plain text/html
    3. 
          
  3. q value — only now does the weight matter
    4. 
        

      


      
So a client saying text/plain;q=0.1, */*;q=1.0 and a server offering
      text/plain gets text/plain, at q=0.1, even though the wildcard
      carries q=1.0 — because the exact match is more specific. That result surprises people, and it
      is unambiguously correct.


      
q=0 is a prohibition

      

        
A quality of zero means "not acceptable" — never send it.
        It is not "low priority". Treat it as a weight and you will happily return a representation
        the client explicitly forbade, which is how Accept-Charset: *;q=0 ends up
        serving a charset that was refused. This page counts refusals separately for exactly that
        reason.

      


      
406 is real, and rarer than you think

      
When nothing on offer is acceptable, the correct answer is 406 Not Acceptable.
      In practice a */* in the header means it almost never fires — which is why the
      status only appears when the client sent a genuinely closed list, or refused everything with
      q=0.


      
Languages match by prefix, in one direction

      
RFC 4647 basic filtering: the range en matches the tag en-GB,
      because en-GB is a refinement of en. The reverse is not true —
      a client asking for en-GB is not automatically satisfied by en-US.

      
The match must also fall on a subtag boundary: en matches en-GB
      but must not match eng. Comparing with startsWith and forgetting the
      hyphen is the classic bug here.


      
Encoding has a rule of its own

      
identity — meaning no compression — is always acceptable unless
      explicitly refused, even if it is not listed. That is a special case in the spec, and
      omitting it produces a server that 406s a client which simply forgot to mention it.


      
And whatever you negotiate on, you must Vary on

      
If the response depends on Accept-Language, the response must carry
      Vary: Accept-Language, or a cache will serve one visitor's language to another.
      Negotiation without Vary is not a partial implementation; it is a correctness bug
      that only appears once a cache is in front of you.


    

  






  

    


      
🔨 Build it yourself


      
1. Parse one range at a time

      
function parseRange(part){
  const bits = part.trim().split(";");
  const [type, subtype] = bits.shift().trim().toLowerCase().split("/");
  let q = 1, params = 0;
  for (const bit of bits){
    const [k, v] = bit.trim().split("=");
    if (k.trim().toLowerCase() === "q") q = clamp01(parseFloat(v));
    else params++;                       // media-type params, NOT accept-params
  }
  return { type, subtype: subtype || "*", q, params };
}

      
Everything after q is an accept-param and does not count toward specificity.
      Counting them is a common and quiet mistake.


      
2. Specificity as a number

      
function specificity(r){
  if (r.type === "*") return 1;          // */*
  if (r.subtype === "*") return 2;       // type/*
  return 3;                              // type/subtype
}


      
3. Pick the best matching range for one offer

      
function bestRangeFor(offer, ranges){
  const [ot, os] = offer.toLowerCase().split("/");
  let best = null;
  for (const r of ranges){
    const matches = (r.type === "*")
      || (r.type === ot && (r.subtype === "*" || r.subtype === os));
    if (!matches) continue;
    if (!best || better(r, best)) best = r;
  }
  return best;
}

// specificity, THEN params, THEN q - in that order
function better(a, b){
  if (specificity(a) !== specificity(b)) return specificity(a) > specificity(b);
  if (a.params !== b.params)             return a.params > b.params;
  return a.q > b.q;
}


      
4. Choose, and honour the prohibition

      
function negotiate(header, offers){
  const ranges = parseAccept(header);
  let winner = null, winnerRange = null;
  for (const offer of offers){            // server order = the tiebreak
    const r = bestRangeFor(offer, ranges);
    if (!r) continue;                     // nothing matched at all
    if (r.q === 0) continue;              // EXPLICITLY refused - never send it
    if (!winner || r.q > winnerRange.q) { winner = offer; winnerRange = r; }
  }
  return winner ? { offer: winner, q: winnerRange.q, status: 200 }
                : { offer: null, status: 406 };
}

      
Note the two different continues. "No range matched" and "a range matched and
      said no" are different situations, and collapsing them loses the ability to report why.


      
5. Language matching, on subtag boundaries

      
function langMatches(range, tag){
  if (range === "*") return true;
  const r = range.toLowerCase(), t = tag.toLowerCase();
  if (r === t) return true;
  return t.startsWith(r + "-");           // 'en' matches 'en-GB', never 'eng'
}

      
The + "-" is the whole rule. Without it en matches
      eng, and you serve English to someone who asked for Engenni.

A parser that passes a synthetic test and fails a real browser header is not a parser. These
      cases are the spec's own examples plus the ones that catch the "sort by q" shortcut.
