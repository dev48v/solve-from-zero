🔀 ULID Generator — a real, from-scratch Universally Unique Lexicographically Sortable Identifier: 128 bits = a 48-bit millisecond timestamp + 80 bits of crypto.getRandomValues randomness, written as 26 Crockford Base32 characters (0123456789ABCDEFGHJKMNPQRSTVWXYZ) · generate one or many, flip on the monotonic factory so IDs minted in the same millisecond stay correctly ordered (increment the random tail), and decode any ULID back to the exact moment it was born plus its random component · because the time sits first, big-endian and fixed-width, sorting ULIDs as plain text sorts them by creation time — a thing a random UUIDv4 can never do · vanilla JS, no library

Same 128 bits as a UUID — but they sort themselves.

A ULID packs the uniqueness of a UUID into a friendlier, time-ordered shape. The left 48 bits are a Unix millisecond timestamp; the right 80 bits are pure randomness from crypto.getRandomValues. Both halves are written in Crockford's Base32 — 26 characters drawn from 0123456789ABCDEFGHJKMNPQRSTVWXYZ (no I L O U, so nothing gets mistaken for a digit). Because the timestamp comes first, is big-endian and fixed-width, sorting ULIDs as plain strings sorts them by creation time — something a random UUIDv4 can never do, and the whole reason ULIDs make excellent primary keys. Generate a batch and watch them climb; flip on the monotonic factory and mint several in the very same millisecond to see them stay in order; then decode any ULID back to the exact moment it was created. All in your browser, no library.

Five things worth knowing about ULIDs

1. The timestamp is not a secret. Anyone can decode a ULID's first 10 characters back to the millisecond it was created — that is the feature, not a leak, but do not use a ULID where you would not print a creation time. 2. Randomness carries the collision resistance. Within one millisecond the only thing separating two IDs is 80 random bits, so the birthday-bound is ~2⁴⁰ IDs per ms before a coin-flip collision — astronomically safe, but it is the random half doing the work, which is why we draw it from crypto.getRandomValues, not Math.random(). 3. Monotonicity is what makes same-ms IDs sort. Plain generation randomises the whole tail each call, so two IDs born in the same millisecond can land in either order; the monotonic factory instead increments the previous random value by one, guaranteeing the later ID is the larger string. 4. Crockford Base32 excludes I L O U. Decoding treats I and L as 1 and O as 0, so a hand-typed ULID is forgiving; U is dropped entirely to avoid accidental words. 5. Sorting works only because time is first, big-endian and fixed-width. Ten characters, most-significant first, always the same length — that is the exact recipe that makes ASCII/byte order equal chronological order. Break any of those three and the guarantee evaporates.

🔨 Build it yourself

    
A ULID generator is small: one 32-character alphabet, one function to encode a 48-bit time into 10 characters, one to encode 80 random bits into 16 characters, and a factory that remembers the last one so it can stay monotonic. Decoding is the same steps run backwards. The only real subtleties are keeping the random half as bytes (80 bits overflows a JS number, so you cannot hold it as one integer), draining a bit-buffer 5 bits at a time to hit Crockford Base32, and incrementing those bytes with carry for monotonicity. No parser, no dependency — well under 100 lines. Here it is, step by step.

    
    
      
  1. 
        
    1
    The alphabet and the shape
    
        
    Crockford Base32 is 32 symbols — the digits plus the uppercase letters, minus I L O U so nothing is mistaken for 1 0 or spells words. A ULID is always 128 bits: a 48-bit timestamp encoded as 10 characters (10×5 = 50 bits, top 2 always zero) followed by 80 random bits as exactly 16 characters. 10 + 16 = 26.
    
        
    const B32 = "0123456789ABCDEFGHJKMNPQRSTVWXYZ"; // no I L O U
const TIME_LEN = 10;   // 48-bit ms timestamp  -> 10 chars
const RAND_LEN = 16;   // 80 bits of randomness -> 16 chars
const RAND_BYTES = 10; // 80 bits = 10 bytes
// total 26 chars = 128 bits, same budget as a UUID
    
      
    2. 
      
  2. 
        
    2
    Encode the 48-bit timestamp → 10 chars
    
        
    A millisecond timestamp is at most 48 bits, and 2⁴⁸ is comfortably below Number.MAX_SAFE_INTEGER (2⁵³), so plain arithmetic is exact. Build the 10 characters right-to-left by repeatedly taking the value mod 32 (the low digit) and dividing by 32 — the same base-conversion you would do by hand, just in base 32.
    
        
    function encodeTime(ms){
  if (ms < 0 || ms > 0xFFFFFFFFFFFF) throw new RangeError("time");
  let out = "";
  for (let i = TIME_LEN - 1; i >= 0; i--){
    const mod = ms % 32;              // low base-32 digit
    out = B32[mod] + out;            // prepend  (big-endian)
    ms = (ms - mod) / 32;            // shift right by one digit
  }
  return out;                        // 10 chars, most-significant first
}
    
      
    3. 
      
  3. 
        
    3
    80 real random bits
    
        
    The random half must be cryptographically strong, so fill ten bytes from crypto.getRandomValues. Ten bytes is 80 bits — kept as a byte array, never a single number, because 2⁸⁰ is far past what a JS Number can hold exactly. Those bytes are the value we will both encode and, for monotonicity, increment.
    
        
    function randomBytes(){
  const a = new Uint8Array(RAND_BYTES);  // 10 bytes = 80 bits
  crypto.getRandomValues(a);             // CSPRNG, not Math.random()
  return a;
}
    
      
    4. 
      
  4. 
        
    4
    Encode 80 bits → 16 chars (a bit buffer)
    
        
    Base32 wants 5 bits per character but bytes come in 8s, so stream them through a small buffer: shift each byte in, and whenever at least 5 bits are queued, pull the top 5 out as one character. 80 divides evenly by 5, so exactly 16 characters come out with no padding and no leftover bits.
    
        
    function encodeRandom(bytes){
  let out = "", buf = 0, bits = 0;
  for (let i = 0; i < bytes.length; i++){
    buf = (buf << 8) | bytes[i];       // push 8 bits in
    bits += 8;
    while (bits >= 5){                 // pull 5-bit groups out
      bits -= 5;
      out += B32[(buf >> bits) & 31];
    }
  }
  return out;                          // exactly 16 chars, bits === 0
}
    
      
    5. 
      
  5. 
        
    5
    A plain ULID
    
        
    Glue the two halves together and you have a valid ULID: current time as 10 characters, fresh randomness as 16. This alone is spec-correct — but two calls inside the same millisecond get independent random tails, so their relative order is a coin toss. Fixing that is the next step.
    
        
    function ulid(ms = Date.now()){
  return encodeTime(ms) + encodeRandom(randomBytes());
}
// e.g. 01ARZ3NDEK | TSV4RRFFQ69G5FAV
//      ^ 10 time    ^ 16 random
    
      
    6. 
      
  6. 
        
    6
    Increment bytes with carry
    
        
    Monotonicity means: same millisecond ⇒ take the previous random value and add one. Since it is a byte array, "add one" is grade-school carrying from the last byte: if a byte is 0xFF it wraps to 0 and the carry moves left. Overflowing all ten bytes in a single millisecond is impossible in practice, but guard it anyway.
    
        
    function incrementBytes(bytes){
  for (let i = bytes.length - 1; i >= 0; i--){
    if (bytes[i] < 0xFF){ bytes[i]++; return bytes; } // no carry
    bytes[i] = 0;                                     // carry left
  }
  throw new Error("random overflow within the same millisecond");
}
    
      
    7. 
      
  7. 
        
    7
    The monotonic factory
    
        
    A closure remembers the last timestamp and last random bytes. New millisecond → fresh random. Same millisecond → increment the remembered bytes. Because the timestamp is identical and the random tail only ever goes up, the newer ULID is always the larger string — sortable even at machine speed.
    
        
    function monotonicFactory(){
  let lastTime = -1, lastRand = null;
  return function(ms = Date.now()){
    if (ms === lastTime){
      lastRand = incrementBytes(lastRand.slice()); // +1 on a copy
    } else {
      lastTime = ms;
      lastRand = randomBytes();                    // new ms -> new random
    }
    return encodeTime(lastTime) + encodeRandom(lastRand);
  };
}
    
      
    8. 
      
  8. 
        
    8
    Decode: normalise, then split
    
        
    Decoding starts by cleaning the input: upper-case it and apply Crockford's forgiving substitutions — O is really 0, I and L are really 1. Then check the length is 26 and split into the 10-character time and 16-character random parts. The first character must be ≤ 7, or the timestamp would exceed 48 bits.
    
        
    function normalize(s){
  return s.trim().toUpperCase()
    .replace(/O/g, "0").replace(/[IL]/g, "1"); // U stays invalid
}
function splitUlid(input){
  const s = normalize(input);
  if (s.length !== 26) throw new Error("a ULID is 26 characters");
  for (const c of s) if (B32.indexOf(c) < 0) throw new Error("bad char " + c);
  if (B32.indexOf(s[0]) > 7) throw new Error("timestamp overflow (> 48 bits)");
  return { time: s.slice(0, 10), rand: s.slice(10) };
}
    
      
    9. 
      
  9. 
        
    9
    Decode the time and the random bytes
    
        
    The timestamp is Horner's method in base 32: acc = acc·32 + digit, giving back the millisecond value you can hand to new Date(). The random half runs the bit-buffer the other way — shift 5 bits in per character, pull whole bytes out — reproducing the exact ten bytes, which prove the round-trip when you re-encode them.
    
        
    function decodeTime(str){
  let ms = 0;
  for (const c of str) ms = ms * 32 + B32.indexOf(c); // base-32 Horner
  return ms;                                           // milliseconds
}
function decodeRandom(str){
  const bytes = []; let buf = 0, bits = 0;
  for (const c of str){
    buf = (buf << 5) | B32.indexOf(c);  // push 5 bits in
    bits += 5;
    if (bits >= 8){ bits -= 8; bytes.push((buf >> bits) & 0xFF); } // pull a byte
  }
  return bytes;                          // 10 bytes
}

  10. 
        
    10
    Why they sort — and the round-trip test
    
        
    The sort guarantee is pure structure: the timestamp is first, big-endian, and fixed-width, and the Base32 alphabet is in ascending value order — so byte-comparing two ULIDs compares their timestamps first, then their random tails, which is exactly chronological order. And because decode is the mirror of encode, re-encoding a decoded ULID reproduces it character-for-character.
    
        
    const mint = monotonicFactory();
const a = mint(1700000000000), b = mint(1700000000000); // same ms
console.assert(a < b, "same-ms IDs stay ordered (monotonic)"); // ✓

const { time, rand } = splitUlid(a);
const ms = decodeTime(time);                       // 1700000000000
console.assert(encodeTime(ms) === time, "time round-trips");   // ✓
console.assert(encodeRandom(Uint8Array.from(decodeRandom(rand))) === rand,
  "random round-trips");                                       // ✓

🎉 Day 54 of SolveFromZero.
You built a real ULID generator with no library. It rests on three ideas: a 48-bit timestamp base-converted into 10 Crockford Base32 characters, 80 crypto-random bits streamed through a 5-bit buffer into 16 more, and a monotonic factory that increments the random bytes with carry so IDs minted in the same millisecond still sort. Because the time sits first — big-endian, fixed-width, ascending alphabet — comparing the strings is the same as comparing the moments, which is the one superpower a random UUIDv4 will never have. That is why ULIDs make such good time-ordered primary keys.
