🍪 cookie jar simulator — a real RFC 6265 engine with state. Feed it the Set-Cookie headers a server sent, then ask for a URL, and it computes the exact Cookie: request header a browser would send — in the right order, naming which rule dropped every cookie that did not make it. The trap at the centre is a token that is legally two different things depending only on where it sits: Set-Cookie: Secure=1 is a cookie named Secure that goes over plain HTTP, while Set-Cookie: a=b; Secure is a flag — same nine characters, opposite meaning. Then the rules people invert: the default Path is not /, path matching is not a string prefix, and adding Domain=example.com makes a cookie broader than leaving it off. The jar key is (name, domain, path), so two cookies can share a name and both get sent. RFC 6265 (2011) and RFC 6265bis (what browsers do now) disagree on 7 of 12 scenarios, counted live rather than asserted. 76 reference cases. Pure vanilla JavaScript, one file, offline.

76 REFERENCE CASES


      


    

  






  

    


      
A cookie is four lines of syntax and eight rules of state.


      
Everyone can read a Set-Cookie header. Almost nobody can predict the
      Cookie header that comes back, because the answer depends on a stored jar, and
      the storage rules are where the surprises live.


      
1. The same token is a name or a flag, depending on position


      
Set-Cookie: Secure=1; Path=/     → a cookie NAMED "Secure". Not secure. Goes over http.
Set-Cookie: a=b; Secure          → the flag. The cookie never leaves https.


      
The parser splits on the first semicolon and takes everything before it as
      the name-value pair, unconditionally. Whatever is in that slot is a name, even if it spells
      Secure, HttpOnly or Domain. Everything after the first
      semicolon is an attribute, even if it looks like a cookie.


      
Which produces the other half of the same trap:


      
Set-Cookie: a=b; c=d             → ONE cookie. "c" is an unknown attribute, silently ignored.


      
One header sets one cookie. There is no syntax for two. Code that "sets several cookies in
      one header" is setting one and discarding the rest with no error anywhere.


      
2. The comma that eats the date


      

        
HTTP lets you fold repeated headers into one comma-separated line. Every
        header except this one. Expires=Wed, 09 Jun 2021 10:18:14 GMT contains
        a comma inside a value, so folding two Set-Cookie headers together and splitting
        them apart again produces garbage — and never an error.

      


      
Set-Cookie: a=b, c=d             → ONE cookie, name "a", value "b, c=d".


      
This is why Set-Cookie is carved out by name in RFC 9110 as the field that
      cannot be combined, and why every HTTP library has a special case for it.


      
3. The default Path is not /


      
Omit Path and the cookie does not get the whole site. It gets the
      directory of the URL that set it: everything up to but not including the last slash.


      
set at /app/login   → Path=/app        set at /app/       → Path=/app
set at /login       → Path=/           set at /            → Path=/


      
So a session cookie set by POST /app/login is invisible to /, and
      the bug reads as "the user is logged out on the home page only".


      
4. Path matching is not a prefix test


      
Path=/foo does not match /foobar. The rule has
      three branches: exact equality, or a prefix where the cookie path already ends in
      /, or a prefix where the next character of the request path is a
      /. A plain startsWith leaks /admin cookies to
      /administrator.


      
5. Domain widens. It never narrows.


      
Set-Cookie: a=b                       → host-only. ONLY example.com.
Set-Cookie: a=b; Domain=example.com   → example.com AND every subdomain.


      
Adding the attribute you thought was a restriction is the thing that shares your cookie
      with every subdomain you do not control. And you cannot go the other way: a page on
      example.com setting Domain=shop.example.com is rejected outright.


      
The leading dot in Domain=.example.com is dropped. It is not a
      "include subdomains" switch — it is a fossil from the 1994 Netscape spec, where the
      absence of a dot meant host-only. RFC 6265 made subdomains the behaviour for both forms and
      kept the dot only so old headers keep parsing.


      
Finally, Domain=com is refused, and so is Domain=co.uk: a
      public suffix may not be claimed, or one site could set a cookie for every site under
      it. That check needs the Public Suffix List — roughly ten thousand entries maintained by
      hand, because there is no algorithm that separates co.uk from
      example.com. This page embeds a small subset of it.


      
6. The jar key is (name, domain, path)


      
Not the name. Two cookies called sid at / and /admin
      are two rows in the jar, and both are sent, in one header, with the longer path first:


      
Cookie: sid=admin-value; sid=root-value


      
A server reading only the first value gets whichever cookie has the longest path, which is
      a property of the jar and not of anything the server did. This is the classic "I logged out
      and I am still logged in" bug: the delete removed one row and the other one is still there,
      because a delete only matches if the domain and path match too.


      
And the rule that hides inside an overwrite: when a cookie replaces one with the same key,
      it inherits the old creation time. Ordering in the header uses creation time
      as its tiebreak, so refreshing a cookie does not move it to the end — a detail that only
      becomes visible when two cookies share a name.


      
7. Max-Age beats Expires, and 0 is a value


      
If both are present, Max-Age wins regardless of order. Max-Age=0
      and any past Expires both mean delete now — and 0 is
      the number that if (maxAge) quietly skips, so the delete never happens and the
      session never ends. An unparseable value in either attribute is ignored, not an
      error: the cookie is stored as a session cookie and outlives what you meant.


      
8. What 2011 did not have


      
    
        
  • SameSite. Absent from RFC 6265 entirely. Modern browsers treat a cookie
        with no SameSite attribute as Lax: sent on same-site requests and
        on top-level safe navigations, withheld from cross-site subresources and from
        cross-site POSTs. That default is the single biggest behaviour change in the header's
        history, and it is invisible in the header itself.
    • 
        
  • SameSite=None requires Secure. Without it the cookie is rejected, so
        the "opt out of the new default" fix fails silently on http.
    • 
        
  • Cookie prefixes. __Secure- requires Secure;
        __Host- additionally requires no Domain and
        Path=/. They are enforced by name, which is the point — the guarantee
        survives being read back by code that never saw the header.
    • 
        
  • Only a secure origin may set a Secure cookie, and a non-secure origin
        may not overwrite one.
    • 
      


      
RFC 6265bis also adds the host-only flag to the jar key, which this page does not model
      — it keeps RFC 6265's (name, domain, path).


      
What a cookie is not


      
    
        
  • Not scoped by port. Unlike almost everything else in the browser,
        cookies ignore the port. :3000 and :8080 share a jar.
    • 
        
  • Not scoped by scheme under RFC 6265 — without
        Secure, an http page reads a cookie an https page set.
    • 
        
  • Not integrity-protected. HttpOnly hides a cookie from
        document.cookie; it does nothing about a network attacker or about the user
        editing the jar by hand.
    • 
      


    

  






  

    


      
🔨 How it is built


      
1. The split that creates the trap

      
const semi = s.indexOf(";");
const nv   = semi < 0 ? s : s.slice(0, semi);   // the name-value pair, WHATEVER it spells
const rest = semi < 0 ? "" : s.slice(semi + 1);
const eq   = nv.indexOf("=");                   // the FIRST '=', so a value may contain more
if (eq < 0) return { ok:false, reason:"no '=' in the pair, ignore the whole header" };

      
Four lines, and three of the page's reference cases fall out of them.
      indexOf(";") before anything else is why Secure=1 is a name.
      indexOf("=") rather than split("=") is why
      token=a=b=c keeps its value. And never splitting on , is why a
      folded Expires date survives — as one cookie with a strange value, which is
      the honest outcome.


      
2. default-path, which is a directory and not a root

      
function defaultPath(uriPath){
  const p = String(uriPath || "");
  if (!p || p.charAt(0) !== "/") return "/";
  const i = p.lastIndexOf("/");
  return i === 0 ? "/" : p.slice(0, i);   // everything BEFORE the last slash
}

      
/app/login becomes /app. The i === 0 branch is the
      one that gets dropped, and dropping it turns /login into "", which
      then matches everything for a completely different reason.


      
3. path-match has three branches, not one

      
function pathMatch(reqPath, cookiePath){
  if (reqPath === cookiePath) return true;                       // exact
  if (reqPath.indexOf(cookiePath) !== 0) return false;           // not even a prefix
  if (cookiePath.charAt(cookiePath.length - 1) === "/") return true;
  return reqPath.charAt(cookiePath.length) === "/";              // the boundary test
}

      
The last line is the whole rule. Without it, Path=/foo matches
      /foobar and a cookie scoped to /admin is handed to
      /administrator.


      
4. domain-match, with the same boundary problem

      
function domainMatch(host, dom){
  if (host === dom) return true;
  if (isIP(host)) return false;                       // an IP matches by equality only
  if (host.length <= dom.length) return false;
  if (host.slice(host.length - dom.length) !== dom) return false;
  return host.charAt(host.length - dom.length - 1) === ".";   // stops notexample.com
}

      
Same shape as path-match, same missing line in most implementations: a plain
      endsWith lets notexample.com match example.com.


      
5. Storage: the key, and the creation time that survives

      
const idx = jar.cookies.findIndex(k =>
  k.name === name && k.domain === domain && k.path === path);   // all THREE
let creation = now;
if (idx >= 0){
  creation = jar.cookies[idx].creation;    // PRESERVED across an overwrite
  jar.cookies.splice(idx, 1);
}
if (expires !== null && expires <= now)
  return { action: idx >= 0 ? "deleted" : "ignored", ... };     // an expiry IS the delete

      
There is no separate delete operation in the protocol. Setting a cookie whose expiry is in
      the past is the delete — and it only works if the name, the domain and the path
      all match the row you meant to remove.


      
6. Retrieval: filter with a reason, then sort

      
sent.sort((a, b) =>
  b.path.length - a.path.length ||     // longest path first
  a.creation - b.creation ||           // then oldest first
  a.seq - b.seq);

      
Every cookie that does not survive the filter is pushed to a skipped list with
      the sentence that rejected it, which is the only reason the page can answer "why is my cookie
      not being sent" instead of showing an empty header.


      
7. Two specs behind one flag

      
function effectiveSameSite(cookie, mode){
  if (mode === "rfc6265") return "none";      // the attribute did not exist in 2011
  const v = cookie.sameSite;
  if (v === "strict" || v === "lax" || v === "none") return v;
  return "lax";                               // the 6265bis default
}

      
The same flag gates the prefix checks, the Secure-origin checks and the
      overwrite-a-Secure-cookie check, so the disagreement count on the SIMULATE tab is measured by
      running one scenario list twice rather than being written down.


      
8. What the 76 reference cases cover

      
Secure=1 is a NAME          a=b; Secure is a FLAG      a=b; c=d is ONE cookie
a=b, c=d is ONE cookie      token=a=b=c keeps its =    no '=' at all is ignored
default Path is a DIRECTORY /foo does not match /foobar   Path=foo is ignored
no Domain = host-only       Domain widens to subdomains   .example.com drops the dot
Domain=com refused          Domain=co.uk refused          IPs match by equality
Max-Age beats Expires       Max-Age=0 deletes             a bad value is IGNORED
the key is name+domain+path an overwrite keeps creation   names are case-SENSITIVE
attributes are case-INsensitive   the LAST duplicate wins
SameSite default is Lax     Lax allows top-level GET, not POST
__Host- forbids Domain      __Host- needs the default path to already be /

      
Each of those is a case where a plausible implementation returns the opposite answer, which
      is the only reason to write a reference case at all.
