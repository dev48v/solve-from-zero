SOLVEFROMZERO · DAY 83

URI Templates (RFC 6570) — {?a,b} emits the ? only if something is defined, {+var} deliberately does not encode /, and {?list*} repeats the name.

What it is, and what it replaces

STEP 1 · THE PROBLEM

A URI Template is a string with holes in it: /users/{id}/repos{?page,per_page}. Hand it a set of variables and it becomes a real URI. That sounds like string formatting, and the reason it is a 40-page RFC instead is that building a URL by concatenation is where bugs live. You forget to escape a slash, you leave a dangling ? when every parameter turned out to be empty, you emit && because one value was null, or you escape a path separator that was meant to stay a path separator. Every one of those is a one-line mistake and every one of them ships. RFC 6570 is the list of answers, written down once, so your code stops re-deciding them per endpoint.

The left column is what a careful developer writes by hand. The right column is what the template says. They disagree in every row — and in the rows where they disagree, the hand-written one is wrong.

The grammar is two things and nothing else

STEP 2 · LITERALS AND EXPRESSIONS

A template is a sequence of literals and expressions. Anything outside { } is a literal and is copied through almost untouched; anything inside is an expression. An expression is an optional one-character operator, then a comma-separated list of varspecs, where a varspec is a variable name with an optional modifier. That is the entire syntax. Everything that follows — the eight operators, the encoding rules, explode, prefix — is about what an expression produces, never about how it is spelled.

Note what is not in the grammar: no nesting, no conditionals, no arithmetic. A variable name may contain a dot, but the dot is part of the name — {a.b} looks up the single key "a.b", it does not reach into an object.

One table. Eight rows. The whole specification.

STEP 3 · THE OPERATOR TABLE

Every operator is fully described by five numbers: the string emitted before the first value, the string emitted between values, whether values are named, what an empty value becomes, and which characters survive unencoded. Learn this table and you have not learned eight features, you have learned one function with five parameters. The implementation below is literally a lookup into these rows — there is no branch anywhere that says "if the operator is ?". That is the point of writing it down this way: the thing that looks like eight behaviours is one behaviour with a configuration.

Two allow-sets, and why {+var} leaves your slashes alone

STEP 4 · PERCENT-ENCODING

Expansion encodes values, and it encodes them in one of exactly two ways. The default keeps only unreserved characters (A-Z a-z 0-9 - . _ ~) and percent-encodes everything else, including /, ? and :. The + and # operators keep unreserved and reserved characters — the URI structural punctuation : / ? # [ ] @ ! $ & ' ( ) * + , ; = — and also copy existing %XX triplets through untouched. That difference is not a convenience, it is a statement about who owns the value: a default expansion treats the value as opaque data, a + expansion treats it as a piece of URI you already trust.

Undefined is skipped. Empty is not.

STEP 5 · THE THREE-STATE RULE

Most expander bugs are this one. A variable has three states, not two: undefined (absent, or null), empty (the zero-length string), and a value. An undefined variable is skipped entirely — no separator, no name, nothing, as if the varspec were not written. An empty string is a perfectly good value and still produces its name and its separator. And the spec goes further: an empty list and an empty map count as undefined, because there is nothing to join. Confusing "empty" with "undefined" is how ?a=&b= turns into ?&, or how a required parameter silently vanishes.

empty_keys is {} and empty_list is []. Both are undefined. empty is "" and is not.

The ? is emitted once, and only if something survived

STEP 6 · FIRST VS SEPARATOR

This is the rule that makes the whole thing worth using. The operator's prefix — the ?, the #, the / — is not emitted when the expression is parsed. It is emitted when the first defined variable is about to be written, and never again; every later variable gets the separator instead. So {?a,b,c} with all three undefined produces the empty string, not ?. With only c defined it produces ?c=3, not ?&&c=3. You cannot get this wrong by accident, because there is nowhere to get it wrong: the flag lives in the loop.

The same loop gives {&x} its purpose: it is {?x} with the prefix changed to &, for when you already wrote a query string by hand and need to continue it.

Named operators write the name; the rest write only the value

STEP 7 · NAMED, AND ifemp

Three operators are named: ;, ? and &. For those, each value is preceded by the variable name and an =. The other five emit the value alone. The subtlety is the empty string: a named operator with an empty value emits the name followed by ifemp, which is = for ? and & but the empty string for ;. That is why {?empty} is ?empty= while {;empty} is ;empty with no equals sign — and that asymmetry is deliberate, because a matrix parameter with no value is a real thing and a query parameter with no value conventionally keeps its =.

Lists, maps, and the star that changes the join

STEP 8 · COMPOSITE VALUES AND EXPLODE

A variable can hold a string, a list, or an associative array. Without the explode modifier *, a composite value is always flattened with commas, no matter which operator you used — so {/list} is /red,green,blue, one path segment. A map flattens to a flat alternating list, key,value,key,value, which is why {keys} loses the pairing entirely. Add the star and the operator's own separator takes over: {/list*} becomes /red/green/blue, three segments, and an exploded map emits real key=value pairs. The star is not "spread" — it is "use my separator instead of the comma".

Read the {keys} row twice. An unexploded map is not key=value pairs with commas between them; it is one flat comma list in which the keys and values alternate. Nothing in the output tells a reader which is which.

Named and exploded: the name comes back, every time

STEP 9 · THE TRAP MOST HAND-ROLLED EXPANDERS FAIL

Combine a named operator with an exploded list and the variable name is repeated for every member: {?list*} is ?list=red&list=green&list=blue. It is tempting to read the star as "drop the name and just spread the values", producing ?red&green&blue — which is not a query string at all, since none of those are name=value pairs. The expansion algorithm in §3.2.1 is explicit, and the specification's own prose example for {?count*} shows the repeated name. If you only ever test exploded lists against the unnamed operators (/, ., +) you will never see the difference, because for those the name genuinely does disappear.

:3 counts characters, and is illegal on a list

STEP 10 · THE PREFIX MODIFIER

{var:3} takes the first three characters of the value and expands those. Three characters, not three bytes and not three percent-encoded triplets — the truncation happens on the decoded string, before encoding, so a value of /foo/bar truncated to 4 gives /foo and then encodes to %2Ffoo, six output characters from a prefix of four. It is also the one modifier with a hard error attached: a prefix on a list or a map is not "truncate each member", it is illegal, and an expander that quietly does something anyway is hiding a bug in your template.

Literals are copied — almost

STEP 11 · THE PART EVERYONE SKIPS

The text between expressions is not purely passed through. A literal may contain unreserved characters, reserved characters, percent-encoded triplets and non-ASCII characters, and those are copied verbatim. A space, a <, a >, a quote, a backslash, a caret or a backtick cannot appear in a URI, so the expander percent-encodes them. This is small and it is still worth getting right: it is the difference between a template a human can read in a config file and a URI a client library will accept. Note that a bare % that is not followed by two hex digits is itself encoded to %25.

An unmatched { or } is a syntax error, not a literal brace. There is no escape for them — a URI template cannot contain a literal brace, because braces are not legal URI characters anyway.
