📷 EXIF Viewer — a real, from-scratch image-metadata reader: drop or pick a JPEG (real FileReader.readAsArrayBuffer, never uploaded) and a hand-written parser walks the file byte by byte — find the APP1 marker (0xFFE1), the "Exif\0\0" header, the TIFF header (byte order II/MM + 0x002A + IFD offset), then walks IFD0, the EXIF sub-IFD and the GPS IFD, decoding each 12-byte entry with correct type handling (BYTE / ASCII / SHORT / LONG / RATIONAL) and endianness · reads Make, Model, Lens, DateTimeOriginal, ExposureTime, FNumber, ISO, FocalLength, Orientation and dimensions, converts GPS rationals (deg/min/sec) to decimal latitude & longitude, shows a live thumbnail, and has a graceful "no EXIF found" path (PNGs and screenshots usually carry none) · everything client-side, no library

Every photo carries a hidden diary. Here is how to read it.

When your camera or phone saves a JPEG it staples on a block of EXIF metadata: the camera make and model, the lens, the exact moment the shutter fired, the aperture, shutter speed, ISO, focal length, orientation — and, if location was on, the GPS coordinates. That block is not magic; it is a tiny, self-describing TIFF structure tucked inside the JPEG's APP1 segment. This tool parses it from scratch: it reads the raw bytes with FileReader.readAsArrayBuffer (nothing ever leaves your browser), finds the 0xFFE1 marker and the "Exif\0\0" header, reads the TIFF byte-order flag (II little-endian or MM big-endian), then walks each Image File Directory — a list of 12-byte entries — decoding every value by its type and endianness. No exif-js, no dependency. Drop one of your own photos, or load the built-in synthetic sample.

Five things worth knowing about EXIF

1. GPS in a photo is a real privacy leak. A JPEG straight off a phone can pin the exact spot it was taken to within a few metres. That is why sharing platforms usually strip EXIF on upload — and why this tool never sends your file anywhere. 2. PNGs (almost) never carry EXIF. The classic EXIF block lives in a JPEG/TIFF APP1 segment; PNG has its own text chunks and rarely stores camera data, so a "no EXIF found" result on a PNG is normal, not a bug. 3. Endianness is not optional. The TIFF header's first two bytes — II or MM — decide whether every multi-byte number in the block is little- or big-endian. Read one integer with the wrong order and every offset points into garbage. 4. The value field is only four bytes. Each entry has a 4-byte slot; if the value fits (a SHORT, one LONG) it sits inline, otherwise those four bytes are an offset to where the real data lives — the single trickiest rule in the format. 5. Rationals, not floats. EXIF stores exposure, aperture and GPS as pairs of integers (numerator / denominator). ExposureTime is literally 1/250; a GPS coordinate is three rationals — degrees, minutes, seconds — which you fold into a single decimal.

🔨 Build it yourself

    
An EXIF reader is a small, exact byte-walk over two nested formats: a JPEG is a chain of markers, and hidden inside one of them (APP1) is a whole TIFF file of metadata. The only tools you need are a DataView over the file's ArrayBuffer and a firm grip on two rules — endianness (read every number in the byte order the header declares) and the inline-vs-offset value field. Get those right and the rest is a loop over 12-byte entries. Here it is, step by step.

    
    
      
  1. 
        
    1
    Read the file as raw bytes — no upload
    
        
    FileReader.readAsArrayBuffer hands you the file's exact bytes in memory, entirely in the browser. Wrap them in a DataView, which lets you read integers of any width at any offset and — crucially — pick the byte order per read.
    
        
    function readFile(file){
  const reader = new FileReader();               // local only, never uploaded
  reader.onload = () => {
    const view = new DataView(reader.result);    // reader.result is an ArrayBuffer
    const exif = parseExif(view);                // walk the bytes
    render(exif);
  };
  reader.readAsArrayBuffer(file);                // give me the raw bytes
}
    
      
    2. 
      
  2. 
        
    2
    A JPEG is a chain of markers
    
        
    Every JPEG starts with 0xFFD8 (Start Of Image). After it come segments, each introduced by 0xFF + a marker byte, then a 2-byte big-endian length. Walk them until you hit APP1 (0xFFE1) or the start of scan (0xFFDA), skipping each segment by its length. Marker lengths are always big-endian, regardless of the EXIF byte order inside.
    
        
    if (view.getUint16(0) !== 0xFFD8) return null;   // not a JPEG
let off = 2;
while (off + 4 <= view.byteLength){
  const marker = view.getUint16(off);            // e.g. 0xFFE1
  if ((marker & 0xFF00) !== 0xFF00) break;        // lost sync
  if (marker === 0xFFDA) break;                   // start of scan, no more metadata
  const size = view.getUint16(off + 2);           // segment length (big-endian)
  if (marker === 0xFFE1) { /* APP1 — check for Exif */ }
  off += 2 + size;                                // jump to next marker
}
    
      
    3. 
      
  3. 
        
    3
    Confirm "Exif\0\0", then find the TIFF header
    
        
    An APP1 segment can hold other things (XMP), so verify the six identifier bytes 45 78 69 66 00 00 = "Exif\0\0". Right after them the TIFF block begins — and everything from here is measured as an offset relative to the start of that TIFF header, not the file.
    
        
    // at the APP1 marker `off`: [FF E1][len][ "Exif\0\0" ][ TIFF ... ]
if (view.getUint32(off + 4) === 0x45786966 &&    // "Exif"
    view.getUint16(off + 8) === 0x0000){          // \0\0
  const tiff = off + 10;                          // TIFF header starts here
}
    
      
    4. 
      
  4. 
        
    4
    The TIFF header sets the byte order
    
        
    Two bytes decide everything: 0x4949 = "II" (Intel, little-endian) or 0x4D4D = "MM" (Motorola, big-endian). A sanity check follows — the number 42 (0x002A) read in that order — then a 4-byte offset to the first directory, IFD0.
    
        
    const bo = view.getUint16(tiff);
const little = bo === 0x4949 ? true              // "II" little-endian
             : bo === 0x4D4D ? false             // "MM" big-endian
             : null;
if (little === null) throw new Error("bad TIFF byte order");
if (view.getUint16(tiff + 2, little) !== 0x002A) throw new Error("bad magic 42");
const ifd0 = view.getUint32(tiff + 4, little);   // offset to IFD0, from `tiff`
    
      
    5. 
      
  5. 
        
    5
    An IFD is a list of 12-byte entries
    
        
    A directory starts with a 2-byte count, then that many 12-byte entries, then a 4-byte pointer to the next IFD. Each entry is: 2-byte tag, 2-byte type, 4-byte count, and a 4-byte value-or-offset. Every one of those numbers respects the II/MM order.
    
        
    function readIFD(view, little, tiff, ifdOff){
  const out = {};
  const n = view.getUint16(ifdOff, little);       // entry count
  for (let i = 0; i < n; i++){
    const e = ifdOff + 2 + i * 12;                // this entry
    const tag   = view.getUint16(e, little);
    const type  = view.getUint16(e + 2, little);
    const count = view.getUint32(e + 4, little);
    out[tag] = { type, count, value: readValue(view, little, tiff, e) };
  }
  return out;                                     // next-IFD ptr is at ifdOff+2+n*12
}
    
      
    6. 
      
  6. 
        
    6
    Types, sizes, and inline-vs-offset
    
        
    Each type has a byte width: BYTE/ASCII/UNDEFINED = 1, SHORT = 2, LONG = 4, RATIONAL = 8. Multiply by the count. If the total fits in four bytes or fewer, the value lives right there in the entry's value field; otherwise those four bytes are an offset (from the TIFF start) to where the data actually is.
    
        
    const SIZE = { 1:1, 2:1, 3:2, 4:4, 5:8, 7:1, 9:4, 10:8 };  // bytes per element
function dataOffset(view, little, tiff, e, type, count){
  const bytes = (SIZE[type] || 1) * count;
  return bytes <= 4
    ? e + 8                                        // fits inline in the value field
    : tiff + view.getUint32(e + 8, little);        // else it's an offset from `tiff`
}
    
      
    7. 
      
  7. 
        
    7
    Decode a value by its type
    
        
    Now read count elements at that offset, each in the declared byte order. ASCII becomes a NUL-terminated string; SHORT/LONG become numbers; a RATIONAL is two LONGs — numerator then denominator — which we keep as a pair so we can show 1/250 and also divide it out.
    
        
    function readValue(view, little, tiff, e){
  const type = view.getUint16(e + 2, little), count = view.getUint32(e + 4, little);
  let p = dataOffset(view, little, tiff, e, type, count);
  if (type === 2){                                 // ASCII
    let s = "";
    for (let i = 0; i < count; i++){ const c = view.getUint8(p + i); if (!c) break; s += String.fromCharCode(c); }
    return s.trim();
  }
  const out = [];
  for (let i = 0; i < count; i++){
    if (type === 3){ out.push(view.getUint16(p, little)); p += 2; }        // SHORT
    else if (type === 4){ out.push(view.getUint32(p, little)); p += 4; }   // LONG
    else if (type === 5){ out.push([view.getUint32(p, little), view.getUint32(p + 4, little)]); p += 8; } // RATIONAL
    else if (type === 10){ out.push([view.getInt32(p, little), view.getInt32(p + 4, little)]); p += 8; }  // SRATIONAL
    else { out.push(view.getUint8(p)); p += 1; }                           // BYTE / UNDEFINED
  }
  return out.length === 1 ? out[0] : out;
}
    
      
    8. 
      
  8. 
        
    8
    Follow the sub-IFD pointers
    
        
    IFD0 holds the basics (Make, Model, Orientation, DateTime), but the juicy camera settings live in a separate EXIF sub-IFD pointed to by tag 0x8769, and location lives in the GPS IFD at tag 0x8825. Both are just offsets — read them with the very same readIFD.
    
        
    const ifd0 = readIFD(view, little, tiff, tiff + ifd0Off);
const exif = ifd0[0x8769] ? readIFD(view, little, tiff, tiff + ifd0[0x8769].value) : {};
const gps  = ifd0[0x8825] ? readIFD(view, little, tiff, tiff + ifd0[0x8825].value) : {};
//  0x010F Make · 0x0110 Model · 0x0112 Orientation   (IFD0)
//  0x829A ExposureTime · 0x829D FNumber · 0x8827 ISO · 0x920A FocalLength · 0xA434 LensModel (EXIF)
    
      
    9. 
      
  9. 
        
    9
    Make rationals human, GPS decimal
    
        
    ExposureTime [1,250] reads best as 1/250 s; FNumber [28,10] is f/2.8. GPS is three rationals — degrees, minutes, seconds — folded into one decimal, then negated for the S/W hemispheres so a single number drops onto a map.
    
        
    const rat = r => r[1] ? r[0] / r[1] : 0;           // [num,den] -> number
function exposure(r){ const v = rat(r); return v < 1 ? "1/" + Math.round(1 / v) + " s" : v + " s"; }
function gpsDecimal(dms, ref){                     // [[d,d'],[m,m'],[s,s']] + "N/S/E/W"
  let deg = rat(dms[0]) + rat(dms[1]) / 60 + rat(dms[2]) / 3600;
  if (ref === "S" || ref === "W") deg = -deg;      // southern / western hemisphere
  return deg;
}

    The "no EXIF" path — and a self-test
    
        
    Plenty of files have no EXIF: PNGs, screenshots, anything a chat app re-encoded. Every stage returns cleanly so the UI can say "no EXIF found" instead of throwing. To prove the walker itself, assemble a tiny TIFF in both byte orders and confirm the same rational round-trips.
    
        
    if (view.getUint16(0) !== 0xFFD8) return { ok:false, reason:"not a JPEG (PNGs rarely carry EXIF)" };
if (app1 < 0)                     return { ok:false, reason:"no APP1 Exif segment" };

// self-check: a RATIONAL f/2.8 must decode the same little- AND big-endian
console.assert(Math.abs(rat([28,10]) - 2.8) < 1e-9, "rational num/den");        // ✓
console.assert(gpsDecimal([[51,1],[30,1],[0,1]], "N").toFixed(2) === "51.50", "DMS->decimal"); // ✓
console.assert(gpsDecimal([[0,1],[7,1],[3960,100]], "W") < 0, "western hemisphere is negative"); // ✓
