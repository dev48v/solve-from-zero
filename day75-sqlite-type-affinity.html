🗄️ A real SQLite type-affinity engine, a real record codec, and a writer that emits a database file the actual library will open. Everyone knows a SQLite column’s declared type is “only a hint”. Almost nobody knows what the hint does. CREATE TABLE p(x FLOATING POINT) is an INTEGER column, because rule 1 finds the INT inside POINT before rule 4 ever looks at FLOA — what decides is the position in the rule list, not the position in the name. Over 1,226 type names checked against the library itself, the model everyone actually carries — the first marker in the name wins — is wrong 343 times (27.98%), and 26 of 66 type names that really occur in ported DDL get an affinity that contradicts what the name means: STRING and VARBINARY and UUID and JSON are all NUMERIC columns that will happily turn '42' into the integer 42. 🔴 The finding is what the affinity then does to the bytes. A REAL column and a NUMERIC column store the double 2.0 as the same three record bytes, 02 01 02 — the whole cell, with its length and rowid varints in front, is 03 01 02 01 02 — and read them back as 2.0 and 2 — different type, different value, one schema string apart. Over 121 integral doubles the records are byte-identical 121 times out of 121 and the type diverges 121 times out of 121. A SQLite record is not self-describing: serial type 1 says “one-byte integer” and a schema-driven OP_RealAffinity overrules it on the way out, which is also why the same 121 values cost 361 bytes in the REAL column and 1,210 in the BLOB one — the “loose” column is the compressed one. Every verdict here is differential against two independent builds of the real library, SQLite 3.45.1 (Python 3.11) and SQLite 3.50.0 (node:sqlite), in both directions: 1,012 rows the library wrote and this engine read, and 900 rows this engine wrote that both libraries read back with PRAGMA integrity_check clean. What the references said

Two independent builds of the real SQLite C library ship on the machine this was written on, and both were used, in both directions. Nothing on this page was checked against my own expectations.

🔴 Five claims of mine did not survive the differential.

  1. CAST(text AS INTEGER) is a different parse from CAST(text AS NUMERIC). I had INTEGER truncating the float parse, so CAST('3.0e2' AS INTEGER) came out 300. The library says 3: the INTEGER cast reads only the leading integer prefix and stops at the dot. Storage does not work that way — the same string in a NUMERIC column really is 300 — so the correction is that CAST and INSERT do not share a parser.
  2. CAST(1e300 AS INTEGER) saturates, and the clamp has to be done in integer arithmetic. Mine clamped in double space and produced 9223372036854775808 — one past int64 max, a value that cannot exist.
  3. SQLite has no negative zero. The literal, a bound parameter and a stored value all come back +0.0, in both builds. This engine keeps the IEEE sign bit, so that is a real divergence: measured, reported here, not quietly patched away to make a number look better.
  4. My own affinity resolver had a hard-coded NUMERIC fallback instead of reading the last rule out of the rule table. Every test passed. It was only caught when the verifier deliberately changed the default affinity and the engine did not move.
  5. An Array already has a .values — the iterator — so row.values || row silently took the function, and the file writer emitted records with zero columns. The real library opened those files perfectly happily and reported empty rows.

And one that was the harness, not either side: the reference speaks inf and JavaScript’s parseFloat only reads Infinity, so '1e400' — which really does become a REAL infinity in a NUMERIC column — arrived as a NaN and looked like an engine bug for about ten minutes.

A declared type is a string, and the string is searched for substrings

Every other SQL engine you have used checks the value against the column type and rejects what does not fit. SQLite does something else entirely, and the difference is not “it is more relaxed”. It is that the declared type is not consulted at all when a value arrives. What is consulted is one of five affinities, and the affinity is derived from the declared type by case-insensitive substring search, in a fixed order, once, at CREATE TABLE time. Nothing validates. Nothing warns. Any word at all is a legal type name.

1 · The five rules are matched by rule number, not by position

Rule 1: if the name contains INT, INTEGER. Rule 2: else if it contains CHAR, CLOB or TEXT, TEXT. Rule 3: else if it contains BLOB, or there is no declared type at all, BLOB. Rule 4: else if it contains REAL, FLOA or DOUB, REAL. Rule 5: otherwise NUMERIC.

Read that list again with FLOATING POINT in mind. It contains FLOA, which is rule 4. It also contains INT — inside the word POINT, at character 12 — which is rule 1. Rule 1 is checked first, so the column is an INTEGER column. The marker that wins is the one belonging to the lowest-numbered rule, no matter where in the string it sits, and that is exactly the thing a reader’s eye does not do. Over 1,226 generated and real type names, reading left-to-right instead gives the wrong answer 27.98% of the time.

The implementation is not five passes. It is one left-to-right scan with a four-character rolling window that breaks out of the loop the instant it sees INT — which is the same thing, and this page carries both models and checks them against each other on every name it is given.

2 · NUMERIC is the default, so a typo changes the semantics

Rule 5 is not an error case. It is where every unrecognised name lands, and it is a converting affinity: text that looks like a number becomes a number. So VARCHR(255), a one-character typo, is not a text column that happens to be misspelled — it is a numeric column, and '007' stored in it comes back as 7. STRING is the same trap without the typo: S-T-R-I-N-G contains no CHAR, no CLOB, no TEXT, so it is NUMERIC. VARCHAR and STRING, two names for the same intention, behave in opposite ways.

BINARY and VARBINARY land there too, so the standard SQL name for a byte string does the opposite of BLOB. So do UUID, JSON, INET, ENUM, GEOMETRY and BYTEA. Of the 66 scored real-world names on the RESOLVE tab, 26 get an affinity that contradicts what the name means where it came from.

3 · Affinity is a conversion, and the conversion is conditional

TEXT affinity renders numbers as text. REAL affinity turns integers into doubles. INTEGER and NUMERIC affinity try to turn text into a number — but only if the whole string is a well-formed numeric literal, and only if the conversion is “lossless and reversible”. BLOB affinity converts nothing at all. NULL is never converted by anything, and a BLOB is never converted by anything either: it is the one storage class that walks through every affinity untouched.

The parse has edges that are worth knowing because they are not the edges of your language’s parser. Leading and trailing ASCII whitespace is tolerated, interior whitespace is not, so '  7  ' is 7 and '5 5' is text. A no-break space is not whitespace. '0x1A' stays text, because the hex form is a literal syntax, not a string conversion. '.5' and '5.' both parse. '1e' does not. 'inf' and 'NaN' do not — but '1e400' does, and becomes a REAL infinity.

4 · “Lossless” means fifteen significant digits

The rule reads as a promise that nothing can be damaged. It is defined over the first fifteen significant decimal digits, and a decimal string can carry more than that. '1.0000000000000001' into a NUMERIC column is stored as the integer 1: the parse produces a double, the double is 1.0 exactly, the double folds back to an integer, and the fraction is gone. '1.000000000000001' — one digit shorter — survives as a REAL. Over 60 generated decimals, 16 silently become a different number.

A string too long for int64 is a different case with a different outcome: '12345678901234567890' becomes a REAL, because the integer parse overflows and the double parse does not.

5 · INTEGER and NUMERIC affinity are the same thing at INSERT

Two of the five affinities cannot be told apart by anything you can store. Every value that goes into an INTEGER column goes identically into a NUMERIC one. The documented difference — that INTEGER also folds an integral REAL down to an integer — turns out to be what NUMERIC does as well. The place they part company is CAST: CAST('3.5' AS INTEGER) is 3 and CAST('3.5' AS NUMERIC) is 3.5. Over 255 CAST cells they differ on 17.

6 · The record: varints, serial types, and two values that cost nothing

A row on disk is a header followed by a payload. The header is a varint giving its own total length, then one varint serial type per column. 0 is NULL. 1 to 6 are integers of 1, 2, 3, 4, 6 and 8 bytes. 7 is an IEEE double. 8 and 9 are the integers 0 and 1 and occupy no payload bytes at all — the value is in the type code. Anything 12 or above is a blob if even and text if odd, with the length recovered as (N−12)/2 or (N−13)/2.

SQLite’s varint is big-endian, seven bits per byte, most significant first, up to nine bytes — and the ninth byte contributes all eight of its bits, not seven. That is why 8×7+8 = 64 exactly. A decoder that masks the ninth byte like the others is correct on every positive number that fits in eight bytes and wrong on every negative one, because in two’s complement every negative int64 sets the top bit and needs the full nine.

7 · The headline: a record is not self-describing

Put the double 2.0 in a REAL column. SQLite does not write eight bytes of IEEE. It writes serial type 1 and a single byte 02, because it knows the column has REAL affinity and it can afford to store the value as an integer and put the type back on the way out. The generated bytecode for reading a REAL-affinity column is OP_Column followed by OP_RealAffinity, and that second opcode exists for exactly this.

Now put the same 2.0 in a NUMERIC column. Identical bytes — 03 01 02 01 02 for the whole cell payload — and it reads back as the integer 2. The record is 02 01 02 either way, and the cell around it is 03 01 02 01 02. The bytes do not know. Over 121 integral doubles the two columns agree byte-for-byte 121 times and disagree on typeof() 121 times.

Two consequences. The first is that any tool which parses a SQLite file without also parsing its schema — and a great many forensic and recovery tools do exactly that, because the record format is self-contained and the schema is just more rows — reports the wrong type for every whole-numbered value in every REAL column. Not a corrupted file. Not an ambiguous one. A file where the answer genuinely is not in the bytes. The second is a size inversion: 121 doubles cost 361 bytes in the REAL column and 1,210 in the BLOB column, because BLOB affinity has no permission to re-type anything and must write the full eight-byte float every time. The column with the strictest-sounding name is the compressed one.

8 · Comparison applies affinity too, so a query changes answer

A column reference in a comparison carries its column’s affinity; a bare literal carries none. If one side is numeric-ish and the other has none, NUMERIC affinity is applied to the other side. If one side is TEXT and the other has none, TEXT affinity is applied. Otherwise nothing happens.

So a column holding the text '5' answers WHERE x = 5 with a row under INTEGER, TEXT, REAL and NUMERIC affinity, and with nothing at all under BLOB affinity — the one case where neither side has an affinity to lend. Over 30 (stored value, literal) pairs, 12 give different answers depending only on the declared type. No error, no warning, and an index does not save you because the index is built with the same rules.

9 · Sorting compares the storage class before the value

The order is NULL, then INTEGER and REAL together compared numerically, then TEXT, then BLOB. Not one of those is a tie-break: the class is compared first and the value only inside a class. So in a column with no affinity, '2' sorts after 10, and x'00' sorts after every string. Integers and doubles are compared exactly rather than by casting the integer to a double, which is why 9223372036854775807 does not compare equal to 9.223372036854776e18.

10 · The escape hatch, and why it is opt-in

Since 3.37 a table can be declared STRICT. Then the type must be one of exactly five names, and a value that does not fit is an error rather than a conversion. It is opt-in and it will stay that way: SQLite’s compatibility promise means every existing file has to keep behaving exactly as it does. Affinity is not a legacy wart on its way out. It is the default, and it is the thing your ORM is generating DDL against right now.

What to do about it on Monday

None of this is a bug and none of it is going to change. The useful response is to know which of your columns are not the type you think, and to stop writing the two queries that the affinity rules answer differently.

1 · Ask your own database, in one query

There is no affinity column in pragma_table_info — it reports the declared type, which is the thing that misled you in the first place. But CAST uses the same resolver, and two cells separate all five affinities uniquely.

SELECT m.name AS "table", i.name AS column, i.type AS declared,
       CASE typeof(CAST('3.5' AS INTEGER)) WHEN '' THEN '' END  -- placeholder, see below
  FROM sqlite_schema m, pragma_table_info(m.name) i
 WHERE m.type = 'table';

The CAST target cannot be parameterised, so run the listing first and then, for each distinct declared type T, one probe:

SELECT typeof(CAST('3.5' AS T)), typeof(CAST(5 AS T));

  integer, integer  -> INTEGER      real, real     -> REAL
  text,    text     -> TEXT         real, integer  -> NUMERIC
  blob,    blob     -> BLOB

A few names are reserved words in the type position (SET is one) and the grammar refuses the probe outright. Those are not affinity questions; they are names you cannot write there at all.

2 · The three-second smell test on any schema

  • Any name with INT hiding inside it: POINT, MULTIPOINT, INTERVAL, FLOATING POINT, CONSTRAINT-ish names generated by a tool. All INTEGER.
  • Any name meant to be text that contains none of CHAR, CLOB, TEXT: STRING, UUID, JSON, ENUM, INET, XML. All NUMERIC.
  • Any name meant to be bytes that is not spelled BLOB: BINARY, VARBINARY, BYTEA, IMAGE, JSONB. All NUMERIC.
  • Anything you typed by hand and did not test. A misspelling is not an error.

3 · Stop writing the query that changes answer

Bind the value with the type you actually mean, rather than relying on the comparison to convert for you. WHERE id = ? with a string argument is fine on an INTEGER column and silently empty on a BLOB-affinity one. If a column can hold more than one storage class — and any column with BLOB or NUMERIC affinity can — then either normalise on the way in or compare against CAST(? AS <type>) so the conversion is written down.

A quick census of what a column really contains:

SELECT typeof(x), count(*) FROM t GROUP BY 1;

If that returns more than one row on a column you believed was one type, the affinity has been converting for you and something upstream has been inconsistent about what it binds.

4 · Use STRICT for new tables, and know what it costs

CREATE TABLE t(
  id     INTEGER PRIMARY KEY,
  name   TEXT NOT NULL,
  price  REAL,
  blobby BLOB,
  other  ANY          -- the fifth name: keeps the old behaviour, on purpose
) STRICT;

Only INT, INTEGER, REAL, TEXT, BLOB and ANY are legal. Everything else is a CREATE TABLE error, which is the point. Note what STRICT does not do: it does not make a REAL column store an eight-byte float, and it does not stop ANY columns from holding all five classes at once.

5 · If you write a tool that reads the file, read the schema first

The record format is self-contained and that is exactly the trap. Parse page 1, decode the sqlite_schema rows, take the sql column, recover each column’s declared type, resolve it to an affinity, and only then decode the data pages. Otherwise every whole-numbered value in every REAL column is reported as an integer, and no part of the file will tell you.

The rest of the layout is stable and small: page size at offset 16 (with 1 meaning 65536), reserved bytes per page at 20, text encoding at 56, and the size in pages at 28 — which is only trustworthy when the change counter at 24 equals the version-valid-for at 92, otherwise fall back to the file length. Table b-tree pages are 0x0D for leaves and 0x05 for interiors; on page 1 the cell pointers are still counted from byte 0 even though the page header starts at 100. A payload longer than usable − 35 spills onto overflow pages, and how much stays local is a formula, not a constant.

6 · How this page was checked

Two independent builds of the real library, used in both directions. Forward: 1,226 type names resolved through CAST in SQLite 3.45.1 (Python 3.11) and SQLite 3.50.0 (node:sqlite) — and the CAST shortcut itself proved against real column storage before it was trusted, because a discriminator you have not checked is not a reference. Then 5 affinities × 54 literals of storage, 255 CAST cells, 150 comparison cells, and 4 real database files the library wrote whose 1,012 rows this engine recovered and re-encoded byte-identically.

Reverse: 900 rows written by this engine across three page sizes, every one of them opened by both libraries with PRAGMA integrity_check clean, three of three needing a real interior b-tree page above the leaves. That is the direction that catches an off-by-one in the header, the page layout or the cell format, because the library refuses rather than guessing.

The lineage is the same one as Day 61 (git check-ignore), Day 72 (OpenSSL and Node), Day 73 (GNU tar and Python tarfile) and Day 74 (zlib and gzip): build the engine from the specification, then let something that is not the engine decide whether it is right. Every subprocess runs from an empty directory, which is a Day 72 scar — a MinGW binary globbed its own argv and turned a hostname into a file listing.

7 · Read the source

The engine between ENGINE:BEGIN and ENGINE:END in this file touches no DOM, reads no clock and has no random source, which is what lets the verifier load it straight out of the HTML and run it against the reference. It is the affinity resolver, the numeric-literal parser, the storage-class conversions, the CAST rules, the comparison and ordering rules, the varint, the serial types, the record encoder and decoder, the b-tree page writer and the file reader — and nothing else. If a number on this page is wrong, it is wrong in there.
