SOLVEFROMZERO · DAY 74

🌀 A real DEFLATE decoder — and a real DEFLATE encoder to feed it, because a page that shipped a blob would be proving nothing. Everyone knows that gzip stores repeated data as “go back d bytes and copy n”. Almost nobody knows that the copy is normally not a copy: RFC 1951 lets the distance be smaller than the length, so the match reads bytes that have not been written yet and the decoder must produce them as it goes. That is not an exotic corner — in a 120-file corpus 5.21% of all 44,553 matches overlap, and 92 of 120 files contain at least one. 🔴 The finding is what happens next. The two obvious wrong implementations fail on exactly the same condition and produce completely different symptoms: slice-then-append returns a shorter file, which every test catches, while memcpy from the window returns a file of the right length with invented bytes — and the bytes it invents are zeros, so it is silently correct on 24 of those 92 files. Every one of those 24 is a zero-filled or sparse input: a run of zeros is 100% overlapping matches and catches the second bug 0 times out of 12, which is to say the canonical “does my decompressor handle run-length data” fixture is the one input that cannot detect it. Meanwhile JSON and log lines overlap on 0.05% and 0.11% of their matches and random bytes on 0.00%. 🔴 Second finding, same shape: the two Huffman trees in a dynamic block are not two trees. Section 3.2.7 describes ONE sequence of HLIT + HDIST code lengths, so a run-length code can begin among the literal lengths and finish among the distance lengths. This page builds such a stream bit by bit and zlib 1.3.0, zlib 1.3.1 under Python 3.11 and GNU gzip 1.13 all decode it — while 0 of 2,400 streams from real zlib, at five levels and four strategies, ever contain one, because zlib's encoder run-length-codes the two halves separately — while this page's own encoder, following the RFC's sentence rather than zlib, crosses on about 1 stream in 120. Also here: length 258 has two legal spellings and no compressor emits the second; an incomplete Huffman code is an error except for exactly one distance code of exactly one bit, checked at fifteen bit-lengths against all three references; the 32 KiB window walks straight through block boundaries, including into a stored block; and the fixed distance code is complete only because of two codes the specification says can never occur. Every verdict here is differential against zlib 1.3.0 (Node 22), zlib 1.3.1 (Python 3.11) and GNU gzip 1.13, in both directions. Pure vanilla JavaScript, one file, no build step.

DEFLATE, from zero

DEFLATE is the compression inside gzip, zip, PNG, HTTP Content-Encoding, git packfiles and almost every jar on your disk. It is specified in RFC 1951, which is fifteen pages long and thirty years old, and it is one of the few formats a person can genuinely implement in an afternoon. That is what makes it worth doing: the whole thing fits in your head, and the places where it does not behave the way your head says are therefore very sharp.

1 · Two ideas, stacked

DEFLATE is LZ77 followed by Huffman coding. LZ77 replaces repeated text with a back-reference: instead of writing the quick brown again, write “go back 240 bytes and take 15”. Huffman then gives the common symbols short bit patterns and the rare ones long ones. Neither idea is DEFLATE's; the format is the packing of the two, and every surprise in it lives in the packing.

2 · The stream is bits, and the bits go two ways

Section 3.1.1 says data elements are packed starting with the least significant bit, and Huffman codes are packed starting with the most significant bit of the code. Both sentences are true at once. A 5-bit HLIT field and a 5-bit Huffman code sit in the same byte and are read in opposite directions. This is the single most common reason a from-scratch inflater produces garbage on its first run, and it is why this engine has both a bits() and a code() writer that disagree on 240 of the 256 possible bytes.

3 · Three kinds of block, and BFINAL

A stream is a chain of blocks. Each starts with one bit — is this the last block? — and two bits of type. Type 00 is stored: byte-align, read a 16-bit length and its one's complement, then copy that many raw bytes. Type 01 uses the fixed Huffman codes printed in the RFC. Type 10 carries its own codes. There is no length field for a compressed block: it ends when the end-of-block symbol 256 is decoded. And the blocks are not independent, which is finding number four below.

4 · The length and distance alphabets

A literal is a symbol 0–255. Symbol 256 ends the block. Symbols 257–285 are lengths, each carrying 0–5 extra bits, and they cover 3 through 258. A length is always followed by a distance symbol, 0–29, carrying up to 13 extra bits, covering 1 through 32768. The tables look like a clean geometric ladder and they are, right up to the last rung: code 284 spans 227–258 with five extra bits, and code 285 also means 258 with none. Two spellings, one length. Every compressor uses the short one and the long one is still legal — the DECODE tab builds both.

5 · The copy that reads its own output

This is the one that matters. Nothing says the distance must be at least the length. <length 258, distance 1> is the legal, ordinary, extremely common way to say “259 identical bytes”, and to decode it you must emit one byte at a time and let the source pointer chase the destination. A byte-at-a-time loop gets this right by accident. Anything that materialises the source region first — a slice, an append, a memcpy — gets it wrong, and the two wrongnesses look nothing alike.

Slicing gives you a short file: your output is missing len − dist bytes and every later distance is now measured from the wrong place, so it usually blows up loudly a few kilobytes later. memcpy gives you a file of exactly the right length whose bytes past the overlap point are whatever the destination buffer held — zeros, in a freshly allocated one. On a zero-filled input those zeros are the correct answer, which is how this bug survives the test everyone writes for it.

6 · A dynamic block describes its own trees, badly on purpose

A type-10 block starts with HLIT, HDIST and HCLEN, then the bit lengths of a third Huffman code — the code-length code — in a scrambled order (16, 17, 18, 0, 8, 7, 9, 6, …) chosen so that the rarely-used lengths sit at the end and HCLEN can truncate them. That third code is then used to read HLIT + HDIST code lengths, with 16 meaning “repeat the previous length 3–6 times”, 17 meaning “3–10 zeros” and 18 meaning “11–138 zeros”. Three levels of indirection before a single byte of your data appears.

7 · And that sequence is one sequence

HLIT + HDIST lengths, read as a single array. The boundary between the literal lengths and the distance lengths is positional; the run-length codes know nothing about it. So a run of six can start at index 256 and finish at index 261, defining the end-of-block length and all four distance lengths at once. Real inflaters handle this because they, too, read one array. Real compressors never produce it, because zlib's send_tree() is called once per half. The consequence is a decoder bug that no amount of testing against real files will ever expose.

8 · Canonical codes, and the two ways they break

Only the lengths are transmitted; the codes themselves are reconstructed by a rule (section 3.2.2) that both sides run identically. Whether a set of lengths is usable is decided by the Kraft sum ∑2−len. Exactly 1 and you have a prefix code. Above 1 and it is over-subscribed: two symbols would share a code, and every inflater refuses. Below 1 and it is incomplete: some bit patterns decode to nothing. Incomplete is also refused — with exactly one exception, next.

9 · The one incomplete code that is allowed

A block whose data contains a single distance value only needs one distance code. One code of one bit is incomplete — it fills half the code space — and inflate_table() tolerates it anyway, because refusing it would reject streams that compressors legitimately produce. The tolerance is exactly “one code, and it is one bit long”: a single two-bit distance code is rejected by zlib, by Python and by GNU gzip alike. The DECODE tab builds all fifteen bit-lengths and the verifier races every one of them against all three.

And the check happens when the tree is read, not when it is used. The stream this page builds declares the distance code and then never emits a single match — and all three references still refuse it at two bits.

10 · The window is the stream, not the block

32 KiB of history, and it does not reset. A match in block 7 may reach back into block 3. It may reach back into a stored block, where the bytes were never Huffman-coded at all. Decoding a block in isolation is not possible, which is why random access into a gzip file is a research topic rather than a function call. And a decoder that gets this wrong is fine on anything under about 16 KB and fails on everything above it.

11 · DEFLATE is not gzip and is not zlib

A raw DEFLATE stream has no header, no checksum and no length. RFC 1950 (zlib) wraps it in two bytes whose 16-bit value must be a multiple of 31, and appends an Adler-32 of the uncompressed data. RFC 1952 (gzip) wraps it in ten-plus bytes of header and appends a CRC-32 and the uncompressed size modulo 232 — which is why a gzip member cannot honestly describe a 4 GiB file. Feed one to a decoder expecting the other and it will not politely fail: it will start decoding the header as bits.

12 · Two codes that can never occur, and why they must exist

Section 3.2.6 gives the fixed distance code as codes 0–31 of five bits each, and adds that 30 and 31 “will never actually occur”. Build the tree with only the thirty meaningful codes and the Kraft sum is 30/32: incomplete, and an inflater following its own rules must reject its own fixed blocks. The two dead codes exist purely to make the arithmetic close. This engine failed exactly that way on its first run, and the assertion that catches it is still in the self-check.

13 · How this page was checked

In both directions, against three shipped implementations. Every stream this engine writes — stored, fixed, dynamic, and every adversarial construction on the DECODE tab — is decoded by zlib 1.3 through Node, by Python 3.11's zlib.decompressobj(-15) and by GNU gzip 1.13 through a pipe. Every stream those produce, at five levels and four strategies, is decoded here and compared byte for byte. Write it yourself

The engine between ENGINE:BEGIN and ENGINE:END in this file's source is about 900 lines and touches no DOM, no clock and no random number generator. Here is the order to build it in, and the traps in the order you will hit them.

The order that works

  1. The bit reader first, and test it alone. bits(n) reads LSB-first; reading a Huffman code is a different loop that shifts each new bit in at the bottom of the code. If you write one function for both you will lose a day.
  2. Canonical Huffman from lengths. Count the lengths, compute the first code of each length, hand codes out in symbol order. Twenty lines. Return the Kraft slack too — you need it in three places later.
  3. Stored blocks. Align, LEN, NLEN, copy. Now you can round-trip a file without compressing anything, which means your framing is right before your entropy coding exists.
  4. Fixed blocks. The code lengths are four constant ranges. Build the distance code over 32 symbols, not 30.
  5. The length/distance tables. Write them as data and then assert the recurrence: every base is the previous base plus the previous span, exactly once excepted. A transcription error here decodes fine for a week.
  6. Dynamic blocks. HLIT/HDIST/HCLEN, the scrambled code-length order, then the 16/17/18 run-length alphabet over one array of HLIT + HDIST lengths.
  7. The back-reference, one byte at a time. Resist every optimisation until the overlapping case passes.
  8. Then a compressor, so you have something to decode that you did not write by hand: a hash chain over three-byte keys, lazy matching, and Huffman lengths from the block's own symbol frequencies.

The traps, in the order they bite

  • The two bit orders. 240 of 256 byte values are written differently by the two writers; only the 16 bit-reversal fixed points agree.
  • The fixed distance code has 32 entries. Thirty five-bit codes fill 30/32 of the code space and your own completeness check will reject your own output.
  • Overlapping matches. out.extend(out[p:p+n]) in Python, append(out, out[p:p+n]...) in Go, out.concat(out.slice(p,p+n)) in JavaScript, memcpy in C: all four are wrong and only the C one keeps the length right, which makes it the worst of them.
  • A run-length code can cross the HLIT boundary. If you parse the two halves separately you will be correct against every file you can find and wrong on the specification.
  • Incomplete codes. Reject them — except one distance code of one bit. Validate at header time, not at first use.
  • The window spans blocks, including stored ones, and resets nowhere.
  • Truncation must be an error. A short read that returns the bytes decoded so far is how a corrupt archive becomes a corrupt file with no warning.
  • Block type 3 is reserved. It is also what you decode when your bit reader has drifted, so a clear message here saves an hour.
  • zlib's bl_count redistribution needs a floor guard. The classic length-limiting loop walks down from maxLen−1 looking for a length to borrow from; when every surviving leaf is already at maxLen it walks off the bottom of the array and silently produces an over-subscribed tree. This engine hit that on a corpus of 200 and now verifies the tree it just built before using it.

How to know you are right

  • Differentially, in both directions. Your streams into a real inflater; a real compressor's streams into yours. Either direction alone leaves half the format untested — a decoder that never sees a stored block cannot be wrong about one.
  • Sweep the levels and the strategies. zlib at level 0 emits stored blocks, at level 1 mostly fixed ones, with Z_RLE only distance-1 matches and with Z_HUFFMAN_ONLY no matches at all. Four very different streams from one library.
  • Then build the streams the compressor will not. The seam-crossing run, the second spelling of 258, the single one-bit distance code, the match that reaches into a stored block: none of them appear in any file on your disk, all of them are legal, and three separate references agree on every one.
  • Sanity-check the reference itself. A differential test can be wrong about the reference and not only about the engine: on Day 72 a MinGW openssl.exe globbed its own argv and turned a hostname of * into a list of filenames. Every subprocess in this day's verifier runs from an empty scratch directory and every reference prints its version.

Claims that did not survive being measured

  • 🔴 “The two naive copies are the same bug.” They fire on the same condition and they are not the same bug. The slice model is wrong on every file that contains an overlap; the memcpy model is wrong on 68 of those 92, and the 24 it survives are every zero-filled and every sparse file in the corpus. The page now leads with the gap rather than the condition.
  • 🔴 “No compressor ever crosses the HLIT seam.” True of zlib, false in general — this page's own encoder, which run-length-codes the joint array exactly as section 3.2.7 describes it, crosses on about 1 stream in 120. So the split-trees decoder is not defended by “nobody produces it”; it is defended by “nobody you have tested against produces it”.
  • 🔴 “Crossing the seam is an optimisation.” Measured: it saves 8 bits across 120 streams. It is not an optimisation anybody is defending, which is exactly why the incompatibility is worth knowing about — there is no pressure on either side to converge.
  • 🔴 “The fixed distance code has 30 codes.” It has 32, and the engine discovered this by refusing its own fixed blocks.
