SOLVEFROMZERO · DAY 76

🔤 A real UAX #15 normaliser — recursive canonical and compatibility decomposition, the canonical ordering algorithm, the derivation of Full_Composition_Exclusion, the blocked-composition rule and the Hangul arithmetic — written from the raw UCD fields rather than called out to a library. Everyone knows NFC composes and NFD decomposes, and that the two undo each other. Over the 2,061 characters that actually have a canonical decomposition, NFC(NFD(c)) === c holds for 941 and fails for 1,120 — 54.34%, more than half. U+0958 DEVANAGARI LETTER QA is one assigned character; the composed form turns it into two and will never put it back. And for 1,035 of the failures NFC does not merely decline — it hands back a different character: U+212B ANGSTROM SIGN normalises to U+00C5, the letter Å. 🔴 The finding is positional. a + ◌̂ + ◌̀ is one code point after NFC — U+1EA7, Vietnamese ầ. a + ◌̀ + ◌̂, the same three characters with the two accents swapped, is two — U+00E0 U+0302 — and no normalisation form will ever make them equal. Both marks carry combining class 230, and canonical ordering is a stable sort that refuses to reorder marks that share a class, because in that case their order is data. Swap that same acute past a cedilla (class 202) instead and nothing happens at all: over 3,600 different-class pairs the swap is erased 3,600 times, over 53,232 same-class pairs it survives 53,184 — and the zeroes are the tell. The shortcut everybody writes, compose every adjacent pair you can, is wrong on 9.88% of 40,000 marked strings; sort every run of marks by class is wrong on 20.01%; and two strings that are each already NFC concatenate into a string that is not, 8.93% of the time. Every verdict is differential against five independent implementations across four Unicode versions — ICU 77 (Node 22, Unicode 16.0), Python 3.13 (15.1), Java 21 (15.0), Perl 5.38 (15.0) and Python 3.11 (14.0). A normaliser is three passes, and two of them are not what they sound like

Unicode lets the same text be spelled more than one way on purpose. é is U+00E9 and it is also U+0065 U+0301, and both are correct. Normalisation is the function that picks one spelling so that comparison, hashing, sorting and indexing have something stable to work on. Four forms, two axes: NFD and NFC use only canonical mappings, which preserve meaning; NFKD and NFKC also use compatibility mappings, which do not. D means decomposed, C means composed. That is the entire folklore, and almost every mistake below survives it.

1 · Decomposition is recursive, and the table is only half the story

A decomposition mapping can point at a character that itself has a decomposition. U+1E14 (Ē with grave) maps to U+0112 U+0300, and U+0112 maps to U+0045 U+0304, so the real answer is three code points, not two. Every implementation either recurses or pre-flattens the table. The engine recurses, in decomposeCp, which is nine lines.

The 11,172 Hangul syllables carry no table entry at all. U+AC01 is U+1100 U+1161 U+11A8 by arithmetic: (cp − 0xAC00) divided by 588 gives the leading jamo, the remainder divided by 28 the vowel, the remainder after that the optional trailing consonant. Half a screen of algebra replaces a table with more entries than every other canonical decomposition in Unicode combined. The self-check walks all 11,172.

2 · Canonical ordering is a STABLE sort, and that is the whole rule

Every character has a canonical combining class: 0 for a starter, and a positive number for a mark, roughly “where it sits relative to the base” — 230 above, 220 below, 202 attached below, and so on. Two marks with different classes render in different places, so their order in the string is arbitrary and normalisation sorts it away. Two marks with the same class stack on top of each other, so their order is visible, and normalisation must not touch it.

That one distinction is the source of the finding at the top of this page. Because the sort is stable, a + ◌̂ + ◌̀ and a + ◌̀ + ◌̂ survive it unchanged, go into composition in different orders, and come out as one code point and two. They are not canonically equivalent under any form. Meanwhile a cedilla (202) and an acute (230) get sorted into a fixed order and the same swap is invisible. Same acute, same base, opposite consequence, decided by a number attached to the other mark.

Use a sort() that is not stable, or add a tie-break on code point to make the output “deterministic”, and you have written a different function. The scoreboard above measures that one: it is wrong on a fifth of all marked strings.

3 · Composition walks to the last starter, not to the previous character

The composition pass keeps a pointer to the last starter it emitted and tries to fold each following character into that, not into whatever is immediately to the left. The guard is the blocked rule: a character C is blocked from starter L if anything between them has a combining class greater than or equal to ccc(C).

So in a U+033A U+0353 U+0302 the two marks of class 220 are left where they are and the circumflex, which is third, reaches back over both of them and merges into the a: the result is U+00E2 U+033A U+0353. The mark that composed is not the mark that was adjacent. In the corpus above that happens 3,978 times in 40,000 strings, and it is exactly the case that a greedy pairwise composer gets wrong.

The subtle half: when a composition succeeds, the last class seen is deliberately not updated, because the character that carried it is gone. Update it and you have written a normaliser that passes almost every test anyone writes and disagrees with ICU on strings with three marks.

4 · Not every decomposition may be composed again

This is the one that breaks the mental model. A character is in Full_Composition_Exclusion — NFC will never re-create it — for one of three reasons:

  • It is on a list. CompositionExclusions.txt sections 1 and 2: Devanagari, Bengali, Gurmukhi, Oriya, Tibetan, Hebrew presentation forms, one maths symbol and the stemmed musical notes. Composing them back would erase a distinction the scripts need. 81 characters, frozen since Unicode 4.1.
  • Its decomposition is a single character — a singleton. There is no pair to compose, so NFC has nothing to do and simply keeps the decomposition. This is the big bucket: 1,035 characters, and it is why NFC can hand you a code point you never wrote.
  • Its decomposition starts with a non-starter. Four characters, including U+0344 COMBINING GREEK DIALYTIKA TONOS. Composition only ever attaches to a starter, so these can never come back either.

Only the first bucket is data. The engine derives the other two from the decomposition table in six lines — and the self-check asserts that the three buckets are disjoint and that together they account for exactly the characters that fail the round trip. That is an identity between two independent derivations, not a constant anybody typed in.

5 · So NFC is not “the composed one”

Feed NFC the single character U+0958 DEVANAGARI LETTER QA and it gives you back U+0915 U+093C — two code points, longer than what you handed it, from the form whose name means composed. Feed it U+212B ANGSTROM SIGN and it gives you U+00C5, a different character with a different name and a different purpose. Feed it U+2126 OHM SIGN and it gives you Greek capital omega.

The right mental model is not compose/decompose. It is: every canonically equivalent string has one designated spelling per form, and NFC’s designated spelling is not always the shortest one. Length is not the invariant. NFD(NFC(s)) === NFD(s) is — that one holds on every string, and the self-check asserts it rather than any particular output.

6 · Concatenation is where this reaches your logs

Normalisation is not a closure over concatenation. Take "a", already NFC. Take "◌́", a lone acute, also already NFC. Join them and you have U+0061 U+0301, which is not NFC. Nothing was wrong with either half and nothing checked the seam.

In the census above that happens 350 times over 3,920 base/mark joins — 8.93% — and it is the mechanism behind the whole family of bugs where a value is normalised at the API boundary, assembled into a key, and then fails to match the stored version. The fix is not more normalisation calls, it is normalising the final string, or knowing that the seam can never carry a mark.

7 · The compatibility forms delete information on purpose

NFKC maps U+00BD ½ to three characters 1, U+2044 FRACTION SLASH, 2 — note that it is not an ASCII /, so the obvious string compare against "1/2" still fails. It maps U+00A0 NO-BREAK SPACE to an ordinary space, which quietly changes what a whitespace-trimming parser sees. It maps U+FF41 and U+1D43 and 16 other code points to the single letter a. Counted over every non-ASCII code point below U+1FBFF, 1,403 of them have a pure-ASCII NFKC and they collapse onto just 399 distinct ASCII strings.

Which is why “normalise usernames with NFKC then compare” is a two-edged rule: it defeats a homograph, and it also means at least 2,592,702 distinct strings collapse onto admin and 39,767,760 onto paypal — lower bounds, counting only single code points, before ligatures and multi-character mappings. Whether that is a defence or a hole depends entirely on whether you normalise before the uniqueness check or after it.

8 · Your library’s Unicode version is a wire-format decision

Five implementations on one laptop, four Unicode versions between them. The Unicode Normalization Stability Policy says the normalisation of a string is fixed for all future versions — provided every character in it was already assigned in the version you are using. That proviso is doing all the work.

Measured: over all 1,112,064 code points, this 15.1 engine agrees with ICU 77 (Unicode 16.0) on NFC every single time, and disagrees on NFD 20 times, NFKD 56 and NFKC 36. Feed it the decomposed spelling of those 20 and NFC breaks on all 20. A newer character arrives at an older service, is not recognised, is passed through unchanged, and is stored next to the same text normalised by a newer node. No error, two rows.

9 · What the verifier does that this page cannot

The page runs its own engine. The verifier runs everyone else’s: it drives Node/ICU, both Pythons, a Java single-file program and a Perl script, each from a freshly created empty directory, passing every payload as a file path rather than as a shell argument — a scar from Day 72, where a MinGW binary expanded its own * argument into a file listing and made the reference lie.

It also re-derives the exclusion set the other way round: instead of reading the frozen list, it asks each reference which characters fail NFC(NFD(c)) === c and checks that the answer is the set this engine derived. That is the one direction that could catch a wrong hard-coded list, and hard-coded lists are the only data on this page.

What to do about it on Monday

  1. Pick a form per column and write it in the schema. NFC for anything a human typed and will read back. NFKC only for a fold you are willing to lose data to — search keys, lookup columns. Never both in one column.
  2. Normalise at exactly one boundary, and make it the last one. Because concatenation is not closed, normalising each part and then joining is not the same as joining and then normalising. Normalise the final value.
  3. Never assume NFC is shorter. U+0958 gets longer. If you have a length budget in bytes — a column width, a protocol field — measure the normalised form, not the input.
  4. Do not sort combining marks yourself. If you find yourself writing marks.sort(byClass), that is a fifth of your marked strings wrong. Use a stable sort or, better, use the library.
  5. Treat NFKC as a one-way fold. Store the original, index the fold. Once ﬁ is fi and U+00A0 is a space you cannot get the user’s text back.
  6. Do the uniqueness check on the fold, and store the original. If NFKC(casefold(name)) is what makes two accounts “the same”, that has to be the unique index, not a validation the API layer runs.
  7. Pin the Unicode version across services. Two runtimes, two versions, and a newly assigned character passes through one unchanged and gets rewritten by the other. Nothing raises.
  8. Test on three marks, not one. Every wrong normaliser in this page’s scoreboard is correct on a base plus a single mark. The blocked rule only shows up from the third character.

Where the numbers came from

The engine ships three UCD fields as strings — Canonical_Combining_Class, Decomposition_Mapping with its compatibility tag, and sections 1 and 2 of CompositionExclusions.txt. That is all the data. The composition table, the exclusion property, the ordering algorithm, the blocked rule and every Hangul syllable are computed from it.

The differential reference is five independent implementations across four Unicode versions: ICU 77.1 through Node 22 (Unicode 16.0), CPython 3.13 (15.1), Java 21 java.text.Normalizer (15.0), Perl 5.38 Unicode::Normalize (15.0) and CPython 3.11 (14.0). ICU is C++, CPython’s normaliser is its own C, Java’s is its own Java, and Perl’s is its own XS — four separate codebases with four separate data pipelines, which is what makes an agreement mean something.

The lineage is the same one as Day 61 (git check-ignore), Day 69 (ICU through new URL()), Day 72 (OpenSSL and Node), Day 73 (GNU tar and Python tarfile), Day 74 (zlib and gzip) and Day 75 (two SQLite builds): build the engine from the specification, then let something that is not the engine decide whether it is right.
