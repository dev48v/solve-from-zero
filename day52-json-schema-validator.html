Describe the shape once — then check any document against it, live.

A JSON Schema is itself just JSON that describes the shape another JSON value must have: which type each field is, which properties are required, the allowed enum values, string patterns, numeric minimum/maximum, array bounds, and so on. A validator walks the document and the schema together, recursing into every object property and array element, and records each place the value breaks a rule. Below is a from-scratch validator — no ajv, no dependency — that does exactly that: edit either box and it re-validates as you type, printing pass / fail plus a list of violations, each tagged with the failing keyword and the JSON-pointer path that points at the exact spot in the document. Five things people get wrong about JSON Schema validation

1. integer is not number. 3 passes both, but 3.5 passes number and fails integer — the check is "is it a whole number", not "does it look like a digit string". A JSON "3" (string) fails both. 2. additionalProperties is off by default being true. Unless you set it to false (or a schema), any extra key is allowed — a huge source of "why did my typo validate?". 3. required does not imply properties. Listing a key in required only asserts it exists; it says nothing about its type. You still need a matching entry under properties to constrain the value. 4. Paths are JSON Pointers, not dot-paths. The failing location is /items/2/sku, with / separators and array indices as segments — and literal / or ~ in a key are escaped as ~1 / ~0. 5. $ref replaces its siblings. In draft-07 a schema with $ref ignores keywords sitting next to it — the reference is the schema at that spot. Put constraints inside the referenced definition, not beside the $ref.

🔨 Build it yourself

    
A JSON Schema validator sounds heavy, but the core is a single recursive function. You hand it a schema node, a data value, and the path you took to reach that value; it applies every keyword the schema declares, and for the keywords that descend — properties, items, additionalProperties, $ref — it calls itself on the child with the path extended by one segment. Errors are collected into one shared array as { path, keyword, message }, so when the walk finishes you have every violation with the exact JSON-pointer that locates it. No parser to write (the browser's JSON.parse gives you plain objects and arrays), no library — under 120 lines of real logic. Here it is, step by step.

    
    
      
  1. 
        
    1
    Parse both inputs, guard the JSON
    
        
    The schema and the document both arrive as text. Run each through JSON.parse inside a try/catch; a malformed schema or document is its own kind of error and should be reported before any validation runs. Once parsed you have ordinary JS objects, arrays, numbers, strings, booleans and null — nothing exotic to walk.
    
        
    function parseOrErr(text){
  try { return { value: JSON.parse(text), error: null }; }
  catch (e) { return { value: undefined, error: e.message }; }
}
const s = parseOrErr(schemaText), d = parseOrErr(docText);
if (s.error || d.error) return showParseErrors(s.error, d.error);
    
      
    2. 
      
  2. 
        
    2
    A precise JSON type test
    
        
    JSON has seven types and JavaScript blurs a few, so write one function that answers "does this value match this schema type?". The traps: typeof null === "object" and arrays are objects too, so screen those out; integer means a whole number (Number.isInteger), and a JSON string of digits is not a number.
    
        
    function matchesType(v, t){
  switch (t){
    case "string":  return typeof v === "string";
    case "number":  return typeof v === "number" && !Number.isNaN(v);
    case "integer": return typeof v === "number" && Number.isInteger(v);
    case "boolean": return typeof v === "boolean";
    case "array":   return Array.isArray(v);
    case "object":  return v !== null && typeof v === "object" && !Array.isArray(v);
    case "null":    return v === null;
  }
}
    
      
    3. 
      
  3. 
        
    3
    The recursive core: (schema, data, path)
    
        
    One function does everything. It takes the current schema node, the value at this spot, and the JSON-pointer path that reached it, plus the root schema (for $ref) and the shared errors array. Each keyword that applies pushes a { path, keyword, message }. Keywords that go deeper call validate again with a longer path. That's the whole architecture.
    
        
    function validate(schema, data, path, root, errors){
  if (schema === true)  return;           // "anything goes"
  if (schema === false){ errors.push({ path, keyword:"false",
                          message:"no value is allowed here" }); return; }
  if (typeof schema !== "object" || schema === null) return;
  // ...apply type, enum, string/number/array/object keywords, $ref...
}
    
      
    4. 
      
  4. 
        
    4
    type & enum — the whole-value checks
    
        
    type may be a single string or an array of allowed types — the value must match at least one. enum restricts the value to a fixed list; because entries can be objects or arrays, compare with a deep equality, not ===. Both attach to whatever value sits at the current path.
    
        
    if (schema.type !== undefined){
  const types = [].concat(schema.type);
  if (!types.some(t => matchesType(data, t)))
    errors.push({ path, keyword:"type",
      message:`expected ${types.join(" or ")}, got ${jsonType(data)}` });
}
if (schema.enum !== undefined && !schema.enum.some(e => deepEqual(e, data)))
  errors.push({ path, keyword:"enum",
    message:`must be one of ${schema.enum.map(v => JSON.stringify(v)).join(", ")}` });
    
      
    5. 
      
  5. 
        
    5
    String & number constraints
    
        
    These only apply when the value is of the right primitive type — if data is not a string, string keywords simply do not fire (the type keyword is what complains about the wrong type). Count characters with the spread form so emoji count as one, and compile pattern as a real RegExp.
    
        
    if (typeof data === "string"){
  const len = [...data].length;
  if (schema.minLength != null && len < schema.minLength)
    push("minLength", `string length ${len} < ${schema.minLength}`);
  if (schema.maxLength != null && len > schema.maxLength)
    push("maxLength", `string length ${len} > ${schema.maxLength}`);
  if (schema.pattern != null && !new RegExp(schema.pattern).test(data))
    push("pattern", `does not match /${schema.pattern}/`);
}
if (typeof data === "number"){
  if (schema.minimum != null && data < schema.minimum) push("minimum", `${data} < ${schema.minimum}`);
  if (schema.maximum != null && data > schema.maximum) push("maximum", `${data} > ${schema.maximum}`);
}
    
      
    6. 
      
  6. 
        
    6
    Arrays — recurse per element, path + "/" + i
    
        
    For arrays, check minItems/maxItems on the length, then apply the items subschema to every element — calling validate recursively with the path extended by the index. That index becomes a JSON-pointer segment, which is how an error can say it happened at /tags/2.
    
        
    if (Array.isArray(data)){
  if (schema.minItems != null && data.length < schema.minItems)
    push("minItems", `${data.length} items < ${schema.minItems}`);
  if (schema.maxItems != null && data.length > schema.maxItems)
    push("maxItems", `${data.length} items > ${schema.maxItems}`);
  if (schema.items)
    data.forEach((el, i) => validate(schema.items, el, path + "/" + i, root, errors));
}
    
      
    7. 
      
  7. 
        
    7
    Objects — required + properties recursion
    
        
    required asserts each named key is present (the failing path points at the missing key). properties maps key → subschema; for every key that appears in both the data and properties, recurse. Escape each key into a pointer segment — a literal / becomes ~1 and ~ becomes ~0 so paths stay unambiguous.
    
        
    if (isPlainObject(data)){
  (schema.required || []).forEach(k => {
    if (!(k in data)) errors.push({ path: path + "/" + ptr(k),
      keyword:"required", message:`missing required property "${k}"` });
  });
  const props = schema.properties || {};
  for (const k of Object.keys(data))
    if (Object.prototype.hasOwnProperty.call(props, k))
      validate(props[k], data[k], path + "/" + ptr(k), root, errors);
}
const ptr = k => String(k).replace(/~/g,"~0").replace(/\//g,"~1");
    
      
    8. 
      
  8. 
        
    8
    additionalProperties — close the object
    
        
    Any key not named in properties is "additional". If additionalProperties is false, each such key is an error; if it is a schema, validate the extra value against it; if it is absent (the default), extras are allowed. This is what turns an open object into a strict one.
    
        
    if (isPlainObject(data) && schema.additionalProperties !== undefined){
  const named = schema.properties || {};
  for (const k of Object.keys(data)){
    if (Object.prototype.hasOwnProperty.call(named, k)) continue;   // declared
    if (schema.additionalProperties === false)
      errors.push({ path: path + "/" + ptr(k), keyword:"additionalProperties",
        message:`property "${k}" is not allowed` });
    else if (typeof schema.additionalProperties === "object")
      validate(schema.additionalProperties, data[k], path + "/" + ptr(k), root, errors);
  }
}
    
      
    9. 
      
  9. 
        
    9
    $ref — follow a JSON pointer inside the doc
    
        
    A local $ref like #/definitions/address means "validate against the subschema found at this pointer in the root schema". Resolve it by splitting on / and walking the root, un-escaping ~1/~0, then validate against the target. Because the target can itself contain $ref back to a definition, this naturally supports recursive schemas like trees.
    
        
    function resolveRef(ref, root){
  if (ref === "#") return root;
  const parts = ref.replace(/^#\//,"").split("/")
                   .map(p => p.replace(/~1/g,"/").replace(/~0/g,"~"));
  return parts.reduce((cur, p) => (cur == null ? undefined : cur[p]), root);
}
if (schema.$ref !== undefined){
  const target = resolveRef(schema.$ref, root);
  if (target === undefined) errors.push({ path, keyword:"$ref",
    message:`cannot resolve $ref "${schema.$ref}"` });
  else validate(target, data, path, root, errors);
  return;                        // $ref replaces sibling keywords (draft-07)
}
    
      
    10. 
      
  10. 
        
    10
    Collect, then report pass / fail
    
        
    Kick the whole thing off at the root with an empty path, hand in a fresh errors array, and let the recursion fill it. Zero errors means the document is valid; otherwise render each violation — keyword, its JSON-pointer path, the message, and the value at that pointer, which you can pull straight back out of the parsed document.
    
        
    function run(schema, data){
  const errors = [];
  validate(schema, data, "", schema, errors);   // root path = ""
  return errors;                                 // [] === valid
}
const errors = run(schema, data);
render(errors.length === 0 ? "VALID" : "INVALID", errors, data);
// each error → { path:"/role", keyword:"enum", message:"..." }

🎉 Day 52 of SolveFromZero.
You built a real JSON Schema validator with no library, and the whole thing collapsed into one recursive function: apply every keyword the schema node declares to the value at the current path, and for the keywords that descend — properties, items, additionalProperties, $ref — call yourself on the child with the path extended by one JSON-pointer segment. Collect { path, keyword, message } as you go and an empty list at the end means "valid". That same shape scales to the rest of the spec — patternProperties, oneOf, if/then/else — they are just more keywords hanging off the same recursion. Reach for it whenever you need to trust JSON coming from a form, an API, or a config file.
