SOLVEFROMZERO · DAY 77

🧩 A real POSIX ERE matcher — a hand-written parser, a Thompson automaton run as a parallel simulation for leftmost-longest, and a backtracker for leftmost-first, over one shared syntax tree, so the same pattern string can be read two ways and matched two ways and the four answers put side by side. Everyone knows the first rule of alternation: the branches are tried in order, so put the longer one first. /a|ab/ against ab matches a in JavaScript, Python and Perl. In grep, sed and awk it matches ab — and so does /ab|a/. Over 12,000 swapped pairs, reordering the branches changes the POSIX answer 0 times and the ECMAScript answer 1,860 times, 15.50%: the single most-repeated piece of regex advice is load-bearing in one family and a no-op in the other, with no error either way. 🔴 The finding is positional. a*? is three characters. To ECMAScript it is one lazy quantifier and the answer is the empty string; to POSIX it is two operators, (a*)?, and the answer is the whole run — opposite extremes from an identical spelling, decided only by which binary you piped it through. Inside a bracket expression POSIX has no escape character at all, so [\.] is a class of two members, backslash and dot: grep and sed agree, and gawk, shipped by the same project, does not. Of 40 frontier patterns, five real implementations return the same answer for only 19; twenty split two ways and ^* splits three (sed: syntax error · grep: matches · gawk: no match). And the divergence is not chaos, it is an identity: over 16,800 generated cases the two policies always agree on whether there is a match, always start at the same index, and the ECMAScript match is a prefix of the POSIX match 16,800 times out of 16,800 — they differ only in how much, on 1,758 of them, 10.46%. GNU is then neither engine: its whole match is POSIX leftmost-longest on 1,409 of 1,409 capture cells, while its \1 and \2 are backtracking-ordered, so the assignment the standard actually specifies disagrees with what GNU produces 53 times, 3.76%. Even “the Perl family” is not one family — Python and Perl leave V8 on 48 of the same 16,800 cases, every one of them a quantifier whose body can match the empty string. Every verdict is differential against six real implementations — GNU grep 3.0, GNU sed 4.9, GNU Awk 5.0.0, Node 22 (V8), CPython 3.11 and Perl 5.38 — plus a definition-based oracle, every subprocess run from an empty directory. There are two layers, and almost every argument about regex confuses them

When two tools disagree about a pattern, exactly one of two things has happened. Either they read the pattern differently — the string parsed into two different syntax trees — or they read it the same way and chose a different match out of the several the pattern allows. Those are separate mechanisms and they fail in separate ways, but in practice they arrive together as one wrong answer and get argued about as one thing.

This engine keeps them apart on purpose. parsePattern(src, dialect) produces a tree, and search(src, s, {dialect, policy}) then runs one of two searches over it. Two dialects times two policies is four combinations, and only two of them are real products: posix + longest is what grep, sed and awk do, and js + first is what JavaScript, Python, Perl, PCRE, Java and .NET do. The other two are probes: hold the policy still and swap the dialect and you have isolated the parsing; hold the dialect still and swap the policy and you have isolated the search. That is how the MATCH tab can tell you why two engines disagree instead of only that they do.

On the generated corpus the answer is always the same: 100% of the divergence is policy, because the generator only uses constructs both dialects read alike. On the frontier table it flips: nearly all of it is syntax. Same subject, same tooling, two completely different causes — which is why one debugging habit does not work for both.

Leftmost-longest is a rule about the whole match, and it needs an automaton

POSIX says: of all the matches, take the one that starts earliest; of the matches that start there, take the longest. That is a statement about the set of matches, not about the order in which you look for them, and it has a consequence people find surprising: there is nowhere to put a preference. a|ab and ab|a denote the same set, so they are the same regex. The branch order is not part of the semantics, and an implementation that honoured it would be wrong.

You cannot get that out of a backtracker without extra machinery, because a backtracker is an order. So this engine compiles the tree to a Thompson NFA and runs the classic parallel simulation: keep the whole set of reachable states, feed one character, keep the new set, and every time the accepting state is in the set write down the position. When the set goes empty, the last position you wrote down is the longest match from that start. Scan the start position forward and the first one that produces any match is the leftmost. Two loops, no recursion, no preference anywhere.

The verifier does not take that on trust. It rebuilds leftmost-longest a second time from the definition — a memoised “does this node derive exactly s[i..j]” over a tree the corpus generator built, never the engine's parser — and then simply takes the smallest i and the largest j. Over 16,800 cases the automaton and the definition agree 16,800 times, and so do GNU sed, GNU grep and GNU Awk.

Leftmost-first has no rule at all — the search order is the answer

The other family works the other way round. There is no property that picks the match out of the set; the match is defined as whatever the backtracker reaches first, and the backtracker's traversal order is written into the specification. Alternatives left to right. Greedy quantifiers try one more repetition before they try stopping; lazy ones try stopping first. The first complete path wins, and nothing later in the search can displace it however much longer it would have been.

That is why /a|ab/ stops at a. The first branch succeeded, the rest of the pattern is empty, the match is complete, and ab is never considered. It is also why the standard advice exists at all: in this family, branch order is the only lever you have.

Both descriptions are precise; neither is a bug. What is a bug is carrying one model into the other's territory — writing grep -Eo 'GET|GET /health' and expecting the health-check branch never to fire, or writing /\d{4}|\d{2}/ in JavaScript and expecting four digits.

The two policies always agree on whether, and only ever differ on how much

The two searches are running over the same tree, so they recognise the same language: if one finds a match, the other must. And both scan the start position from the left, so the leftmost start is the same for both. Everything they can disagree about is therefore squeezed into a single dimension, the end.

Those are testable statements, and this page runs them as identities rather than as examples. Over 16,800 generated cases: same verdict on whether there is a match, 16,800 times; same start index, 16,800 times; the POSIX match never shorter, 16,800 times; and the ECMAScript match a literal prefix of the POSIX one, 16,800 times. Then they diverge on 1,758 of them — 10.46%, from 186 of the 420 patterns. A wider engine-only sweep repeats the same five invariants over 63,000 cells with 0 failures.

The practical reading: switching a pattern between the two families will never turn a match into a miss. It will silently truncate one in about one case in ten, which is strictly worse, because a miss is loud and a short match is not.

A bracket expression is a list, and a list has no escape character

This is where the two dialects stop being the same language. In POSIX, everything between [ and the closing ] is a list of members, and the only characters with any special meaning inside it are ^ in first position, - between two members, and [ immediately followed by :, . or =. A backslash is a member. So [\.] is a two-member class, backslash or dot, and the reflex of escaping the dot “just in case” has silently widened the class.

The consequences run the other way too. ] in first position is a member, so []a] is a legal two-member class in POSIX — and in ECMAScript [] is a complete, empty class that can never match, followed by the literal characters a]. Same six characters, one matches two things and the other matches nothing. Conversely [a\]b] is a class of a and backslash followed by the literal text b] in POSIX, and a three-member class in ECMAScript. And a trailing - is a member, which is why [a-] works everywhere and reads as a broken range to everyone who sees it.

[[:alpha:]] is the other half of the split. POSIX classes are locale-aware and are the only portable way to say “a letter” in an ERE, because there is no \w. ECMAScript has never had them: [[:alpha:]] parses as a class containing [, :, a, l, p, h followed by a literal ]. It does not raise an error. It just matches something else. Perl, notably, does support them — which is why Perl sits in neither camp cleanly.

a*?: the same three characters, the opposite extreme

POSIX ERE has no lazy quantifiers. It also does not forbid writing a quantifier after a quantifier: the grammar applies them left to right, so a*? parses as (a*)? — a greedy run of a, made optional. Against aaa that is the whole string. In ECMAScript the trailing ? is not an operator at all, it is a flag on the *, and the answer is the empty string. Longest possible and shortest possible, from a pattern that is byte-for-byte identical, and no diagnostic on either side.

Push it one character further and the split changes shape rather than going away. a** is legal POSIX — two stars, still the longest run — and a SyntaxError in V8, CPython and Perl alike. So of the three spellings a*, a*?, a**, the two families agree on the first, return opposite answers for the second, and disagree about whether the third is a program.

The general lesson is that stacked postfix operators are the one place where the two grammars are genuinely incompatible rather than merely different, because ECMAScript spends the second operator slot on laziness and POSIX spends it on composition.

GNU is not POSIX, and the three GNU tools are not each other

The engine on this page implements the specification, which makes it a useful instrument for measuring how far the tools have drifted from it. Of the 40 frontier patterns it agrees with GNU sed on 36, and every one of the four gaps is a named GNU extension rather than a silent bug: \w and \b (POSIX ERE has no shorthand classes and no word boundaries), a{,2} (POSIX intervals are {n}, {n,} and {n,m}, so {,2} is four literal characters), and ^* (quantifying an anchor is undefined).

The GNU tools then disagree with each other. gawk honours backslash escapes inside a bracket expression where grep and sed do not, which is the [\.] split, and it reads \b as a backspace rather than a word boundary — gawk spells that one \y. And ^* gets three different answers from three programs in the same distribution: sed refuses to compile it, grep compiles it and matches, gawk compiles it and does not.

None of this is exotic. It is the ordinary situation for anyone whose build pipeline greps on one machine, awks on another and ships a JavaScript validator for the same field.

Captures: GNU gets the whole match right and the pieces Perl-wrong

POSIX specifies the subexpressions too: consistent with the whole match being the leftmost longest, each parenthesised subexpression from left to right shall match the longest possible string. That is a second optimisation problem layered on the first, and it is genuinely awkward to implement.

So implementations mostly do not. Over 1,409 cells drawn from 160 two-group patterns, this engine's captures agree with what GNU sed puts in \1 and \2 on 1,409 of 1,409 — because it computes them the same way GNU does, by pinning a backtracking search to the end the automaton already chose and taking that search's own preference order. The rule the standard writes down disagrees with both of us on 53 cells, 3.76%. ([a-c])c?(c+) against bcc is the shape: GNU assigns b and c, letting the un-grouped c? take a character; the standard says the second group should have taken cc.

Both numbers are worth carrying. The whole match from a GNU tool is POSIX. The pieces are not, and if you have ever ported a sed expression to Python and found the groups shifted while the match did not, this is the reason.

“The Perl family” is not one family either

Grouping every backtracking engine together is convenient and wrong. On the generated corpus — where the syntax is deliberately neutral, so only the search can differ — CPython and Perl leave V8 on 48 of 16,800 cases, and they leave it in exactly the same places and with exactly the same answers. Every one of those 48 patterns has a quantifier whose body can match the empty string.

The mechanism is a single clause. ECMAScript's repeat rule discards an iteration that consumed nothing, and discarding it sends the search back into the body to try the body's remaining alternatives — so (|a)* against aaa rejects the empty branch and takes a, three times, and matches aaa. Python and Perl accept the empty iteration and stop the loop there, matching the empty string. Move the empty branch to the end, (a|)*, and all three agree again. The neighbour decides.

On the frontier the split widens for a different reason: Perl disagrees with V8 on 11 of 40 and Python on 5, mostly because Perl speaks POSIX bracket classes and accepts ] in first position. There are not two families here. There are four dialects that happen to cluster.

Why the fast one is the one without the preference

The parallel simulation carries at most one copy of each automaton state, so its work is bounded by states times input length no matter what the pattern looks like. There is no input that makes it exponential, and there is no such thing as a catastrophic-backtracking outage in grep. That property is not a clever optimisation on top of leftmost-longest; it is the same fact seen from the other side. Because the rule says nothing about search order, the implementation is free to explore every branch at once.

A backtracker cannot do that, because the order it explores in is the answer it is required to give. (a+)+b against a long run of a with no b is the standard demonstration. The engine on this page carries a step limit for exactly that reason; the automaton side needs none.

This is also why the two families cannot simply be merged. Backreferences and lookaround are expressible in a backtracker and not in a finite automaton, and leftmost-longest is expressible in an automaton and awkward in a backtracker. RE2 and Go's regexp chose the automaton and dropped backreferences; every language you write validation in chose the other way.

How this page is checked

Nothing here is asserted against my own expectations. Six real implementations ship on the build machine and all six are used: GNU grep 3.0 for membership, GNU sed 4.9 for exact offsets and for \1/\2, GNU Awk 5.0.0 for offsets, Node 22's V8, CPython 3.11's re and Perl 5.38. A seventh reference is written inside the verifier and shares no code with the engine: leftmost-longest read straight off the definition, over a syntax tree the corpus generator produced rather than the engine's parser, which checks the parser and the automaton at once.

Every pattern and subject crosses the process boundary hex-encoded inside a file, never as a shell argument, and every subprocess runs from a freshly created empty directory — the Day 72 lesson, when a MinGW binary globbed its own argv and turned a bare * into a list of filenames before the code under test ever saw it. Each reference prints its version, which is asserted, and each is fed known-answer probes including a literal * before any of its output is believed. The generated corpus is asserted to contain no backslash at all, so no GNU extension can hide inside it and excuse a disagreement.

What to do about it on Monday

  1. Never move a regex between grep/sed/awk and an application language without re-testing it. It will not throw. About one pattern in ten changes its answer, and the change is always a shorter match, never a missing one.
  2. If you rely on branch order, you are in the backtracking family — say so. Writing ab|a instead of a|ab is free and makes the intent survive the port, because it is the spelling both families agree on.
  3. Stop escaping inside bracket expressions. [.], [$], [*] and [a-] need no backslash anywhere; adding one adds a member in POSIX and is merely noise in ECMAScript.
  4. Write [] and ] deliberately. If you need a literal ] in a class, put it first for POSIX tools and escape it for everything else — there is no spelling that works in both, which is itself the reason to keep the class out of shared config.
  5. Do not write a*? in a shell pipeline expecting laziness. There is no lazy quantifier in ERE. If you need the shortest match, use a negated class: "[^"]*" rather than ".*?" — and that spelling is also faster in the backtracking family.
  6. Use [[:alpha:]] in shell tools and \w in code, and never the other way round. Neither one errors in the wrong place; both silently match something else.
  7. If your groups shift when you port a sed expression, the whole match is probably still right. Check the group boundaries specifically — that is the layer that moved.
  8. Reach for an automaton engine when the pattern comes from a user. RE2, Go's regexp and grep cannot be made to hang. A backtracker with a user-supplied pattern is an availability bug waiting for the right input.
  9. Pin the tool, not just the pattern, in CI. gawk disagrees with sed from the same distribution; BSD and GNU differ again. A pattern is not portable, a pattern-plus-implementation is.

How the engine is put together

  • parsePattern(src, dialect) — one recursive-descent parser, two bracket readers and two escape readers. Returns a tree plus the notes the MATCH tab shows, or throws with .reSyntax.
  • compileNFA(ast) — Thompson construction. Alternation becomes a split, unbounded repetition becomes a back edge, bounded repetition is unrolled, and anchors become zero-width assertion states resolved during the epsilon closure.
  • longestFrom(nfa, s, i) — the parallel simulation. One Int32Array stamp per step keeps the state set deduplicated; the last position at which the accepting state was live is the answer.
  • makeBacktracker(parsed) — continuation-passing recursion with an explicit empty-iteration guard, greedy and lazy repetition, and capture save/restore on failure. Takes an optional required end, which is what makes the POSIX capture pass possible.
  • strictPosixCaps() — enumerates every parse that ends where the automaton said and picks the capture vector that is lexicographically longest, group by group. This is the rule as written, and it is the one nobody implements.
  • attribute(src, s) — runs all four dialect × policy combinations and reports whether a disagreement came from the reading or the search.
  • selftest() — identities and bounds only, plus a live differential against the RegExp in the browser running the page.

The engine between ENGINE:BEGIN and ENGINE:END in this file touches no DOM, reads no clock and has no random source. Everything below it is user interface.

What the verification actually did

The corpus is generated from a grammar restricted to constructs both dialects read identically — literals, ., bracket expressions without escapes, groups, alternation and the five interval forms — and the verifier asserts that no pattern in it contains a backslash, a {,n} or a quantified anchor, so a POSIX-family disagreement cannot be excused as a GNU extension. Subjects are strings over {a,b,c} of length 0 to 6, and to 8 for the wide sweep.

Where this page stops

  • No backreferences, no lookaround. Neither is in POSIX ERE, and adding them to the ECMAScript side would mean the automaton and the backtracker no longer recognise the same language — which is the identity most of the checking here rests on.
  • ASCII and the C locale. POSIX character classes and ranges are locale-dependent; every reference here runs under LC_ALL=C and the corpus is ASCII, so the numbers say nothing about collating sequences or multi-character collating elements.
  • Single-line subjects. . and a negated bracket both exclude the newline here, which is what the line-oriented tools do; a POSIX library caller with a multi-line buffer would see different behaviour.
  • The strict POSIX capture rule is one reading. The standard's wording about “subexpressions” can be read as covering every subpattern rather than only the parenthesised ones. This page takes the parenthesised reading and reports the divergence from GNU as a measurement, not as a verdict on who is wrong.
  • gawk is used for offsets only. Its match() gives the whole match, so the capture comparison runs against sed alone.
