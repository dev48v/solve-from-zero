📐 CSS clamp() Generator — pick a min & max size and the two viewport widths they should hit, and it fits a straight line through those two points: size = slope·100vw + intercept. It emits the full clamp(MIN, calc(…rem + …vw), MAX) so type & spacing scale smoothly between the breakpoints instead of jumping · drag a simulated viewport slider and watch a live element resize, with the slope / intercept / rem math shown at every step · vanilla JS, no library

One value that grows with the screen — no media queries, just a line.

Fluid sizing replaces a stack of breakpoints with a single rule: pick the size you want on a small screen and on a large screen, and let the value glide linearly between them. That is exactly a line through two points — (minVw, minSize) and (maxVw, maxSize). Compute its slope and where it crosses zero (the intercept), express the slope as a vw amount (1vw = 1% of the viewport, so multiply by 100) and the intercept in rem, and you get a calc() that is the fluid preferred value. Wrapping it in clamp(MIN, PREFERRED, MAX) pins the ends so it never gets smaller than min or bigger than max. Everything below is computed live: drag the viewport simulator and the preview element resizes using the real number the browser would pick at that width.

Five things people get wrong about fluid clamp()

1. Sizing in px can break zoom. A clamp() whose MIN and MAX are in px ignores the user's browser font-size setting; expressing the bounds in rem keeps text zoomable and is the accessible default — that is why this tool outputs rem unless you switch it. 2. A pure-vw font never stops. font-size:5vw looks fine at 1280px and is unreadable at 320px or absurd on a 4K monitor. The whole point of clamp() is the two guards; do not drop them. 3. The vw unit is 1% of the viewport, not the parent. The coefficient is slope × 100 precisely because 1vw = viewport/100 — mixing that up gives a line 100× too shallow. 4. clamp needs MIN < MAX. The first argument must be the smaller number; if your "min size" is actually bigger than your "max size" you have to swap them, or the clamp collapses to a constant. 5. Fluid is for a range, not a leap. Between the two breakpoints the value is a smooth ramp; outside them it is flat. Pick breakpoints that bracket the sizes people actually use, or most viewers sit on a pinned end and never see the fluid part.

🔨 Build it yourself

    
A fluid-size generator is, underneath the sliders, one small piece of coordinate geometry. You are given two points — the size you want at a small viewport and the size at a large viewport — and you fit the straight line through them. That is a slope and an intercept, nothing more. The only CSS-specific twists are (1) turning the slope into a vw amount by multiplying by 100, because one vw is 1% of the viewport, and (2) writing the intercept in rem so the result respects the user's zoom. Assemble those into calc(intercept·rem + coeff·vw), wrap it in clamp(min, that, max) with the bounds sorted, and you have a value that ramps smoothly between the breakpoints and is pinned flat outside them. To preview it without actually resizing the window, evaluate the same line in JS at a simulated width and clamp it. Under 100 lines of real logic — here it is, step by step.

    
    
      
  1. 
        
    1
    Model it as two points on a line
    
        
    The whole problem is "what size at what width?". Write the two things you know as coordinates: at the small viewport you want the small size, at the large viewport the large size. Those are two points (x1,y1) and (x2,y2) where x is viewport-px and y is size-px. Every other number falls out of them.
    
        
    // x = viewport width (px), y = the size we want (px)
const p1 = { x: minVw, y: minSize };   // e.g. (320, 18)
const p2 = { x: maxVw, y: maxSize };   // e.g. (1280, 32)
// goal: the straight line y = slope*x + intercept through p1 and p2
    
      
    2. 
      
  2. 
        
    2
    Slope = rise over run
    
        
    The slope is how many px of size you gain for each px of viewport: the change in size divided by the change in width. Guard the denominator — if the two viewports are equal the line is vertical (there is no fluid range), so treat the slope as 0 and the value becomes a constant.
    
        
    const run = maxVw - minVw;                       // change in viewport
const slope = run === 0 ? 0                       // same breakpoint -> flat
                        : (maxSize - minSize) / run;   // px per px
// (32 - 18) / (1280 - 320) = 14 / 960 = 0.014583
    
      
    3. 
      
  3. 
        
    3
    Intercept: where the line hits viewport 0
    
        
    With the slope known, solve y = slope·x + b for b using either point. The intercept is the size the line would take at a viewport of 0 — usually a small or even negative number, and that is fine; it is only the constant part of the equation, not a size you ever render on its own.
    
        
    const intercept = minSize - slope * minVw;   // b = y - m*x
// 18 - 0.014583 * 320 = 18 - 4.6667 = 13.3333 px
// check: at 1280 -> 13.3333 + 0.014583*1280 = 32 ✓
    
      
    4. 
      
  4. 
        
    4
    Turn the slope into a vw amount (×100)
    
        
    CSS cannot say "0.0146 px per px of viewport" directly — it says it in vw, and 1vw equals 1% of the viewport, i.e. viewport/100 px. So a coefficient of k·vw contributes k · viewport/100 px. To make that equal slope·viewport, set k = slope · 100. That single multiply is the bridge from geometry to CSS.
    
        
    const vwCoeff = slope * 100;     // 0.014583 * 100 = 1.4583  -> "1.4583vw"
// why: 1.4583vw = 1.4583 * (viewport/100) = 0.014583 * viewport  ✓
// so the vw term reproduces exactly slope*viewport
    
      
    5. 
      
  5. 
        
    5
    Convert the intercept to rem for accessibility
    
        
    Bounds and the intercept go out in rem so the value scales with the user's browser font-size — a pure-px clamp silently overrides someone who set larger text. One rem is the root font-size (16px by default), so divide every px number by it. The vw coefficient stays as-is; it is already relative.
    
        
    const root = 16;                        // 1rem = 16px
const toRem = px => px / root;
const interceptRem = toRem(intercept);  // 13.3333 / 16 = 0.8333rem
const minRem = toRem(minSize);          // 18/16 = 1.125rem
const maxRem = toRem(maxSize);          // 32/16 = 2rem
    
      
    6. 
      
  6. 
        
    6
    Assemble the preferred value with calc()
    
        
    The fluid middle argument is the line itself, written in CSS: the constant rem part plus the vw part. calc() is what lets you add two different units. Round for readability, and keep the sign handling clean so a negative intercept reads as a subtraction rather than + -0.5rem.
    
        
    function preferred(interceptRem, vwCoeff){
  const b = round(interceptRem), k = round(vwCoeff);
  const sign = b < 0 ? "- " + Math.abs(b) : "+ " + b;   // tidy the sign...
  return `calc(${k}vw ${b < 0 ? "- "+Math.abs(b) : "+ "+b}rem)`;
}
// -> "calc(1.4583vw + 0.8333rem)"
    
      
    7. 
      
  7. 
        
    7
    Wrap it in clamp() with sorted bounds
    
        
    clamp(MIN, PREFERRED, MAX) returns PREFERRED but never below MIN or above MAX — the two pins that stop a fluid value from shrinking to nothing or ballooning. The catch: clamp requires MIN ≤ MAX, so sort the two sizes before placing them; whichever is numerically smaller is the floor, regardless of which viewport it belongs to.
    
        
    const lo = Math.min(minRem, maxRem);
const hi = Math.max(minRem, maxRem);
const css = `clamp(${round(lo)}rem, ${preferred(interceptRem, vwCoeff)}, ${round(hi)}rem)`;
// clamp(1.125rem, calc(1.4583vw + 0.8333rem), 2rem)
    
      
    8. 
      
  8. 
        
    8
    Preview by evaluating the same line in JS
    
        
    You cannot resize the real window from a slider, so reproduce what the browser would compute: plug the simulated width into intercept + slope·width and clamp it between the two sizes with plain Math.min/Math.max. Set that as the preview element's font-size in px and it grows and shrinks exactly as the CSS would at that viewport.
    
        
    function sizeAt(width){
  const raw = intercept + slope * width;             // the line, in px
  return Math.min(Math.max(raw, Math.min(minSize,maxSize)),
                                Math.max(minSize,maxSize));  // clamp ends
}
pvText.style.fontSize = sizeAt(simWidth) + "px";     // live preview
    
      
    9. 
      
  9. 
        
    9
    Which zone is the viewport in?
    
        
    To label the preview honestly, compare the simulated width to the breakpoints: at or below minVw the value is pinned to the min (flat); at or above maxVw it is pinned to the max; in between it is on the fluid ramp. This is the same three-part shape clamp() produces, and it is what the coloured track under the slider draws.
    
        
    function zone(width){
  if (width <= Math.min(minVw,maxVw)) return "clamped-min";
  if (width >= Math.max(minVw,maxVw)) return "clamped-max";
  return "fluid";                                    // on the ramp
}
// the track: [min pin] --- [fluid gradient] --- [max pin]
    
      
    10. 
      
  10. 
        
    10
    Wire controls ↔ one state, recompute on every input
    
        
    Each input (min/max size, min/max viewport, root, the simulator) writes into a single state object and calls one render() that recomputes the line, rebuilds the clamp string, repaints the preview, math and stats. A slider and its number box are two views of the same value — update the counterpart when either changes and everything stays in sync with no special cases.
    
        
    const S = { minSize:18, maxSize:32, minVw:320, maxVw:1280, root:16, sim:768 };
function bindPair(rangeEl, numEl, key){
  rangeEl.oninput = () => { S[key] = +rangeEl.value; numEl.value = rangeEl.value; render(); };
  numEl.oninput   = () => { S[key] = +numEl.value;   rangeEl.value = numEl.value;  render(); };
}
function render(){ const f = computeFluid(S); paintClamp(f); paintPreview(f); paintMath(f); }
