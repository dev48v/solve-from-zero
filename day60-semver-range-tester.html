A version is a promise. A range is the set of promises you will accept.

1.2.3 is not a decimal number and it is not a string — it is three independent counters with a contract attached. Bump the patch and you promised nothing changed but a bug. Bump the minor and you promised you only added. Bump the major and you admitted you broke something. A range like ^1.2.3 is you saying "I will take any promise up to the next break". Everything a package manager does with versions falls out of two functions: a comparator that puts two versions in order, and a desugarer that turns friendly range syntax into plain >= / < bounds. This page implements both from scratch — including the parts everybody gets wrong: 0.9.0 < 0.10.0, 1.0.0-alpha < 1.0.0, 1.0.0-alpha.11 > 1.0.0-alpha.2, build metadata being invisible to comparison, and why your -beta.1 silently refuses to install.

Five things worth knowing about semver

1. The three numbers are counters, not digits. 0.10.0 is newer than 0.9.0, because each field is compared as an integer, one field at a time, left to right. Sort your version list as strings and 0.10.0 lands before 0.9.0; sort with parseFloat and 1.2.3 becomes 1.2 and ties with 1.2.9. Both bugs ship regularly. 2. 0.x has no contract. The spec explicitly says anything may change at any time below 1.0.0, which is why ^ changes meaning there: ^1.2.3 allows everything under 2.0.0, but ^0.2.3 allows only up to 0.3.0, and ^0.0.3 allows nothing but 0.0.3 itself. Staying on 0.x forever is not "being careful", it is opting out of the promise. 3. Prereleases are invisible by default. 1.3.0-beta.1 does not satisfy ^1.2.3, even though it sits neatly between the bounds — a range only admits a prerelease if one of its own comparators names a prerelease at the same major.minor.patch. That is deliberate: nobody wants an untested beta pulled in by a caret, and it is why publishing under a dist-tag is the normal way to ship one. 4. Build metadata is not a version. 1.0.0+build.1 and 1.0.0+build.2 are equal for every comparison in the spec — the + part is carried along and ignored. Registries reject the second upload as a duplicate, so metadata can label a build but can never distinguish a release. 5. A range is not a version. "lodash": "^4.17.0" in package.json is a wish; the lockfile is the fact. Two machines installing the same wish a week apart legitimately get different code — which is the whole reason npm ci and committed lockfiles exist.

🔨 Build it yourself

    
A semver engine is two ideas stacked. First a total order on versions: parse into {major, minor, patch, pre[], build[]} and compare field by field, with special rules for the prerelease tail. Then a desugarer: every friendly range syntax — ^, ~, 1.2.x, 1.2.3 - 2.3.4, || — collapses into sets of plain >= / < comparators, and "does this version satisfy that range" becomes a loop over those comparators plus one extra rule about prereleases. Here it is, step by step.

    
    
      
  1. 
        
    1
    Parse strictly — the regex is only half the rules
    
        
    One regex splits the five parts, then hand-written checks enforce what a regex reads badly: numeric fields must not carry leading zeros (01 is not a number here), identifiers are limited to [0-9A-Za-z-], and empty identifiers (a double dot, a trailing dot) are illegal. Prerelease and build are kept as arrays of identifiers, never as one string, because every later rule works identifier by identifier.
    
        
    const NUMERIC = /^(0|[1-9]\d*)$/;      // no leading zeros
const IDENT   = /^[0-9A-Za-z-]+$/;      // the only legal charset

function parseSemver(text){
  const raw = String(text).trim();
  const m = raw.match(/^(\d+)\.(\d+)\.(\d+)(?:-([^+]*))?(?:\+(.*))?$/);
  if (!m) return { error: "expected major.minor.patch[-prerelease][+build]" };

  for (const [i, name] of [[1,"major"],[2,"minor"],[3,"patch"]])
    if (!NUMERIC.test(m[i])) return { error: name + " has a leading zero" };

  const pre   = m[4] === undefined ? [] : m[4].split(".");
  const build = m[5] === undefined ? [] : m[5].split(".");
  return { major:+m[1], minor:+m[2], patch:+m[3], pre, build };
}
    
      
    2. 
      
  2. 
        
    2
    Comparing one identifier: numbers first, then ASCII
    
        
    Spec §11.4: identifiers made only of digits compare numerically, identifiers with letters compare in ASCII order, and a numeric identifier always ranks lower than an alphanumeric one. Because leading zeros are already rejected, numeric comparison can be done without Number() at all — the longer digit string is the bigger number, and equal lengths compare lexically. That keeps it exact past 2⁵³.
    
        
    function cmpIdent(a, b){
  const an = NUMERIC.test(a), bn = NUMERIC.test(b);
  if (an && bn) {                                  // both numeric
    if (a.length !== b.length) return a.length < b.length ? -1 : 1;
    return a < b ? -1 : a > b ? 1 : 0;              // exact, no float
  }
  if (an) return -1;                                // numeric < alphanumeric
  if (bn) return 1;
  return a < b ? -1 : a > b ? 1 : 0;                // ASCII order
}

cmpIdent("11", "2");     //  1   eleven > two
cmpIdent("2", "beta");   // -1   numeric loses to alphanumeric
    
      
    3. 
      
  3. 
        
    3
    Comparing the prerelease tail
    
        
    Two rules that look backwards until you say them out loud. Having a prerelease makes a version smaller, because 1.0.0-rc.1 comes before the real 1.0.0. And when both have one, you walk identifier by identifier; if everything matches up to the length of the shorter, the longer one wins, because alpha.1 is a further step along than plain alpha.
    
        
    function cmpPre(a, b){
  if (!a.length && !b.length) return 0;
  if (!a.length) return 1;        // 1.0.0 > 1.0.0-alpha
  if (!b.length) return -1;
  const n = Math.min(a.length, b.length);
  for (let i = 0; i < n; i++) {
    const c = cmpIdent(a[i], b[i]);
    if (c !== 0) return c;
  }
  return a.length === b.length ? 0 : (a.length < b.length ? -1 : 1);
}

// alpha < alpha.1 < alpha.beta < beta < beta.2 < beta.11 < rc.1 < (none)
    
      
    4. 
      
  4. 
        
    4
    The whole comparator — and the field that is never read
    
        
    Major, then minor, then patch, then the prerelease tail. Build metadata is deliberately absent: the spec says it MUST be ignored when determining precedence, so 1.0.0+a and 1.0.0+b are equal. Pass this straight to Array.prototype.sort and you have a correct release history for free.
    
        
    function compareVer(a, b){
  if (a.major !== b.major) return a.major < b.major ? -1 : 1;
  if (a.minor !== b.minor) return a.minor < b.minor ? -1 : 1;
  if (a.patch !== b.patch) return a.patch < b.patch ? -1 : 1;
  return cmpPre(a.pre, b.pre);        // build[] is never looked at
}

const sorted = list.slice().sort(compareVer);
// 0.9.0, 0.10.0, 1.0.0-alpha, 1.0.0-alpha.1, 1.0.0-beta, 1.0.0-rc.1, 1.0.0
    
      
    5. 
      
  5. 
        
    5
    Partials: a range operand may be incomplete
    
        
    Inside a range, 1, 1.2, 1.2.x and * are all legal operands. Parse them into the same shape as a version but with null standing for "unspecified", and remember that once a field is x, everything to its right is x too. Every desugaring rule below is then just arithmetic on those three slots.
    
        
    function parsePartial(text){
  const s = text.trim().replace(/^[v=]+/, "");        // npm tolerates v1.2.3
  const m = s.match(/^(x|X|\*|\d+)(?:\.(x|X|\*|\d+)(?:\.(x|X|\*|\d+)(?:-([^+]*))?(?:\+(.*))?)?)?$/);
  if (!m) return null;
  const num = t => (t === undefined || t === "x" || t === "X" || t === "*") ? null : +t;
  let M = num(m[1]), mi = num(m[2]), p = num(m[3]);
  if (M === null) { mi = null; p = null; }             // x.2.3 is really x
  if (mi === null) p = null;
  return { M, m: mi, p, pre: m[4] ? m[4].split(".") : [] };
}
    
      
    6. 
      
  6. 
        
    6
    Caret and tilde are two lines of arithmetic
    
        
    Caret means "up to the next thing that is allowed to break", and below 1.0.0 the leftmost non-zero field is the breaking field — that single sentence generates all five caret cases. Tilde is simpler: it pins whatever you specified down to the minor and lets the patch float, so ~1.2.3 stops at 1.3.0 but ~1 stops at 2.0.0.
    
        
    function caretRange(q){                       // ^q
  const low = ge(q.M, q.m ?? 0, q.p ?? 0, q.p === null ? [] : q.pre);
  let hi;
  if (q.M > 0)           hi = lt(q.M + 1, 0, 0);   // ^1.2.3 -> <2.0.0
  else if (q.m === null) hi = lt(1, 0, 0);         // ^0.x   -> <1.0.0
  else if (q.m > 0)      hi = lt(0, q.m + 1, 0);   // ^0.2.3 -> <0.3.0
  else if (q.p === null) hi = lt(0, 1, 0);         // ^0.0.x -> <0.1.0
  else                   hi = lt(0, 0, q.p + 1);   // ^0.0.3 -> <0.0.4
  return [low, hi];
}

function tildeRange(q){                       // ~q
  const low = ge(q.M, q.m ?? 0, q.p ?? 0, q.p === null ? [] : q.pre);
  const hi  = q.m === null ? lt(q.M + 1, 0, 0)     // ~1     -> <2.0.0
                           : lt(q.M, q.m + 1, 0);  // ~1.2.3 -> <1.3.0
  return [low, hi];
}
    
      
    7. 
      
  7. 
        
    7
    X-ranges, hyphen ranges, and >1.2
    
        
    An x is a window, so the operator decides which edge of the window you land on: >1.2 means "past the whole 1.2 window", i.e. >=1.3.0, while <=1.2 means "through the end of it", i.e. <1.3.0. Hyphen ranges use the same idea on the right-hand side: 1.2.3 - 2.3 ends at <2.4.0, but a complete 2.3.4 ends at an inclusive <=2.3.4.
    
        
    function plainRange(op, q){
  if (q.m === null) {                                   // "1" / "1.x"
    if (op === "" || op === "=") return [ge(q.M,0,0), lt(q.M+1,0,0)];
    if (op === ">")  return [ge(q.M+1, 0, 0)];           // >1   -> >=2.0.0
    if (op === ">=") return [ge(q.M,   0, 0)];
    if (op === "<")  return [lt(q.M,   0, 0)];
    if (op === "<=") return [lt(q.M+1, 0, 0)];           // <=1  -> <2.0.0
  }
  if (q.p === null) { /* same five cases on the minor */ }
  return [{ op: op || "=", ver: mk(q.M, q.m, q.p, q.pre) }];
}

// 1.2.3 - 2.3.4  ->  >=1.2.3 <=2.3.4
// 1.2.3 - 2.3    ->  >=1.2.3 <2.4.0
// 1.2   - 2      ->  >=1.2.0 <3.0.0

  8. 
        
    8
    Evaluate: AND inside a row, OR across rows
    
        
    Split the whole range on || into rows, desugar each token in a row into comparators, and satisfaction is the obvious double loop. Then the one rule that is not obvious: a version with a prerelease is rejected unless some comparator in the same row names a prerelease on the identical major.minor.patch. That is what stops ^1.2.3 from quietly installing 1.3.0-beta.1.
    
        
    function testComparator(v, c){
  if (c.op === "*") return true;
  const r = compareVer(v, c.ver);
  return c.op === "="  ? r === 0 : c.op === ">"  ? r > 0
       : c.op === ">=" ? r >= 0 : c.op === "<"  ? r < 0
       : c.op === "<=" ? r <= 0 : false;
}

function satisfiesSet(v, comps, includePrerelease){
  if (!comps.every(c => testComparator(v, c))) return false;
  if (v.pre.length && !includePrerelease) {
    const named = comps.some(c => c.op !== "*" && c.ver.pre.length
      && c.ver.major === v.major && c.ver.minor === v.minor && c.ver.patch === v.patch);
    if (!named) return false;
  }
  return true;
}

const satisfies = (v, range) => range.sets.some(s => satisfiesSet(v, s));

  9. 
        
    9
    What npm install actually picks
    
        
    Given the registry's list of published versions and your range, the resolver takes the highest version that satisfies — maxSatisfying. Two functions you already wrote, composed: filter, then reduce with the comparator. This is also why an unlocked ^ can change what you get between two installs of the same package.json.
    
        
    function maxSatisfying(list, range, includePrerelease){
  let best = null;
  for (const v of list) {
    if (!satisfies(v, range, includePrerelease)) continue;
    if (best === null || compareVer(v, best) > 0) best = v;
  }
  return best;
}

// published: 1.2.3 1.2.4 1.3.0 1.3.0-rc.1 2.0.0
// "^1.2.3"  -> 1.3.0     (the rc is invisible, 2.0.0 is out of bounds)

  10. 
        
    10
    Bumping — then prove the whole thing
    
        
    A bump is not always "+1": bumping the patch of 1.2.3-rc.1 gives 1.2.3, because the prerelease was already aiming at that release. Finish with assertions — the §11 chain is the canonical one, and a total-order check over random triples catches any comparator that is subtly inconsistent.
    
        
    function inc(v, release, preid){
  switch (release) {
    case "patch": return v.pre.length ? mk(v.major, v.minor, v.patch)
                                      : mk(v.major, v.minor, v.patch + 1);
    case "minor": return (v.pre.length && v.patch === 0) ? mk(v.major, v.minor, 0)
                                                         : mk(v.major, v.minor + 1, 0);
    case "major": return (v.pre.length && v.minor === 0 && v.patch === 0)
                         ? mk(v.major, 0, 0) : mk(v.major + 1, 0, 0);
    case "premajor": return mk(v.major + 1, 0, 0, [preid, "0"]);
  }
}

const CHAIN = ["1.0.0-alpha","1.0.0-alpha.1","1.0.0-alpha.beta","1.0.0-beta",
               "1.0.0-beta.2","1.0.0-beta.11","1.0.0-rc.1","1.0.0"];
for (let i = 1; i < CHAIN.length; i++)
  console.assert(compareVer(parseSemver(CHAIN[i-1]), parseSemver(CHAIN[i])) < 0, CHAIN[i]);
