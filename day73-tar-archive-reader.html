📦 A real tar reader and writer — hand it a path and it tells you whether ustar can hold it, which clause decided, and what each of four readers would call the file. Everyone knows a tar path is capped somewhere near 255 bytes. Almost nobody knows the cap is not the rule. The 100-byte name field and the 155-byte prefix field are joined by a slash that is never stored, so what has to fit is not the path — it is the two halves either side of some slash. A 130-byte path with no slash after byte 100 is unstorable; a 256-byte path split 155/100 stores in a single block; and GNU tar 1.35's own error message says max 256, not 255. Over a 20,000-path corpus the “≤ 256” model is wrong 2,499 times — 34.83% of everything in the 101–256 band — always claiming storable when it is not, and 2,074 of those refused paths do contain a slash, so “has a slash” is not the rule either. 🔴 The inversion in the scoreboard: the wrong number scores better. “≤ 255” is wrong 2,486 times against 2,499 for the correct ceiling, purely because the 13 paths of exactly 256 bytes in this corpus all happen to be unsplittable. 🔴 And a refused name is not a refused archive. GNU tar reaches for the prefix field only under --format=ustar: in its own gnu and posix formats the same 140-byte path becomes three blocks with a truncated 100-byte twin left in the name field, so one archive presents two different file lists and a reader that does not speak the extension writes a real file at a real, different path — no error on either side. Every verdict here is checked against the real thing: GNU tar 1.35 and Python 3.11 tarfile, in both directions, and they disagree with each other on eight live cells — one trailing slash, four ways of spelling a number, two off-by-one length fields and six missing magic bytes — every one of them producing a different answer rather than an error. The loudest: put an ASCII + in front of the size and the same twelve bytes mean 10 bytes to Python and 951,617,749,834,222,966 to GNU tar, which reads the sign as the 1990s base-64 header format and lists the member anyway. THE NUMERIC FIELDS

Twelve bytes of octal ASCII — eleven digits and a terminator — which is why the classic tar size ceiling is exactly 8 GiB − 1. Above it GNU tar sets the top bit of the first byte and the field becomes big-endian binary.

…AND WHAT THE TWO REFERENCES DO WITH THEM

Python parses the field with int(s, 8), which accepts a leading ASCII minus. GNU tar reads a leading minus as the 1990s base-64 header format and refuses the archive. One byte, two grammars.

PAX RECORDS: A LENGTH THAT COUNTS ITSELF

A pax extended header is a run of %d %s=%s\n records where the leading decimal is the length of the whole record including its own digits. The length, not the newline, ends the record — so a value may legally contain newlines and equals signs, and a line-splitting parser is wrong on both. And because the length counts itself, some bodies have two self-consistent lengths.

1. A tar file is a list of 512-byte blocks and nothing else

There is no index, no directory, no table of contents and no compression. An archive is a stream: a 512-byte header block, then the file's bytes rounded up to a multiple of 512, then the next header, and so on, until two blocks of zeros. That is the entire container format, and it explains almost every surprise on this page.

Because there is no index, a reader cannot know what is in an archive without walking every block, and it cannot check anything about a member until it has already passed the previous one. Because there is no table of contents, appending is trivial — overwrite the zero blocks and keep writing — which is why the same name can appear twice. And because the header is a fixed 512 bytes, every string in it has a hard length, which is where the story starts.

The one number to keep. 512. Header blocks, data padding, the end marker, the checksum window — all of it is arithmetic on 512.

2. The name field is 100 bytes, and that was never enough

Version 7 Unix gave the path 100 bytes at offset 0, and required a NUL terminator, so the real limit was 99. By 1988 that was already painful, and POSIX.1-1988 added a second field: 155 bytes at offset 345, called prefix. The full path is prefix, then a slash, then name.

That slash is the whole trick, and the whole trap. It is not stored anywhere. It exists only in the reader's join. Which means a writer cannot put a path into the two fields unless the path already has a slash at a position where both halves fit — the tail in 100 bytes, the head in 155.

So the storable set is not an interval. It is a condition on slash positions. Written out: a path of length L is storable in ustar exactly when L ≤ 100, or when some slash sits at an index i with i ≤ 155 and L − i − 1 ≤ 100. Everything else on this page follows from that one line.

Why 256 and not 255. Both fields can be completely full — a field that fills its width needs no NUL terminator. 155 + 100 = 255 stored bytes, plus the slash the reader puts back = 256. GNU tar says so itself: file name is too long (max 256).

3. The two refusals are different, and only one of them is about length

Ask GNU tar to store a 257-byte path and it says file name is too long (max 256). Ask it to store a 130-byte path with no slash after byte 100 and it says something else entirely: file name is too long (cannot be split). Two messages, two gates, and the second one fires on paths that are less than half the stated maximum.

This is why the mental model survives. The length gate matches what everyone believes, and it is real. The split gate is invisible unless you happen to generate a long single component — a hash, a base64 blob, a generated identifier, a minified bundle name — which is exactly the sort of filename that shows up in a build directory and nowhere in a test suite.

4. The scoreboard, and the wrong number that wins

Four models, 20,000 paths, scored against the real split rule. The “≤ 100” model is wrong 4,675 times and always pessimistically. The “≤ 256” model is wrong 2,499 times and always optimistically — it promises storage that does not exist, which is the direction that loses data.

And then the result that should not be comfortable: the model holding the wrong ceiling, “≤ 255”, scores better, 2,486 against 2,499. The two models can only differ on paths of exactly 256 bytes, there are 13 of those in the corpus, and all 13 happen to be unsplittable — so refusing them for the wrong reason is right by accident. A benchmark can rank a false belief above a true one and the margin can look like signal.

The fourth model is the one people reach for once they have been bitten: “≤ 256 and it must contain a slash”. It is worse than both, wrong 5,651 times, because it breaks the 11,761 short paths that need no slash at all. A repair aimed at the failing band is free to destroy the band that was already correct.

5. Two writers, one path, different bytes

GNU tar scans backward from byte 155 looking for a slash, so it takes the longest prefix that fits. Python's tarfile walks the path components forward and takes the first split that works, so it takes the shortest prefix that fits. Over the same 20,000 paths the two never disagree about whether a path is storable — 0 disagreements — and they lay the bytes out differently on 2,657 of the 16,436 storable ones, 16.17%.

Both archives are correct. Both round-trip. They are not the same file. So byte-comparing two tarballs of the same tree tells you which tool made them, not whether they contain the same thing — and any build step that checksums a tarball to prove reproducibility is checksumming a choice of split.

6. A refused name is not a refused archive

When a path does not fit, tar does not stop. It reaches for an extension: GNU's 'L' block, which carries the real name as the data of a fake member called ././@LongLink, or pax's 'x' block, which carries it as a keyword record. Either way a reader that does not understand that typeflag sees an ordinary member with a strange name, and then sees the real member with whatever the writer left in the 100-byte name field.

What GNU tar leaves there is the path, truncated to 100 bytes. Not blank, not a placeholder — a plausible relative path that an extractor will create. So one archive has two file lists: the pax-aware list, and the truncated list. Neither reader reports an error, because from each one's point of view nothing is wrong.

The sharpest version of this is not about long paths at all. The 140-byte fixture on the READ tab fits perfectly into prefix + name — one block, no extension, fully losslessly — and GNU tar still writes three blocks and a truncated twin, because it only consults the prefix field under --format=ustar. The divergence is created by a flag, not by the path.

And the truncated twin is not even one path. GNU tar's two long-name formats disagree with each other by a byte: --format=oldgnu leaves 99 bytes in the name field because the pre-1.12 header NUL-terminates it, while --format=gnu and --format=posix leave a full 100. Same tar, same path, three blocks either way, and three different answers to “what will a ustar-only reader write to disk”.

Read that as an operational fact. “My scanner listed the archive and the paths looked fine” and “the extractor wrote these files” are two different questions, and a tar archive is allowed to answer them differently.

7. Directory-ness has two sources, and the references disagree on one cell

A member is a directory if its typeflag is '5'. It is also a directory, in practice, if its name ends in a slash — because v7 tar had no typeflag for directories and stored them as ordinary entries with a trailing slash. Every modern reader still honours that, which makes the answer depend on the last character of one field and the value of another.

And here the two references part company. Python promotes only typeflag NUL. GNU tar promotes NUL and '0'. Since NUL and '0' are documented as the same type — AREGTYPE and REGTYPE, both “regular file” — the same 512 bytes are a directory to tar and a regular file named foo/ to Python. Exactly one of the fourteen cells in the grid, and no error on either side.

The other five typeflags are not promoted by either: a symlink whose name ends in a slash stays a symlink in both. So the disagreement is not a general leniency difference. It is one entry in one list.

8. The checksum, and what it does not cover

The checksum is the sum of the 512 header bytes with its own eight bytes read as ASCII spaces. Simple, and famously ambiguous: the original implementations summed char, which on most compilers is signed. So a header containing any byte ≥ 0x80 has two correct sums, 256 apart per high byte, and every reader accepts either.

This is not a museum piece. A filename with an accent has four high bytes and two valid checksums 1,024 apart; a Devanagari filename here has fifteen and a gap of 3,840. And any file of 8 GiB or more forces the size field into base-256, whose first byte is 0x80 by definition — so every large-file archive carries the ambiguity structurally.

More important than the ambiguity is the scope. The checksum covers the header. It does not cover one byte of file content. Flip a byte inside a member's data and every tar in the world will extract it, silently, and report success. tar has no integrity check on the thing it exists to carry.

9. pax: a length field that counts itself

POSIX.1-2001 fixed the field-width problem properly by moving metadata into text records: %d %s=%s\n, where the decimal is the length of the whole record including the digits of the length. That self-reference is elegant — a parser needs no lookahead — and it has two consequences nobody expects.

First, a writer has to solve for the length, because adding a digit to it changes it. Both references run the same fixpoint. Second, at each decimal boundary the fixpoint has two answers: a body of 96 bytes is a legal record at length 99 (two digits) and equally legal at length 100 (three digits). Below 4,000 there are exactly three such bodies — at 9/10, 99/100 and 999/1000 — one per digit boundary and nothing in between.

And then the failure mode. Get the length wrong by one byte and GNU tar refuses the extended header and falls back to the ustar name. Python does not check: it slices value = buf[keyEnd+1 : start+length-1], assuming the byte it drops is the newline. One short, and the filename silently loses its last character. One long, and the filename silently gains a newline. Same archive, two different files on disk, no error anywhere.

10. Where the value actually comes from

By the time a pax reader has a member, the same field may have been set three times: by the ustar header, by a global 'g' record seen earlier in the stream, and by the per-file 'x' record immediately before it. The order is header, then global, then per-file — so a global record written once at the top of an archive silently overrides a value present in every single header after it, and a field with no record keeps its header value.

Both references agree on all five rows of that ladder, which is worth stating plainly: the pax precedence rules are one of the few parts of this format where nothing disagrees. The disagreements are all in the layers below — the fields, the typeflags and the numbers.

One more field is gated rather than read: uname and gname only exist from POSIX.1-1988 onward, so GNU tar consults them only when the six magic bytes at offset 257 spell ustar. Put a v7 header in front of it with uname=root written in and it reports 0/0 — the string is present, in the right place, and ignored. Python reads it regardless. The engine here follows GNU tar, and the difference is one more cell where the same bytes have two answers.

11. What did not survive building this

  • “255 bytes” was wrong, and the reference said so in an error message. The number is 256, because the joining slash is not stored. The correction came from tar's own text, not from reading the standard.
  • “≤ 256 is a safe over-approximation” was wrong in the dangerous direction. It is wrong 2,499 times out of 20,000, and every single error is a false yes.
  • The intended headline was “the correct model beats the folk model”, and the measurement refused it. “≤ 255” scores better than “≤ 256” on this corpus. The page teaches the artefact instead of the recommendation, because that is what the numbers said.
  • A first version of the pax parser was a single function that validated the trailing newline. That is GNU tar. It is not Python, and modelling only one of them made the whole off-by-one finding invisible — the interesting cell is precisely where the two parsers differ, so the engine now carries both.
  • The base-256 reader was quietly lying about −1. Computing the two's complement as -(256^11 - v) loses to double precision: the answer came back 0. Complementing each byte instead gives exactly −1. The magnitude is still only exact below 253, and the engine now reports that rather than pretending.
  • A first pass wrote real NUL bytes into the source to spell the AREGTYPE typeflag. A NUL in an HTML file is a parser hazard; the engine now spells it String.fromCharCode(0) and the verifier asserts the page carries none.
What survived, and is worth carrying. Whether a path fits in a tar header is not a property of the path's length. It is decided by where its slashes are, by which --format flag the writer was given, by the last character of an unrelated field, and by whether the reader happens to understand a typeflag it has never seen. Four positional facts, none of them about how long the name is.

1. The split, which is the whole page

function splitGnu(path) {
  var L = utf8Encode(path).length, i, lim;
  if (L > 256) return { ok:false, why:"max 256" };      // 155 + 1 + 100
  if (L <= 100) return { ok:true, prefix:"", name:path };
  lim = L;
  if (lim > 156) lim = 156;                              // PREFIX_FIELD_SIZE + 1
  else if (path.charAt(lim - 1) === "/") lim--;           // a directory's own slash
  for (i = lim - 1; i > 0; i--) if (path.charAt(i) === "/") break;
  if (i === 0) return { ok:false, why:"cannot be split" };   // <- the invisible gate
  ...
}

The loop is the specification. Nothing in it compares L to 255, and nothing in it looks at the path's total length after the first line — from there on the only question is where the slashes are. Python's version walks the components forward instead and reaches the same yes/no on every path tried here, with a different answer for the bytes.

2. The checksum, and the eight bytes that are not there

function checksums(b, off) {
  var u = 0, s = 0, i, v;
  for (i = 0; i < 512; i++) {
    v = (i >= 148 && i < 156) ? 32 : b[off + i];   // its own field reads as spaces
    u += v;
    s += v > 127 ? v - 256 : v;                     // ...and again, as signed chars
  }
  return { unsigned:u, signed:s };
}

Two accumulators over one pass. They are equal exactly when no byte of the header exceeds 0x7f, so the ambiguity is a property of the filename's encoding and the file's size, not of the writer's care.

Change P.pax to false and the two continue statements stop firing: the extension headers become ordinary members and the real member keeps its truncated name. That one flag is the difference between the two file lists, and it is the whole of the “ustar-only reader” profile.

5. Verify it against the real thing

Nothing here has to be taken on trust. Two reference implementations ship on almost every machine, and both directions are checkable:

python -c "import tarfile;b=open('p.tar','rb').read();\
print(tarfile.TarInfo.frombuf(b[512:1024],'utf-8','strict').name)"   # the truncated twin

6. If you are writing tar-handling code

  • Never validate a path against a length. Ask whether a slash exists in the window, or just call the split and look at the answer. A length check is wrong in the direction that loses files.
  • Do not assume the listing is the extraction. Duplicate names are legal and the last wins, so build the plan before you trust the list — and remember an archive can be two archives concatenated, with the second half invisible without --ignore-zeros.
  • Decide what your reader is before you write it. If it does not implement 'x', 'g', 'L' and 'K', it will see extra members with placeholder names and truncated real ones. That is not a bug you can fix by being careful with the name field.
  • Accept both checksums. Any reader that only accepts the unsigned sum will reject real archives, including every one produced by a historic tar with a non-ASCII filename.
  • Do not treat a tar checksum as integrity. It covers the headers. Sign or hash the archive if you need to know the contents are intact.
  • Do not compare two tarballs byte for byte to decide whether two trees match. The prefix split is a writer's choice and two correct writers make two different files.
