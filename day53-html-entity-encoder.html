SolveFromZero · Day 53

& HTML Entity Encoder / Decoder — a genuinely two-way tool: type raw text on the left and it escapes the characters that would break HTML into entities on the right (&amp; &lt; &gt; &quot; &#39;), or paste entities on the right and it decodes them back to text on the left · toggle named vs numeric references (&copy; vs &#169; vs &#xA9;), only-unsafe vs encode-everything (push every non-ASCII character to numeric/named entities for a pure-ASCII payload), and decimal vs hex · decoding parses a built-in named table plus numeric &#nnn; / &#xhh; by real Unicode code point (emoji included) · live as you type, copy either side · distinct from URL-encoding and Base64 · vanilla JS, no library

Five characters can hijack your markup — entities defuse them.

HTML has exactly five characters that mean something to the parser: & starts a reference, < and > delimit tags, and "/' delimit attribute values. If any of those appear literally in text you did not intend as markup, the page breaks — or worse, someone injects a <script>. The fix is a character reference (an "entity"): a stand-in that starts with & and ends with ;, either named (&amp;) or numeric by Unicode code point in decimal (&#38;) or hex (&#x26;). This tool does both directions from scratch, no library: encoding iterates the string by code point (so emoji stay whole) and swaps each character that needs escaping; decoding runs one regular expression that recognises named, decimal and hex references and turns them back into characters via String.fromCodePoint. Edit either box and the other updates live. This is not URL-encoding (%20) and not Base64 — it is specifically the HTML text/attribute escaping layer.

Five things people get wrong about HTML entities

1. Escape & first, or you double-encode. If you replace < before &, then re-run the encoder, an already-escaped &amp; becomes &amp;amp;. Iterating character-by-character (as this tool does) sidesteps the ordering trap entirely — each source character is looked at exactly once. 2. &apos; is HTML5-only. The named apostrophe was not defined in HTML4, so for maximum compatibility the numeric &#39; is the safe choice; most real escapers emit &#39; even in "named" mode. 3. Context decides what is dangerous. A " is harmless in text but ends an attribute; a > is fine inside an attribute but should be escaped in text. Escaping for the wrong context either over-encodes or leaves a hole — which is why frameworks have separate text vs attribute escapers. 4. Entities are not sanitization. They neutralise markup in an HTML text/attribute context, but they do nothing for a javascript: URL, an unquoted attribute, or a value interpolated into inline JS/CSS — those need their own escaping or an allow-list. 5. Numeric references are Unicode code points, not bytes. &#233; is always é regardless of the page's charset, and an emoji is one code point (&#x1F680;) — never two surrogate halves. That is why the encoder walks the string with a code-point iterator, not by charCodeAt.

🔨 Build it yourself

    
An HTML-entity codec is two small functions over one shared table. Encoding walks the string one code point at a time and, for each character that must (or you chose to) escape, emits either a named reference from a lookup or a numeric &#…;. Decoding is a single regular expression that matches &name;, &#123; and &#x1F;, and a replace callback that turns each back into a character — named via the reverse table, numeric via String.fromCodePoint. The only real subtleties are iterating by code point so emoji survive, escaping & implicitly-first by never looking at a character twice, and guarding the numeric range on decode. No parser, no dependency — under 100 lines of logic. Here it is, step by step.

    
    
      
  1. 
        
    1
    One table, both directions
    
        
    Store the named references once as name → character (that is what decoding needs), then derive the reverse character → name for encoding. Deriving it — instead of hand-writing two tables — guarantees they never drift apart, and "first name wins" keeps the canonical short names (amp, not some alias) for the core characters you list first.
    
        
    const NAMED = {                 // name -> character  (decode source of truth)
  amp:"&", lt:"<", gt:">", quot:'"', apos:"'",
  nbsp:" ", copy:"©", reg:"®", trade:"™",
  eacute:"é", mdash:"—", euro:"€" /* ...~100 more... */
};
const TO_NAME = {};             // character -> name  (encode, first wins)
for (const n in NAMED){ const c = NAMED[n]; if (TO_NAME[c] === undefined) TO_NAME[c] = n; }
    
      
    2. 
      
  2. 
        
    2
    The five characters that must be escaped
    
        
    Only five characters carry meaning to the HTML parser. Everything else is optional. Keep them in a set so the encoder can ask, in O(1), "is this one of the dangerous ones?" — that membership test is the whole decision in "only-unsafe" mode.
    
        
    // & opens a reference · < > delimit tags · " ' delimit attributes
const CORE = { "&":1, "<":1, ">":1, '"':1, "'":1 };
const isUnsafe = ch => CORE[ch] === 1;
    
      
    3. 
      
  3. 
        
    3
    Encode: iterate by code point
    
        
    for (const ch of text) yields whole code points — an emoji comes out as one ch, not two broken surrogate halves. For each one decide whether to escape: always if it is unsafe, and additionally (in "encode everything" mode) if it is non-ASCII (code point > 127). Untouched characters are copied straight through.
    
        
    function encode(text, opts){
  let out = "";
  for (const ch of text){                     // code-point iteration
    const cp = ch.codePointAt(0);
    const escape = isUnsafe(ch) || (opts.scope === "all" && cp > 0x7F);
    out += escape ? toEntity(ch, cp, opts) : ch;
  }
  return out;
}
    
      
    4. 
      
  4. 
        
    4
    Named vs numeric, decimal vs hex
    
        
    Building the entity string is a two-way branch: prefer a named reference if the user chose "named" and one exists for this character; otherwise fall back to a numeric reference in the chosen radix. Hex references are written &#x…; with the code point in base 16; decimal is just the number.
    
        
    function toEntity(ch, cp, opts){
  if (opts.mode === "named" && TO_NAME[ch] !== undefined)
    return "&" + TO_NAME[ch] + ";";                 // &copy;
  return opts.radix === "hex"
    ? "&#x" + cp.toString(16) + ";"                 // &#xA9;
    : "&#"  + cp + ";";                             // &#169;
}
    
      
    5. 
      
  5. 
        
    5
    Why & is safe without ordering tricks
    
        
    The classic bug is replacing < before & with chained .replace() calls, so a real & in the input gets turned into &amp; and then its own & gets escaped again. Because this encoder reads each source character exactly once and writes its finished entity, the ampersand of an entity it just produced is never re-examined. No ordering, no double-encoding.
    
        
    // ❌ the trap: chained replaces re-process the & you just wrote
s = s.replace(/</g,"&lt;").replace(/&/g,"&amp;");  // "<" -> "&amp;lt;"  (wrong)
// ✅ single pass: each input char -> one output token, never revisited
for (const ch of text) out += isUnsafe(ch) ? toEntity(ch, ...) : ch;
    
      
    6. 
      
  6. 
        
    6
    Decode: one regex for all three forms
    
        
    A character reference is always &, a body, then ;. The body is one of three shapes: # + digits (decimal), #x + hex digits, or letters (a name). One alternation captures the body; a replace callback decides what to do with each match. Anything that does not match the pattern is left exactly as-is.
    
        
    //            decimal        hex             named
const ENT = /&(#[0-9]+|#[xX][0-9a-fA-F]+|[a-zA-Z][a-zA-Z0-9]*);/g;
function decode(text){
  return text.replace(ENT, (m, body) => fromEntity(m, body));
}
    
      
    7. 
      
  7. 
        
    7
    Numeric decode — parse, range-check, fromCodePoint
    
        
    If the body starts with #, read the number — base 16 when the next char is x/X, else base 10 — and turn the code point into a character with String.fromCodePoint, which correctly produces astral characters (emoji) as a surrogate pair. Guard the range 0…0x10FFFF; an out-of-range or malformed value is left as literal text rather than throwing.
    
        
    function fromEntity(m, body){
  if (body[0] === "#"){
    const hex = body[1] === "x" || body[1] === "X";
    const cp  = parseInt(body.slice(hex ? 2 : 1), hex ? 16 : 10);
    if (!(cp >= 0 && cp <= 0x10FFFF)) return m;      // invalid -> leave alone
    try { return String.fromCodePoint(cp); } catch (e){ return m; }
  }
  return NAMED[body] !== undefined ? NAMED[body] : m;   // named (next step)
}
    
      
    8. 
      
  8. 
        
    8
    Named decode — look up, or leave verbatim
    
        
    A named body is a straight lookup in the same NAMED table. The important behaviour is the miss: an unknown name like &widget; is not an error and must be returned unchanged — turning it into a "?" would silently corrupt text. Returning the original match m makes decode a safe no-op on anything it does not recognise.
    
        
    // inside fromEntity, the non-numeric branch:
const ch = NAMED[body];
return ch !== undefined ? ch : m;   // &copy; -> ©   ·   &widget; -> &widget;

  9. 
        
    9
    Wire it live — two boxes, two events
    
        
    Bind an input listener to each textarea. Typing in the raw box encodes into the entities box; typing in the entities box decodes into the raw box. Because each direction reads one box and writes the other, there is no feedback loop — the box you are typing in is never overwritten while you hold focus.
    
        
    rawBox.addEventListener("input", () => { entBox.value = encode(rawBox.value, OPT); });
entBox.addEventListener("input", () => { rawBox.value = decode(entBox.value); });
// changing an encode option just re-runs the encode direction:
[modeBtns, scopeBtns, radixBtns].forEach(bindOption(() => {
  entBox.value = encode(rawBox.value, OPT);
}));
    
      
    10. 
      
  10. 
        
    10
    The round-trip guarantee
    
        
    A correct codec satisfies decode(encode(x)) === x for every string. It holds here because every entity the encoder can emit — named from TO_NAME or numeric in either radix — is something the decoder recognises and maps back to the same code point. Test it on a deliberately nasty string and you should get the original back, byte for byte.
    
        
    const x = '<b>café & "quotes"</b>';
const round = decode(encode(x, { mode:"named", scope:"all", radix:"hex" }));
console.assert(round === x, "round-trip must be lossless");   // ✓

🎉 Day 53 of SolveFromZero.
You built a real, lossless HTML-entity codec with no library. The whole thing rests on two ideas: encode by walking the string one code point at a time and swapping each character that needs escaping for a named or numeric reference, and decode with a single regex that recognises named, decimal and hex references and maps each back through the same table (or String.fromCodePoint). Because you read each source character exactly once you never double-encode the ampersand, and because you iterate by code point emoji survive intact. That same shape is what textContent-based escapers and framework auto-escapers do under the hood — reach for it any time untrusted text has to land inside HTML.
