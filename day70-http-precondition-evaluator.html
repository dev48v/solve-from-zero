🎯 HTTP conditional-request & byte-range evaluator — a real RFC 9110 §13.2.2 engine. Give it a resource and the six conditional fields and it returns the exact status your origin will produce, naming the rule that decided it and showing which present headers were never even consulted. The trap at the centre is not a token that means two things — it is a token that means nothing at all by itself: W/"abc" against a strong "abc" is a 304 in If-None-Match, a 412 in If-Match, a 200 in If-Range, a 200 in If-None-Match on a POST, and a 206 in If-None-Match on a GET that merely also carries a Range field. Four different status codes, one unchanged token, and nothing about the tag decides — the header, the method and an unrelated neighbour do. 79 reference cases, and the engine is checked against a live Apache httpd 2.4.41 over 3,750 real requests with zero status disagreements, 341 Content-Range strings and 176 response bodies byte-identical. The model everybody writes — evaluate every conditional and AND the results — is exactly right on all 7,680 grid cells where no header is muzzled and wrong on 22.50% of the 3,840 where one is, which is precisely why it survives every test suite. THE FIVE PLACES ONE TOKEN CAN SIT

A representation whose current validator is the strong tag "abc123". In every row below the client sends the weak spelling of that same tag — W/"abc123" — unchanged, byte for byte. Nothing about the token varies down the column.

A conditional request is not a set of tests. It is a walk.

Six fields can appear on one request: If-Match, If-Unmodified-Since, If-None-Match, If-Modified-Since, Range and If-Range. The obvious implementation reads each one, decides whether it passes, and combines the answers. That is wrong, and it is wrong in a way no ordinary test can see.

RFC 9110 §13.2.2 lays the six out in a fixed order with two else branches in it. Step 2 is only reached when If-Match is absent. Step 4 is only reached when If-None-Match is absent. So a header that is present, well formed, and would have failed is never consulted, and the response is the one it would have prevented. Presence, not value, is what silences it — an If-None-Match holding pure garbage still silences If-Modified-Since.

The rule to internalise. Entity tags outrank dates, always, and the outranking is total: the date is not a tie-breaker, a fallback, or a second opinion. If a tag field is present its date partner might as well not have been sent.

THE WALK, WRITTEN OUT

Pricing the model everyone writes

Below, the whole cross-product of five methods × eight If-Match values × eight If-None-Match values × six If-Unmodified-Since values × six If-Modified-Since values, plus a separate range grid. Each candidate implementation is a defensible reading of the same words; the column is how often it returns a different status code from RFC 9110.

The reason the AND model ships. Split the same grid by whether a muzzle actually fired and it stops looking like a 7% bug. A test suite that sends one conditional header at a time cannot distinguish the two implementations at all, and one conditional header at a time is exactly how conditional requests are tested.

Two comparison functions, and the tag does not choose

RFC 9110 §8.8.3.2 defines strong comparison (neither side may be weak, and the opaque parts match) and weak comparison (the opaque parts match, and W/ is stripped from both sides). Which one runs is a property of the field: strong for If-Match and If-Range, weak for If-None-Match. Then two widely deployed readings narrow the weak one further, and both are switched by something outside the header.

The consequence is that W/"abc" has no verdict of its own. Move it between fields and the status changes; leave it where it is and change the method and the status changes; leave both alone and add an unrelated Range field and the status changes again.

The identical malformation, two opposite verdicts. A field value that holds no valid entity-tag at all matches nothing. In If-Match — “does any listed tag match?” — that answer is no, the condition fails, and the request is refused with 412. In If-None-Match the same answer is the condition succeeding, and the request proceeds untouched. Same bytes, same parser, opposite outcome, decided only by which field name precedes the colon.

AND * IS INVERTED THE SAME WAY

If-Match: * means “only if it exists”. If-None-Match: * means “only if it does not”. The second is how you create a resource without overwriting one, and the first is how you overwrite one without creating it.

Range has two failure modes and they go in opposite directions

A Range field the server cannot honour has two entirely different fates. An invalid one — bad syntax, a last-byte-pos below its first-byte-pos, an unknown unit — is ignored: the field vanishes and the client receives 200 with the whole representation. A valid but unsatisfiable one — correct syntax, every offset past the end — is 416, and the client receives nothing. The natural implementation collapses the two into one error path.

AND THE PART COUNT IS NOT THE RANGE COUNT

§14.2 permits an origin to coalesce ranges that overlap or sit close together. Touching ranges therefore fuse: bytes=0-9,10-19,20-29 is three specifications and one part, returned with a plain Content-Range and no multipart wrapper at all. A client that counts commas to decide how to parse the body is wrong before it starts. Ranges are also emitted in request order, not ascending — ask for bytes=20-29,0-9 and the second part of the body is the first part of the file.

The date is three grammars and a sliding window

§5.6.7 obliges a recipient to accept three formats. A server may only send the first. The second carries a two-digit year, and the disambiguation is not “assume 19xx” — it is a fifty-year window anchored on the reader's own clock, so the same nine characters denote different years depending on when they are read.

One date comparison in HTTP is an equality. If-Modified-Since and If-Unmodified-Since are inequalities against Last-Modified. If-Range with a date is an exact match: not “no newer than”, exactly equal. And HTTP-date has one-second resolution while a filesystem timestamp does not, so

The one that will cost you money.

AND THE VALIDATOR IS A FUNCTION OF THE CLOCK

Apache emits W/"..." instead of "..." for a representation modified within the last second, because a second is the resolution of the Last-Modified it is about to send and it cannot promise that a second request inside that window sees the same bytes. Both range gates use strong comparison, so for exactly one second after a file changes, no download can be resumed — the same request that returns 206 at 1,000 ms returns 200 and the entire body at 999.

Where the revisions disagree

The ordered walk is not in RFC 2616 at all — it first appears in RFC 7232 §6 (2014) and carries into RFC 9110 §13.2.2 (2022). RFC 2616 also declared an If-Modified-Since later than the server's own clock to be invalid, a sentence the later texts deleted. Both differences are invisible on a request carrying one conditional header and appear only when two collide.

Four things I had backwards

  • I modelled an unparseable If-Match as “ignore the field”. Apache returned 412 on every one of them and Apache is right: the field asks whether any listed tag matches, and a list containing no valid tag answers no. My reading turned a refusal into a success on 218 of the first 1,708 differential cases.
  • I assumed the precedence muzzle was about validity. It is about presence. An If-None-Match holding literal garbage silences If-Modified-Since just as effectively as a well-formed one, in the specification and in the server, and clearing the presence flag on a parse failure cost me eight more disagreements.
  • I expected the range-count cap to count the ranges in the field. It counts the ranges that survive clipping to the current length, so one unchanged Range header is over the cap on a long representation and under it on a short one. Nine cases, all on the 333-byte fixture.
  • I read “a suffix-length of 0” and “an empty list element” as the same kind of malformation. They are not: §5.6.1 explicitly requires a recipient to parse and ignore empty elements, so bytes=0-9,,20-29 is a perfectly good two-range request, while bytes=-0 selects nothing and takes the whole field down with it.
  • My first coalesce was wrong, and only the oracle could see it. It merged each new interval into the first part it overlapped and stopped — which is right until one open-ended range bridges two parts that were not touching each other, and then it emits two adjacent parts that should have been one. The live server agreed with me on every request in the differential sweep, because nothing a real client sends has that shape. The byte-marking oracle disagreed on the first few hundred fuzzed fields. Merging now runs to a fixpoint.
  • I asserted that the fifty-year window always lands on the most recent year with those digits, and it does not. The rule in §5.6.7 is one-directional: start in the reader's own century and step back while the result is more than fifty years ahead. It never steps forward. So a 1999-era recipient reads 06-Nov-00 as 1900, not 2000 — the clause that fixed Y2K for HTTP dates cannot rescue a date that already lands in the past, which is the Y2K bug itself, preserved in the grammar. My assertion failed on 21 of the 100 two-digit years at that reader year, and the engine was right.

Building it

Roughly 400 lines with no dependencies and no Date object anywhere. The design decision that makes the rest fall out: the walk is written as a walk, with the two else branches expressed as branches, and every step pushes a record onto a trace rather than returning a bare boolean. That is what makes “which rule decided this” answerable, and it is also what makes the muzzle visible instead of implicit.

1. Two comparison functions, four lines

// RFC 9110 8.8.3.2 -- strong: NEITHER side may be weak, and the opaque parts match.
function strongCompare(a, b) { return !a.weak && !b.weak && a.opaque === b.opaque; }
// weak: the opaque parts match; the W/ prefix is stripped from BOTH sides.
function weakCompare(a, b)   { return a.opaque === b.opaque; }

Note what strongCompare says about a weak tag compared with itself: it does not match. That is not a bug to be smoothed over, it is the definition. A weak validator asserts semantic equivalence, and no amount of equivalence licenses splicing two byte streams together, so the two fields that decide whether bytes may be spliced — If-Match and If-Range — refuse it.

2. The walk, and the two elses

// step 1 : If-Match
if (im.present) { ...; if (!hit) return done(412, ...); }

// step 2 : If-Unmodified-Since -- ONLY when If-Match is absent
if (typeof iusRaw === 'string') {
  if (P.precedence === true && im.present) {
    step(2, { verdict: 'not consulted', muzzled: true });   // never parsed
  } else { ... }
}

// step 3 : If-None-Match
// step 4 : If-Modified-Since -- ONLY when If-None-Match is absent
//          and the gate is inm.present, NOT inm.ok

Writing muzzled: true into the trace instead of simply skipping the step is what lets the page count 3,840 muzzled cells and the 864 where the naive reading diverges. A branch that produces no record cannot be measured, and the whole point of this page is that the difference between the two implementations is unmeasurable by ordinary means.

3. Invalid is not unsatisfiable

if (!rg.valid)       return done(200, 'Range field invalid, therefore ignored', ...);
if (!rg.satisfiable) return done(416, 'Range valid but unsatisfiable', ...,
                                 { 'Content-Range': 'bytes */' + res.length });

Two lines, adjacent, and opposite. The invariant that keeps them apart lives inside parseRange: any syntax problem returns valid:false immediately, before a single offset is compared against the length, so validity is decided without ever looking at the resource. Satisfiability is the only question that needs to know how long the file is. Once those two are separated the 200-versus-416 split writes itself; fuse them and no test involving a well-formed range will ever notice.

4. Coalescing preserves order, which is the part that surprises

for (var i = 0; i < sats.length; i++) {
  var r = { first: ..., last: ... }, merged = false;
  for (var j = 0; j < out.length; j++) {
    if (r.first <= out[j].last + 1 + g && out[j].first <= r.last + 1 + g) {
      out[j].first = Math.min(out[j].first, r.first);
      out[j].last  = Math.max(out[j].last,  r.last);
      merged = true; break;
    }
  }
  if (!merged) out.push(r);              // appended, never sorted
}

The + 1 is the adjacency: 0-9 and 10-19 touch, so they merge. The measured gap tolerance on this machine is exactly zero — one byte of space between two ranges and they stay separate parts — and the merge writes into the earlier slot, which is what keeps request order. Sorting here would be a one-word change and would silently corrupt every client that reassembles by arrival.
