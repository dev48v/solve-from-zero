🛡️ Content-Security-Policy evaluator — a real CSP engine, not a linter. Paste a policy and a resource load, and it answers the only question that matters: does the browser fetch this? Source-list matching is fiddlier than it reads — a scheme-only source matches everything on that scheme, * deliberately does not cover data: or blob:, a host source with no scheme inherits the document's and then upgrades http→https but never the reverse, and *.example.com matches a subdomain but not example.com itself. Then the two clauses that decide whether a policy is real security or decoration: 'unsafe-inline' is ignored when a nonce or hash is present — by design, so you can ship a fallback for old browsers — and 'strict-dynamic' throws away your entire host allowlist — and 'self' with it, which is the one my first implementation kept and the tests caught. Directive fallback is implemented as the actual chain (img-src → default-src, but frame-ancestors and base-uri fall back to nothing), and the evaluator is checked against 60 reference cases plus a bypass scanner that finds the classic 'self'-plus-a-CDN hole. Most CSP headers are decoration, and the reason is two clauses


      
A CSP looks like a firewall rule and behaves like one — mostly. The gap between "I wrote a
      policy" and "I have a policy" is almost always one of two lines in the spec.


      
1. 'unsafe-inline' is ignored when a nonce is present


      
script-src 'self' 'nonce-r4nd0m' 'unsafe-inline'


      
Read that as a human and it says "allow inline scripts". Read it as a browser and the
      'unsafe-inline' is discarded, because a nonce or hash is also
      present. Only nonced scripts run.


      
This is deliberate and it is the best-designed clause in the spec: it lets you ship
      'unsafe-inline' as a fallback for browsers too old to understand nonces, without
      weakening the policy for browsers that do. The old browser gets a permissive policy; the
      modern one silently ignores it.


      

        
The failure mode is the reverse: somebody adds
        'unsafe-inline' to "fix" a broken widget, sees no change, and concludes CSP is
        not working. It is working. The nonce is overriding them, and the fix they actually needed
        was to nonce the widget.

      


      
2. 'strict-dynamic' discards your allowlist entirely


      
script-src 'nonce-abc' 'strict-dynamic' https://cdn.example.com 'self'


      
Every host in that line is ignored. With 'strict-dynamic',
      trust propagates by provenance: a script you noncedmay load further scripts, and
      hosts, schemes and 'self' stop meaning anything.


      
That is usually what you want — host allowlists are famously bypassable — but a policy
      that lists ten CDNs next to 'strict-dynamic' is a policy whose author expected
      those CDNs to matter, and they do not.


      
The wildcard has holes, on purpose


      
img-src * does not mean "any image". * matches network schemes
      only — it deliberately excludes data:, blob: and
      filesystem:, because those are the ones an attacker can construct without
      controlling a host. You have to list data: explicitly, and once you do,
      img-src * data: allows <img src="data:image/svg+xml,…"> —
      which is a script vector in some contexts.


      
Host matching is stricter than a glob


      
    
        
  • *.example.com matches a.example.com and
        a.b.example.com, but not example.com.
    • 
        
  • example.com matches any port and any path, but not a subdomain.
    • 
        
  • A source with no scheme inherits the document's, and then http upgrades to https —
        never the other way. On an https page, example.com allows
        https://example.com and refuses http://example.com.
    • 
        
  • A path in the source is a prefix match, and a source ending in
        / matches that whole directory.
    • 
      


      
Fallback is a chain, and it stops


      
img-src missing? Fall back to default-src. But
      frame-ancestors, base-uri, form-action and
      report-uri do not fall back — a policy with only
      default-src 'self' does not restrict framing at all, which surprises people who
      believe they have replaced X-Frame-Options.


      
Two more links in the chain are easy to miss: script-src-elem and
      script-src-attr fall back to script-src before reaching
      default-src, and worker-src falls back to
      child-src first.


      
The bypass that ships most often


      
script-src 'self' https://some-cdn.example reads as tight. If that CDN hosts
      user-uploaded files, or an old AngularJS build, or a JSONP endpoint, the policy is
      over — an attacker points a script tag at the allowed host and CSP approves it. The
      audit panel on this page flags exactly this shape, because it is the single most common way a
      real policy turns out to be decorative.


    

  






  

    


      
🔨 How it is built


      
1. Parse to a map, keeping duplicates out

      
function parsePolicy(text){
  const out = {};
  for (const part of text.split(';')){
    const tok = part.trim().split(/\s+/).filter(Boolean);
    if (!tok.length) continue;
    const name = tok[0].toLowerCase();
    if (name in out) continue;       // FIRST occurrence wins - later ones are ignored
    out[name] = tok.slice(1);
  }
  return out;
}

      
First occurrence wins. Repeat a directive and the browser keeps the first and drops the
      rest — so a policy that "fixes" a directive by appending a looser copy at the end changes
      nothing, which is the second most common misconception after the nonce one.


      
2. Fallback is a table, not an if-chain

      
const FALLBACK = {
  "script-src-elem": ["script-src", "default-src"],
  "script-src-attr": ["script-src", "default-src"],
  "worker-src":      ["child-src", "script-src", "default-src"],
  "img-src":         ["default-src"],
  "frame-ancestors": [],      // does NOT fall back
  "base-uri":        [],
  "form-action":     []
};

      
Written as data, so the empty arrays are visible. As an if-chain the missing cases look
      like omissions; as a table they look like what they are — the spec saying "no fallback here".


      
3. The two clauses that rewrite the source list

      
function effectiveSources(list){
  const hasNonceOrHash = list.some(s => /^'(nonce|sha(256|384|512))-/.test(s));
  const strictDynamic  = list.includes("'strict-dynamic'");

  let out = list.slice();
  if (hasNonceOrHash) out = out.filter(s => s !== "'unsafe-inline'");   // spec: ignored
  if (strictDynamic)  out = out.filter(s => survivesStrictDynamic(s));  // see below
  return out;
}

      
Both filters run before any matching, which is why the page can show you the
      effective list next to the one you wrote.

      
The second filter was written as isKeyword(s) first, and the tests caught it.
      That drops hosts and schemes — and keeps 'self', because
      'self' is a keyword. Under 'strict-dynamic' the browser ignores
      'self' too, so the evaluator would have reported a policy as protected by an
      origin the browser was not consulting:

      
const survivesStrictDynamic = s =>
  isNonce(s) || isHash(s) ||
  ["'strict-dynamic'","'unsafe-eval'","'wasm-unsafe-eval'",
   "'unsafe-hashes'","'report-sample'","'none'"].includes(s.toLowerCase());
// NOT 'self', and NOT 'unsafe-inline' - both are ignored under strict-dynamic

      
An allowlist again, for the same reason as the schemes: the failure mode of a denylist here
      is silently trusting something.


      
4. Host matching, with the three traps

      
if (src.host.startsWith("*.")){
  const suffix = src.host.slice(1);                 // ".example.com"
  if (!url.host.endsWith(suffix)) return false;     // and NOT example.com itself
} else if (src.host !== url.host) return false;

// scheme: inherit the document's, then allow the http -> https upgrade only
if (!src.scheme){
  if (url.scheme !== docScheme && !(docScheme === "http" && url.scheme === "https"))
    return false;
}

// path is a PREFIX, and a trailing slash means the whole directory
if (src.path && !url.path.startsWith(src.path)) return false;

      
The slice(1) keeps the leading dot, which is the entire reason
      *.example.com refuses example.com. Drop the dot and you have written
      a policy one notexample.com away from useless.


      
5. The wildcard's exclusions are explicit

      
const NETWORK_SCHEMES = ["http", "https", "ws", "wss", "ftp"];

if (src.raw === "*") return NETWORK_SCHEMES.includes(url.scheme);
// data:, blob:, filesystem: are NOT covered by * - they must be listed by name

      
An allowlist of schemes rather than a denylist. A denylist would silently admit whatever
      scheme the platform adds next, which is the wrong default for a security control.


      
6. Sixty reference cases, and an audit that finds real holes

      
// each case: policy, document origin, load, expected verdict
{ p: "script-src 'self' 'nonce-x' 'unsafe-inline'", doc: "https://a.com",
  load: { type: "script", inline: true, nonce: null }, want: "BLOCK",
  why: "'unsafe-inline' is ignored because a nonce is present" }

      
The reference set is where the traps live: nonce-overrides-unsafe-inline,
      strict-dynamic-discards-hosts, *-excludes-data:,
      *.example.com-refuses-the-apex, scheme upgrade one way only, and
      frame-ancestors not falling back. Every one of them is a case where a plausible
      implementation gives the opposite answer.
