💾 A real HTTP Range parser — the header behind every resumed download, every seek in a <video> tag and every byte-serving PDF viewer. bytes=0-499, bytes=500-, bytes=-200, and any comma-separated mixture of the three. This implements RFC 7233 end to end — parse, satisfy, clamp, drop, coalesce — and emits the Content-Range headers a server would actually write. 🔴 The most-missed rule is that a backwards range poisons the whole field, not just itself: bytes=0-99,7-3 is not “one good range and one bad one”, it is a syntactically invalid header, so the server ignores it and serves 200 with the entire body. 🔴 And invalid is not unsatisfiable — bytes=9999- against a 1,000-byte file is perfectly well formed and therefore earns a 416, while bytes=abc earns a 200. Getting those two confused is how a byte-serving endpoint ends up answering 416 to clients that should have received the whole file. Every figure here is a count over an enumerated corpus of 1,124 headers × 9 representation lengths = 10,116 decisions, each checked against six invariants, with 0 violations. The split is 3,240 ignored (32.03%), 5,559 partial (54.95%), 1,317 unsatisfiable (13.02%) — so on this corpus a malformed field is 2.46× more common than a 416, which is the ratio a server that conflates them gets wrong.

1. Invalid and unsatisfiable are different outcomes

🔴 This is the table worth memorising. A field the parser cannot read is ignored — RFC 7233 is explicit that a Range the recipient does not understand or cannot parse is dropped, which means an ordinary 200 with the whole body. A field that parses cleanly but whose every member starts past the end is unsatisfiable, and that is the only situation 416 exists for. The highlighted row is the trap: first > last invalidates the entire field, so the most obviously “bad” range in the list lands in the 200 column, not the 416 one.

2. Clamping, and the identities it has to obey

Three different spellings of “give me everything” have to produce one identical range, and they do: bytes=0-, bytes=-len and bytes=0-(len-1) all resolve to the single range 0–(len-1) at every non-zero length tested. The zero row is greyed out because the identity has nothing to say there — there is no whole representation to name, and 0-(len-1) spells 0--1, which is not a legal spec at all. A suffix longer than the representation clamps to the whole representation instead of failing, and a last past the end clamps to len-1 instead of failing. Only first can push a range off the end into unsatisfiable territory — which is exactly why bytes=900-9999 is a 206 and bytes=9999- is a 416 against the same file.

3. Partial satisfaction and coalescing, where servers get sloppy

When some members are satisfiable and some are not, the unsatisfiable ones are dropped and what remains is served as a 206. It is not a 416 and it is not an error. Across the audited corpus — decisions land in that middle case. Coalescing then shrinks the answer further — — of the 206 decisions emit fewer parts than the client wrote, because overlapping and adjacent members are merged first. Adjacency is the subtle half: 0-99 and 100-199 share no byte, but they are one contiguous run and a server that emits them as two multipart parts is shipping boundary overhead for nothing.

What this covers, and what it does not

The parser implements the bytes unit: first-last, first-, -suffix, comma-separated sets with optional whitespace around the commas, clamping, dropping unsatisfiable members, coalescing, the 200/206/416 decision, and the Content-Range forms including bytes */len. It is not a complete server. Out of scope, and each one changes real behaviour: If-Range and the conditional dance that decides whether a range is honoured at all, Accept-Ranges advertisement, the actual MIME body bytes with their boundary delimiters and CRLFs, Content-Encoding interacting with byte offsets, and ranges against a representation whose length is not known when the request arrives. Three strictness choices are documented rather than hidden: an empty list element such as bytes=0-1,,4-5 is treated as invalid where RFC 7230's list rule would let a recipient skip it; whitespace around the = is rejected because the grammar has none there; and bytes=-0 is treated as unsatisfiable, since a zero-length suffix selects no bytes at all.

How it works

// the rule everyone gets wrong: this poisons the FIELD, not the member
if (last !== null && first > last)
  return bad("first-byte-pos " + first + " is greater than last-byte-pos " + last);

// only first-byte-pos can make a range unsatisfiable - last merely clamps
if (spec.first > len - 1) return null;
const last = spec.last === null ? len - 1 : Math.min(spec.last, len - 1);

// adjacent, not merely overlapping: 0-99 and 100-199 are ONE part
if (prev && s[i].first <= prev.last + 1) prev.last = Math.max(prev.last, s[i].last);

The three-way decision

the field does not parse   -> 200, whole body      (it is ignored, not rejected)
it parses, nothing fits    -> 416 + bytes */len   (nothing else ever gives 416)
it parses, something fits  -> 206, the rest dropped

Self-check

Runs on load. Several are controls: a claim that a malformed field yields 200 means nothing without the paired case that a well-formed impossible field yields 416, so both directions of the 416 rule are asserted; the coalesced output is compared against a byte-by-byte set union rather than against itself; and the adjacency rule is paired with a one-byte gap that must not merge.
