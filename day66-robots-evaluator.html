🤖 robots.txt evaluator — a real RFC 9309 engine, not a syntax checker. Paste a file and a URL and it answers whether a given crawler may fetch it, and which line decided. The rule almost nobody implements is the one that matters: when Allow and Disallow both match, the longest rule wins, not the first — and on a tie, Allow does. The original 1994 convention was first-match-wins, and the two answers differ on real files, which the page measures rather than asserts. Group selection is the second trap: a crawler obeys exactly one group, the most specific match on its name, and rules are never merged across groups — so adding a User-agent: Googlebot block silently removes every * rule for Googlebot, which is how sites accidentally open their whole tree to one crawler. Plus the parts that are not rules at all (Sitemap, Crawl-delay), the scope limits nobody reads (robots.txt is per scheme, host and port), and */$ matching implemented properly. 48 reference cases. Pure vanilla JavaScript, one file, offline.

48 REFERENCE CASES


      


    

  






  

    


      
Everyone can read robots.txt. Almost nobody can evaluate it.


      
The file looks like the simplest configuration format in existence, which is exactly why
      the three rules that matter get skipped.


      
1. Longest match wins, not first


      
Disallow: /search
Allow: /search/public


      
Is /search/public/page allowed? Under RFC 9309, yes: both rules match, and
      /search/public is longer. Under the original 1994 convention it was
      first match wins, so the Disallow would take it — and plenty of parsers still do
      that.


      
On a tie, Allow wins. That asymmetry is deliberate: it makes the file
      fail open rather than closed, on the theory that an ambiguous rule should not silently
      de-index a site.


      
2. One group applies. Never a merge.


      

        
This is the one that causes real incidents. A crawler picks the
        most specific group whose user-agent matches it, and obeys
        only that group. Rules from User-agent: * are not inherited.

      


      
User-agent: *
Disallow: /admin/
Disallow: /private/

User-agent: Googlebot
Disallow: /private/


      
Googlebot may now crawl /admin/. Someone added a Googlebot block to tighten
      one path and silently removed every other restriction for that crawler. The page shows the
      group selection separately for exactly this reason.


      
Specificity is longest-prefix on the user-agent token, and matching is
      case-insensitive — while path matching is case-sensitive.
      Two different rules in one file.


      
3. The wildcards are real, and $ is not a regex


      
    
        
  • * matches any sequence, including empty and including /.
    • 
        
  • $ anchors the end — and only at the end of a rule. In the middle it is a
        literal dollar sign.
    • 
        
  • Everything else is literal. There are no character classes, no alternation, and
        escaping a * is not possible.
    • 
      


      
The safe implementation is to translate the pattern into a regex with every other
      metacharacter escaped, which is exactly what the page does — and the test that matters is
      that a rule containing . or + matches those characters
      literally.


      
What robots.txt does not do


      
    
        
  • It is not access control. It is a request. A disallowed URL is still
        served to anyone who asks.
    • 
        
  • It does not remove pages from an index. A blocked page can still be
        listed from inbound links — and blocking it prevents the crawler from ever seeing a
        noindex tag, which is the opposite of what people intend.
    • 
        
  • It is scoped to one origin. Scheme, host and port.
        https://example.com/robots.txt says nothing about
        http://example.com, https://www.example.com or port 8443.
    • 
        
  • Sitemap and Crawl-delay are not exclusion rules.
        Sitemap is global and outside any group; Crawl-delay is not in the
        RFC at all and is ignored by some major crawlers.
    • 
      


      
The default is allow


      
No matching rule means allowed. A missing file means allowed. An empty
      Disallow: means allowed — it is the documented way to say "everything". And a
      5xx on the robots.txt fetch means most crawlers assume disallow all temporarily,
      which is the one case where a server error is quietly worse than a 404.


    

  






  

    


      
🔨 How it is built


      
1. Parsing into groups, which is not line-by-line

      
// consecutive User-agent lines start ONE group with several names
if (field === "user-agent"){
  if (!collecting) { current = { agents: [], rules: [] }; groups.push(current); collecting = true; }
  current.agents.push(value.toLowerCase());
} else if (field === "allow" || field === "disallow"){
  collecting = false;                       // the next User-agent starts a NEW group
  current.rules.push({ type: field, path: value });
}

      
The collecting flag is the whole grammar. Without it, two adjacent
      User-agent lines become two groups instead of one shared group, and a file that
      addresses several crawlers together falls apart.


      
2. Pattern to regex, with everything else escaped

      
function toRegex(pattern){
  let anchored = false, p = pattern;
  if (p.endsWith("$")) { anchored = true; p = p.slice(0, -1); }
  const body = p.replace(/[.+?^${}()|[\]\\]/g, "\\$&")   // escape ALL metacharacters
                .replace(/\*/g, ".*");                    // then re-enable the one wildcard
  return new RegExp("^" + body + (anchored ? "$" : ""));
}

      
Escape first, then re-enable *. Doing it the other way round lets a
      . in a path rule match any character, which turns
      Disallow: /a.pdf into a rule that also blocks /axpdf.


      
3. The decision: longest wins, Allow breaks ties

      
let best = null;
for (const rule of group.rules){
  if (!toRegex(rule.path).test(path)) continue;
  const len = rule.path.length;
  if (!best || len > best.len ||
      (len === best.len && rule.type === "allow" && best.type === "disallow"))
    best = { ...rule, len };
}
return best ? best.type === "allow" : true;      // no rule matched -> ALLOWED

      
Three clauses and a default. The tie-breaker is the middle condition, and the default at
      the end is the one people invert — robots.txt is allow-by-default, and a parser that returns
      "denied" for an unmatched path will quietly stop crawling a whole site.


      
4. Group selection is longest-prefix on the name

      
let best = null;
for (const g of groups)
  for (const agent of g.agents){
    if (agent === "*"){ if (!best) best = { g, score: 0 }; continue; }
    if (ua.toLowerCase().startsWith(agent) && (!best || agent.length > best.score))
      best = { g, score: agent.length };
  }
return best ? best.g : null;                     // null -> nothing applies -> allowed

      
startsWith, not equality: the RFC says a crawler matches a group if the
      product token is a prefix of its user-agent string. And the * group scores
      zero rather than being skipped, so it is used only when nothing else
      matches — which is what makes "adding a specific group removes the wildcard rules" fall out
      of the code rather than needing a special case.


      
5. The comparison that makes the finding measurable

      
const rfc = allowed(file, ua, path, "longest");
const old = allowed(file, ua, path, "first");
if (rfc !== old) disagreements++;

      
Both strategies implemented behind one flag, run over a generated corpus of paths, and the
      disagreement count printed. "The 1994 rule gives different answers" is a claim; a number is
      a finding.


      
6. What the 48 reference cases cover

      
empty Disallow allows everything      Disallow: / blocks everything
longest match wins                    ties go to Allow
$ anchors, and only at the end        a literal . does not match any char
* matches across slashes              paths are case-SENSITIVE
user-agents are case-INSENSITIVE      a specific group REPLACES the * group
consecutive User-agent lines = 1 group   Sitemap is not a rule
no rules at all -> allowed            no matching group -> allowed

      
Each of those is a case where a plausible implementation gives the opposite answer, which
      is the only reason to write a reference case at all.
